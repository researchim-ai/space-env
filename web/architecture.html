SYSTEM DESIGN / КАК ЭТО РАБОТАЕТ

Один мир.
Несколько способов действовать.

Конфигурация описывает миссию. Runtime исполняет физику. Интерфейс агента ограничивает доступное знание. История связывает решения с результатом и обучающими данными.

SPACE—ENV / LAYERS

Путь одного решения

  1. 01

    Мир и задача

    Начальные орбиты, аппараты и станции, механики, заявки, роли и условия завершения.

    configuration + task + seed
  2. 02

    Наблюдение роли

    Проекция текущего состояния и доступных действий. Скрытое будущее и операторские инструменты не добавляются в интерфейс агента.

    role-scoped observation
  3. 03

    Выбор действия

    Python-политика, числовой RL-агент или LLM выбирает команду. Консервативная маска помогает, но окончательное решение принимает native-допуск.

    action / joint_step
  4. 04

    Физическое исполнение

    Ресурсы и геометрия меняются во времени. Долгая операция может занимать несколько решений; отправка команды не означает мгновенный результат.

    TaskSession → MissionRuntime
  5. 05

    Оценка и сохранение

    Изменения продуктов, ACK, reward и завершение фиксируются вместе с ревизией, происхождением и checkpoint.

    events + reward + replay
SPACE—ENV / INTERFACES

Интерфейсы поверх task-runtime

PYTHON

TaskSession

Прямой контроль шага и наблюдений; управление бюджетом и длительностью решения. Подходит для baseline-политик, воспроизводимых исследований и интеграции планировщиков.

GYMNASIUM

MissionTaskEnv

Числовые наблюдения, presence masks и каталог действий конкретной задачи. Интерфейс для RL без обязательной глобальной регистрации среды.

PETTINGZOO

MissionParallelEnv

Раздельные роли и совместное физическое исполнение. Подходит для multi-agent постановок с общими ресурсами.

LLM

LLMEpisode + policy

Структурированные инструменты и диалоговая история, связанная с native-переходами. Сохраняются ошибки, бюджет и публичная обратная связь.

Общий исполнитель относится к новому task-слою. Legacy Gym-среды остаются отдельным слоем. Текущий измеренный Qwen-эксперимент — один центральный LLM-контроллер трёх ролей, а не три независимо общающихся LLM.

SPACE—ENV / STATE

Состояние важнее списка команд

Продукт проходит наблюдение, обработку, передачу, подтверждение и завершение. На каждом этапе у него есть размер, владелец и временные ограничения. Память, CPU и терминалы нельзя резервировать независимо от этой истории.

Ревизия состояния и idempotency защищают от повторного применения одного вызова. Совместный раунд группировки собирает предложения ролей и исполняет согласованный шаг; конфликтующие притязания на общий ресурс должны пройти проверку допуска.

Оператор может создавать ветки и вводить события сценария. Агент видит только разрешённую проекцию и действует через собственный контракт — операторское знание не становится его обучающим наблюдением.

SPACE—ENV / REPLAY

Воспроизводимость — отдельный результат

Native replay восстанавливает исходное состояние и повторно исполняет записанные действия. Проверяется согласованность переходов и результата, а не только структура JSON. Для LLM дополнительно связываются prompt, schema, raw-ответ, декодированная команда и реально переданный вызов.

Аудит не повторно сэмплирует модель и не обещает побитово одинаковый ответ другого GPU или inference-сервера. Он проверяет зафиксированный эксперимент. Согласованный replay также не доказывает физическую точность или оптимальность поведения.

SPACE—ENV / BOUNDARIES

Границы ответственности

Библиотека моделирует операции и последствия решений в явно заданных инженерных профилях. Она не подключена к реальному аппарату как полётный контур. Mission Control — локальный интерфейс к симуляции; этот статический сайт показывает документацию и сохранённый снимок интерфейса.

Для новой миссии нужны проверка единиц и эпохи, выбранная детализация, независимые физические сравнения и собственный набор задач. Эти требования нельзя заменить увеличением количества страниц, тестов или параметров.
