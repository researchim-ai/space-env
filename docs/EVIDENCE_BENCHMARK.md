# Воспроизводимый бенчмарк космических миссий для AI

Цель — отделить измеренную точность, исполнимость миссий, масштаб и результаты
агентов от заявлений о превосходстве. Бенчмарк не выдаёт общего балла и не
объявляет отсутствующие внешние системы проигравшими.

Фактически выполненные прогоны и ограничения:
[результаты 10 ноября 2026 года](EVIDENCE_BENCHMARK_RESULTS_20261110.md).

## Запуск

Из корня репозитория с установленными reference-зависимостями:

```bash
python -m space_env.validation.evidence_benchmark --profile smoke --output artifacts/evidence-smoke
python -m space_env.validation.evidence_benchmark --profile full --output artifacts/evidence-full
python -m space_env.validation.evidence_benchmark --audit artifacts/evidence-full
```

Каждый запуск требует нового каталога. `full` обозначает всю фиксированную
матрицу этого протокола, а не полное моделирование всех космических процессов.
Это локальная команда, CI и публикация не требуются. Проверяйте статусы треков
в `report.json`, физический `passed` и масштабный `ok`: наличие JSON-отчёта
само по себе не означает прохождения проверок.

Перед измерениями сохраняются manifest, SHA исходников и версии зависимостей.
Во время исполнения сохраняется progress. Ошибки треков и отдельных эпизодов
остаются в отчёте, а не исключаются из результатов.

## 1. Физические проверки

Повторно используются существующие независимые аналитические проверки
`validation.ai_reference_suite`: выбранные орбитальные, двигательные,
энергетические, тепловые, радиотехнические и rigid-body соотношения. Область
применимости каждой проверки остаётся исходной — проверка формулы не
квалифицирует произвольную связанную миссию.

Также исполняются существующие проверки формул сил против boinor и
J2-дуги против LSODA. Константы, EOP/повороты, плотность атмосферы и положения
Солнца/Луны частично общие. Это внешняя реализация формул и другая семья
интеграторов, но не независимая проверка этих входных данных.

Добавлен общий протокол траекторий для трёх задач:

- круговая LEO;
- эллиптическая LEO;
- высокоэллиптическая MEO.

Включена только центральная ньютоновская гравитация. `smoke` имеет горизонт
3600 секунд, `full` — 21600 секунд, выдача через 300 секунд, включая начало
и конец. Эталон решает уравнение Кеплера отдельно от production RHS и solver:

```text
M = sqrt(mu/a^3) * t
E - e*sin(E) = M
x = a*(cos(E)-e)
y = a*sqrt(1-e^2)*sin(E)
dE/dt = sqrt(mu/a^3)/(1-e*cos(E))
```

Поворот орбитальной плоскости фиксирован исходным наклонением. Метрики —
максимум евклидовой ошибки положения и скорости на общей сетке. Заранее
заданы границы 0.01 м и 1e-5 м/с. Это численные бюджеты синтетической
центральной задачи, а не сантиметровая точность прогноза реального аппарата.

## 2. Миссии и решения

`full`: 28 рецептов каталога × 3 политики = 84 предобъявленные попытки.
`smoke`: шесть рецептов × 3 политики = 18 попыток.

Политики:

- `wait`: бездействие;
- `public_memory`: только публичные наблюдения, каждый выбранный action ID
  используется однократно;
- `reference_schedule`: привилегированное заранее заданное расписание.

Все получают одинаковые native scenario/task внутри каждой задачи. Рецепты
включают отрицательные случаи, недостаточное топливо, неверное направление,
проблемы связи и ограничения ресурсов. Их не отбирают по успешности политики.
Сценарии остаются известной публичной регрессией, не слепым/OOD-тестом.

Записи исполняются и проверяются через `LLMEpisode` и native cold replay.
Отдельно считаются попытки, ошибки, успехи и чистые успешные эпизоды.
Привилегированные демонстрации не становятся результатами LLM.

Все записи имеют split `test`. **Обучающие JSONL из этого набора не создаются**;
аудит отвергает такие файлы в соответствующих путях. Для SFT/RL используйте
отдельный train-корпус с разделением семейств и происхождения данных.

## 3. Масштаб

Используется существующий `scaling.benchmark`, каждый повтор — свежий процесс
с одним численным потоком. `full`: 2, 4, 8, 16 аппаратов и соответственно
8, 16, 32, 64 продуктов; два повтора каждой нагрузки. `smoke`: первые две
нагрузки, также по два повтора.

Это ресурсные задачи на фиксированных эфемеридах, а не одновременная
высокоточная динамика всех аппаратов. Измеряются execution/replay/export,
p50/p95 шага, process-lifetime peak RSS, размер checkpoint, выполнение задач
и native replay. Публикуются оборудование и настройки потоков. Время
создания геометрии не входит в worker execution, end-to-end учитывается
отдельно. Нельзя экстраполировать эти результаты на весь backend, тысячи
спутников или другой компьютер. Два повтора — диагностическое измерение,
не статистически устойчивый speedup над конкурентом.

## 4. Польза для обучения агентов

По умолчанию статус `not_measured`. Скриптовые демонстрации, успешные
траектории и работающий экспорт сами по себе не доказывают улучшения модели.

Для отдельных записей реального LLM поддержан парный анализ:

```bash
python -m space_env.validation.evidence_benchmark --profile full --learning paired-learning.json --output artifacts/evidence-with-learning
```

Входной JSON содержит `before_records`, `after_records`, `disclosure`.
Первые два поля — массивы штатных `space-env.llm-episode/1` записей.
`disclosure` содержит:

```json
{
  "training_groups": ["training-family-example"],
  "training_dataset_sha256": "64 lowercase hex digits",
  "before_weights_sha256": "64 lowercase hex digits",
  "after_weights_sha256": "64 lowercase hex digits",
  "before_inference_trace_sha256": "64 lowercase hex digits",
  "after_inference_trace_sha256": "64 lowercase hex digits"
}
```

Строки в примере — описания формата; замените их действительными SHA-256.
Требуются test split, `external_llm`, одинаковые prompt/tools/бюджеты/начальные
checkpoints внутри пары. Повторённые группы, пересечение train/test и один
checkpoint под несколькими независимыми метками отвергаются. На группу
принимается один исход; попытки без успеха остаются в знаменателе.

Вычисляются изменение success rate, улучшения/регрессии и точный двусторонний
тест Мак-Немара через биномиальное распределение несогласных пар. Сигнал
`paired_improvement_detected` требует минимум 20 групп, p < 0.05 и положительное
направление. Это заранее объявленный минимальный фильтр, а не анализ мощности.
Независимость групп должна обеспечиваться дизайном набора, а не названиями.

Native replay проверяет поведение в среде. Переданные SHA весов, обучения и
inference trace — декларации отправителя: этот импортёр не воспроизводит
обучение и не удостоверяет происхождение вызовов модели. Даже положительный
парный результат не является автоматически доказанной причинной пользой SFT/RL.
Для такого вывода нужны исходные датасеты, обучение, inference audit и
контроль условий. В отчёте сохраняется `training_proven: false`.

## Внешние системы

Официальные источники, проверенные 10 ноября 2026 года:

- [Basilisk](https://avslab.github.io/basilisk/) — орбитальная/ориентационная
  динамика, FSW/HIL, Monte Carlo и проверка модулей.
- [BSK-RL](https://avslab.github.io/bsk_rl/) — построение Gymnasium-сред на
  Basilisk; документация показывает EO, инспекцию и Space Domain Awareness.
- [Orekit API](https://test.orekit.org/site-orekit-latest/apidocs/index.html) —
  системы времени/координат, модели сил, манёвры, оценивание и пропагаторы.
- [Tudat](https://docs.tudat.space/en/latest/) — пропагация, оценивание и
  проектирование миссий, включая межпланетные задачи.

Это сведения из документации, **не измеренные сравнительные результаты**.
Наличие модуля также не означает, что он успешно исполняется. Бенчмарк
показывает inventory `not_installed`/`not_executed` отдельно от submissions.

Сначала экспортируйте общий manifest:

```bash
python -m space_env.validation.evidence_benchmark --profile full --manifest-only --output artifacts/common-manifest.json
```

Внешний runner должен использовать ровно `trajectory_manifest` этого файла:
константу mu, начальное состояние, epoch, GCRS, SI и всю заданную сетку времени.
Нельзя без преобразования подписывать TEME/EME2000 как GCRS. Не допускаются
подмена силы, интерполяция на другую сетку, пропущенные задачи и неполный
горизонт. Формат описан в `docs/schemas/external-trajectories-v1.json`.
Каждая траектория содержит `case_id`, SHA соответствующего case и состояния
`[x,y,z,vx,vy,vz]`. Корневой `manifest_sha256` относится **к вложенному
trajectory_manifest**, а не всему four-track manifest. SHA получают штатным
`space_env.simulation.snapshot.digest` от JSON-объекта без дополнительного seal.

```bash
python -m space_env.validation.evidence_benchmark --profile full --external artifacts/basilisk-trajectories.json --output artifacts/with-external
```

Сохраняются версия движка, настройки solver и SHA адаптера. Принимаются
Basilisk, BSK-RL, Orekit и Tudat. Для Basilisk добавлен отдельный runner
`examples/validation/basilisk_trajectory.py`; для остальных трёх движков
нативные runner-адаптеры этим изменением **не реализованы**. Приёмник сравнивает представленные
траектории с одним аналитическим эталоном. Имя движка и SHA адаптера не
удостоверяют, что данные действительно были получены этим движком.


### Runner Basilisk

Опциональная зависимость — официальный `bsk==2.12.2`, установленный отдельно
от основных зависимостей. Runner следует API из
[официального примера орбиты](https://avslab.github.io/basilisk/examples/scenarioBasicOrbit.html).

```bash
python examples/validation/basilisk_trajectory.py --manifest artifacts/evidence-full/manifest.json --output artifacts/basilisk-trajectories.json
```

Используется native `Spacecraft`, центральный `GravBodyData` с общей mu,
RKF78 (relTol 1e-12, absTol 1e-8), шаг задачи 30 секунд и вывод 300 секунд.
Все три задачи обязательны. Никакая production acceleration space-env на
измеряемой стороне Basilisk не вызывается. Инерциальные оси N и начальные
векторы задаются как GCRS; для автономной центральной задачи отдельное
преобразование систем времени/координат не требуется. Это **не проверка**
Basilisk frame/time API и не допустимый обход преобразований в возмущённых
задачах. Шаги и tolerances разных интеграторов не тождественны: сравнивается
прохождение общего accuracy gate, а не скорость или оптимальность solver.

## Что проверяет audit

- целостность manifest, его фиксированную матрицу и текущие исходники;
- каждую успешную запись native replay, исходный рецепт и метрики;
- соответствие baseline-действий причинной истории сообщений;
- сохранение всех строк и привилегированности reference;
- отсутствие held-out training exports;
- вычисление ошибок траекторий и внешних сравнений;
- парный анализ переданных результатов обучения.

Масштабные JSON проверяются на целостность. Тайминги, физические force-checks
и процессы масштаба заново не запускаются этой командой. Для новых измерений
запустите новый benchmark. SHA — проверка целостности, не цифровая подпись и
не свидетельство доверенного времени или внешнего исполнения.

## Что остаётся до заявления о лидерстве

Расширить runner Basilisk и реализовать адаптеры остальных движков; согласовать физику,
системы координат, численную точность и функциональный объём. Добавить
контактную/относительную динамику и длинные возмущённые миссии к общим
сравнениям. Провести реальное обучение и независимый held-out эксперимент.
Расширить масштабные профили до связанных группировок с динамикой и отказами.
Получить независимый запуск и, для реальной достоверности, полётные данные.

Ни тесты, ни этот протокол не дают оснований заявлять «лучше всех» во всех
областях моделирования космических аппаратов.
