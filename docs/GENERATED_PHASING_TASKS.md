# Генерация орбитальных задач и train/development/test

Дополнение: [выбор эпохи манёвра и общие dispatch slots](WINDOWED_ORBIT_PLANNING.md).
Приведённые ниже результаты относятся к immediate generation; новое windowed
семейство проверяется отдельно и увеличивает общий каталог до 27 профилей.

Обновление 15 ноября 2026 года добавляет версионированную генерацию локального
фазирования. В общем каталоге теперь **5 семейств и 24 профиля**. Новые записи:

- `orbit_and_deployment/generated_train`
- `orbit_and_deployment/generated_development`
- `orbit_and_deployment/generated_test`

Каталожные записи — стартовые примеры с двумя аппаратами и seed=0. Генератор
поддерживает 2–8 аппаратов и другие seed через конфигурацию `OrbitSession`.
Это не ограничение пространства задач тремя каталожными примерами.

## Что выбирает агент

Для каждого аппарата опубликованы два противоположных шаблона конечной тяги.
За один шаг допускается не больше одного действия для роли аппарата. Агент
видит текущее идеальное положение, скорость, массу, команды, целевое состояние,
эпоху и характеристики двигателя. Он должен выбрать подходящий манёвр,
а затем дождаться оценки цели с сохранением топлива.

Генератор меняет тягу, длительность 10/15/20 s, исходное топливо 7–10 kg,
ориентацию плоскости и требуемый знак манёвра. Имена действий непрозрачные;
порядок правильного/неправильного варианта меняется. Генерация seed основана на
SHA-256 с явным version namespace, а не на process-dependent Python `hash()`.

Цель конструктивно вычисляется по одному из вариантов отдельным RK4 h=0.005 s.
Эталонный выбор сохраняется только в privileged recipe, в `reference_steps`.
Ни расписание, ни seed/split, ни generation metadata в observation и тексте
задания не публикуются. Целевое состояние публикуется намеренно: без него
задача управления была бы не определена. Из физики и непрозрачных ID потенциально
можно идентифицировать известный пример; полной неразличимости сценариев
или отсутствия любых side channels не заявляется.

## Разделение распределений

Определены непересекающиеся режимы:

- train: горизонт 40 или 50 s, тяга 0.60–1.20 N;
- development: 60 или 70 s, тяга 1.25–1.50 N;
- test: 80 или 90 s, тяга 1.55–1.80 N.

Это удержанные диапазоны двух параметров внутри **одного семейства центральной
гравитации и одного происхождения моделей**. Они не являются независимой
аппаратной валидацией, новым семейством физических сил или полноценной оценкой
переноса промышленной автономии.

Manifest хранит конфигурации, диапазоны, source manifest и physical identity.
Physical digest включает definition, goal и нормализованные команды без
искусственных command IDs. Таким образом, простое переименование действий
не маскирует точный дубликат. В пределах manifest точные совпадения отклоняются;
скрытого resampling и фильтрации по успешности baseline нет. Близкие задачи
не считаются независимыми только потому, что их digest различается.

## Публичная базовая политика

`orbit_policy` выбирает по одному шаблону на аппарат по прогнозу конечной ошибки
положения. Использует только опубликованные состояние, параметры двигателя,
цели и команды. Для нескольких вариантов выполняется собственный RK4 h≤0.25 s
с изменением массы; native solver и приватный эталон не вызываются.

\[
J(a)=\|\widehat{\mathbf r}_a(t_g)-\mathbf r_g\|_2.
\]

Выбирается действие с минимальным J, затем политика ждёт. Для прежнего
фиксированного рецепта, где у аппарата один вариант, сохраняется выбор этого
варианта. Это численный перебор небольшого дискретного каталога в t=0,
не произвольная оптимизация траекторий, обучение или применение LLM.

## Запуск

```python
from space_env.industrial.orbits import OrbitSession
from space_env.industrial.agent import IndustrialEpisode

session = OrbitSession({
    "actors": 4,
    "generation": {"split": "train", "seed": 17},
})
episode = IndustrialEpisode(
    session, split="train", policy_origin="external_llm",
    task_text="Достичь опубликованных целевых состояний, сохранив резерв топлива.",
)
```

Split эпизода должен соответствовать generation split. `IndustrialEpisode`
отклоняет несовпадение даже при прямом вызове. `make_episode` и Gym наследуют split
из генератора; явная попытка пометить generated test-сценарий как train отклоняется.
Corpus runner и пример экспорта повторно проверяют эту принадлежность.

```bash
python -m space_env.industrial.phasing_corpus \
  --samples-per-split 2 --actors 2 \
  --output artifacts/new-phasing-corpus

python examples/modeling/export_phasing.py \
  --corpus artifacts/new-phasing-corpus \
  --output artifacts/new-phasing-training
```

Runner создаёт по одному `wait` и `public` эпизоду для каждого случая, сохраняет
все ошибки, исходный manifest, progress и результаты с replay. Число samples
на split ограничено 1–32 для этого локального инструмента. Набор не объявляется
готовым benchmark стандартом; больший охват и статистические сравнения потребуют
отдельного эксперимента.

Экспортёр проверяет обе печати, source identity, полную матрицу попыток,
принадлежность record к case, split/metrics и cold replay. Выходные JSONL
содержат **только train**:

- RL — все train-эпизоды, включая бездействие и неуспех;
- SFT — только успешные train-эпизоды без ошибок и отрицательной admission feedback.

Development/test проверяются, но их сообщения не копируются в training output.
Privileged configuration/checkpoint остаются только в исходном корпусе.
Файлы и каталоги не перезаписываются. Печати — проверки целостности, а не
подписи доверенного поставщика данных; policy_origin остаётся декларацией.

## Ограничения и следующий этап

Физика прежняя: центральное поле, инерциальная конечная тяга, идеальное состояние,
native resource surrogate; резерв равен исходному топливу минус 1.1 расчётного
расхода эталонного манёвра. Никакой гарантии непрерывной безопасности сближений,
многодневного развёртывания, J2/drag/SRP, body-frame actuation или совместной
сервисной миссии это обновление не даёт.

Следующие содержательные расширения: разные доступные эпохи манёвров, конкуренция
за ресурсы, недостижимые цели с проверяемыми причинами, несколько этапов,
неполная наблюдаемость и оценка обученной модели на более широких удержанных
режимах. Текущий конструктивный генератор создаёт цели по эталонному управлению,
а не сертифицирует существование решения каждого случая с любыми помехами.

## Измерения этого обновления

- **60 тестов прошли**: генерация и разделение режимов, правильные и неправильные
  направления, прежний адаптер и export/replay контракты, запрет перемаркировки
  split, Gym, null generation, отклонение неполной матрицы и обхода путей.
- **6 сгенерированных случаев с двумя аппаратами**, по два на split, исполнены
  с двумя политиками: **12 полных эпизодов с replay**, без ошибок инструментов.
  Численная public-политика выполнила все шесть задач, wait — ни одной.
  Это малый локальный прогон, не оценка вероятности успеха или превосходства.
- Проверены 6 разных physical identities и непересекающиеся диапазоны горизонта
  и тяги. Все случаи одного synthetic lineage; exact disjointness не означает
  независимость физических моделей.
- Собран wheel 0.134.0: **371 Python/JSON файл** совпадает побайтно. Из отдельного
  cwd выполнены discovery 24 профилей и двухшаговый generated-test эпизод
  с правильной меткой test и replay. Использовались имеющиеся зависимости,
  а не чистая установка.

Финальные данные находятся в `artifacts/phasing-generation-20261115/`:
`acceptance-corpus/`, `acceptance-tests.log`, `acceptance-export/`,
`acceptance-wheel/`, `acceptance-wheel-check.json`,
`acceptance-installed-smoke.json`. Предварительные прогоны оставлены отдельно
и не перепривязывались к окончательному source manifest.

После проверки всех 12 записей экспортированы **2 SFT и 4 RL строки** из train.
Development/test сообщения в эти JSONL не вошли; для RL сохранены также
неуспешные train-wait эпизоды. Обучение модели не выполнялось.
