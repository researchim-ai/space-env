# Адаптивные интервалы решений в непрерывной кампании

`CampaignPolicySpec` теперь имеет opt-in параметры `adaptive_wait` и
`max_wait_sec`. При `adaptive_wait=false` сохраняется прежний фиксированный
опрос. Выбор команды не меняется: изменяется только интервал бездействия,
когда по текущему публичному каталогу нечего запускать.

```python
contract = {
    "minimum_completed_requests": 3,
    "completion_action_ids": ["control"],
    "poll_sec": 0.25,
    "adaptive_wait": True,
    "max_wait_sec": 1.0,
}
action = campaign_policy(session.observe(), contract)
```

При новой команде сохраняется короткий poll_sec: контроллер может запускать
другие свободные ресурсные линии на следующих решениях. При wait интервал
ограничивается max_wait_sec, max_decision_sec и ближайшей уже видимой границей:

- Окончание текущей принятой/исполняемой команды.
- Дедлайн уже объявленной заявки.
- ready_sec продукта из текущего локального инвентаря.

Это таймеры текущего наблюдения, не прогноз фактического завершения и не запрос
будущих контактов, геометрии или внешних событий. Интервал может быть короче
poll_sec, если наблюдаемая граница близко. Прошедшие таймеры игнорируются.
Предел адаптивного ожидания должен быть не меньше poll_sec.

Внешние события по-прежнему обрабатывает TaskSession: новое поступление или отказ
прерывают и длинное ожидание. Проверка меняет будущее расписание, сравнивает
идентичные наблюдения и действия до события, затем подтверждает прерывание
в t=0.6, хотя запрошенное ожидание было длиннее. Есть replay после такого прерывания.

## Ресурсная диагностика

`AgentCampaignSession.metrics().resource_accounting` содержит копии native
energy_ledger и bus ledgers. Это trainer-only диагностика: она не добавляется
в observe(). Доступны потребление и генерация энергии, ошибки батарейного,
PV/discharge и теплового учёта. Изменение возвращённого словаря не меняет runtime.

Нулевая ошибка баланса не доказывает точность модели оборудования: это проверка
внутреннего учёта. В частности, более позднее завершение миссии может честно
увеличивать потребление энергии, даже если обращений к контроллеру стало меньше.

## Парное сравнение

```bash
python -m examples.modeling.adaptive_campaign_study --output artifacts/my-adaptive-study
python -m pytest -q tests/test_adaptive_campaign_policy.py tests/test_adaptive_campaign_interrupt.py
```

Драйвер использует шесть авторских коротких вариантов из reactive_campaign_study.
Каждая пара имеет одинаковую исходную native-конфигурацию, seed, цели, команды,
расписание событий и бюджеты 128/128. Отличается только публичный контракт
интервала решений: фиксированные 0.25 секунды либо адаптивное ожидание до 1 секунды.

Оба варианта проходят native replay и проверку каждого действия по сохранённому
публичному наблюдению. Сохраняются RL-строки и SFT успешных безошибочных эпизодов.
В отчёте — число обращений, модельное время завершения, native-ресурсы и ошибки
учёта. Для каждой пары явно приводятся сэкономленные обращения, дополнительное
время миссии и изменение расхода энергии. Отрицательные исходы не переименовываются
в успех: отмена обязательной заявки и неснятый CPU-отказ сохраняют провал цели.

## Границы применимости

Это ограниченный реактивный контроллер, не оптимальный event-driven планировщик.
Границы команды и ready_sec не гарантируют, что появилась новая полезная работа;
порог max_wait_sec ограничивает задержку реакции на изменения, которые не имеют
отдельного внешнего события. Геометрия, частичный прогресс и доступность могут
меняться внутри ожидания. Изменение момента следующего решения меняет траекторию
управления, поэтому полное совпадение продуктов/состояний по битам не заявляется.

Этот блок не меняет шаги физического интегратора и не доказывает многосуточную
точность или производительность. Шесть вариантов разделяют одну синтетическую
геометрию и не являются blind holdouts. Число вызовов — не измерение LLM-токенов,
скорости инференса или качества обученной модели.

Следующий физический блок: длительная многоволновая EO→CPU→ISL→ground кампания,
отдельные измерения исполнения и сходимости, затем более сильный планировщик
и независимые постановки для моделей.

## Измеренный результат — 16 ноября 2026

На 12 эпизодах, составляющих шесть пар, фиксированный режим потребовал 402
обращения, адаптивный — 163: на 239 обращений, или 59.45%, меньше. Все четыре
выполнимых варианта завершились успешно в обоих режимах; два отрицательных
остались провалами исходной цели. Для всех 12 эпизодов проверены native replay
и соответствие действий публичной политике.

В успешных вариантах адаптивное управление завершало миссию на 0.75–1.25 секунды
позже и расходовало дополнительно 0.00463–0.00772 Wh суммарно по двум аппаратам
данного синтетического профиля. Максимальные ошибки внутреннего учёта:
1.34e-14 Wh для энергетики и 4.27e-13 J для тепла. Это численная согласованность
счётчиков, не оценка погрешности физики относительно настоящих аппаратов.

Пройдены 47 локальных тестов. Получены 12 RL-строк и 8 SFT-строк алгоритмических
политик, без inference или тренировки модели. Из установленного wheel отдельно
выполнен сценарий позднего восстановления: 31 решение, 17.75 секунды модельного
времени; 380 Python/JSON-файлов совпали с исходным деревом.

исходники, окружение, эпизоды и артефакты. Старые свидетельства не перепривязывались
к новым исходникам. Файлы прогона: `artifacts/adaptive-agent-campaign-20261116`.
