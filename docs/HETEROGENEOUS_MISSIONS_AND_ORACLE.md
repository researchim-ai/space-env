# Неоднородные миссии и ограниченный точный эталон

Добавлены два отдельных инструмента: EO-миссии с различной стоимостью работ
и точный weighted-calendar эталон для готовых продуктов. Сертификат второго
инструмента не распространяется на полную EO/CPU/ISL-миссию.

## Неоднородная EO-миссия

```python
from space_env.tasks import TaskSession
from space_env.tasks.heterogeneous_missions import heterogeneous_mission

case = heterogeneous_mission({
    "profile": "bulk_tradeoff",
    "longitude_shift_deg": 12,
    "catalogue_seed": 0,
})
session = TaskSession(case["scenario"], case["task"])
```

В каждом рецепте два съёмочных аппарата, два шлюза и четыре заявки.
Допустимы профили `balanced` и `bulk_tradeoff`, с меридианными сдвигами
-12, 0 и 12 градусов. `catalogue_seed` меняет обозначения и их порядок,
но не является новым физическим seed.

У заявок различаются длительность съёмки, сырой и конечный объём данных,
CPU-work и приоритет. Например, bulk-продукт имеет сырой объём 3.2 Мбит,
конечный 2.8 Мбит и восемь секунд CPU-work; малые продукты — 0.3/0.15 Мбит
и одну секунду CPU-work. Native модель начисляет реальные для этого
инженерного профиля затраты памяти, времени и энергии.

Размеры не изменяются только в названиях: обновляются CustomerRequest,
outputs native job и бюджеты соответствующих команд. Бюджеты relay/downlink
равны ceil(output_bits/250000)+2 секунды. Это объявленный лимит управления,
не гарантия завершения передачи: фактическую скорость, ACK, outage и
допуск продолжает вычислять native runtime. В bulk-профиле Ground доступен
на [18,42) секунд. Отмена подтверждённой передачи остаётся отдельным действием.

У задачи явно задан `objective="sla"`: награда учитывает число доставок и
доставленный приоритет, со штрафом за отклонённые пакеты. Для проверенных
эпизодов дополнительно подтверждена формула суммарной native-награды:

```text
return = fulfilled_requests + fulfilled_priority - 0.1 * rejected_batches
```

Наблюдаемость остаётся ideal-local. Не добавлены новые сенсоры, скрытые
неожиданные заявки, полётная калибровка или произвольные команды FSW.
Исполнитель и один из двух gateway-путей выбираются в ходе исполнения;
готового расписания в рецепте нет. Число действий по-прежнему ограничено
каталогом operator-команд.

### Что означает новая геометрия

На начальной эпохе через packaged EOP строится поворот вокруг земной оси
в ITRS, затем он переводится в GCRS. Начальные r/v, станции, targets и области
покрытия согласованно преобразуются; исходная ориентация камер задаётся
по надиру, cloud-mask привязывается к новому SHA области.

Это новые объявленные начальные состояния и sites. Они происходят от одной
публичной синтетической formation-модели и разделяют lineage
`heterogeneous-formation/v1`. Не разделяйте их как независимые train/test
семейства. Это не OOD-доказательство и не независимая проверка преобразований
координат: генератор использует production EOP/frames. Солнечное освещение
и дальнейшая динамика оцениваются runtime для изменённых условий.

## Точный эталон готовых продуктов

```python
from space_env.reference.priority_calendar import solve_priority_calendar

result = solve_priority_calendar(reference_downlink_spec, max_states=65536)
assert result["optimality_proven_in_scope"]
```

Цель — максимум суммы приоритетов продуктов, доставленных вовремя.
Это отличается от прежнего календарного эталона максимума битов.
Динамическое программирование хранит раннее достижимое окончание для каждого
подмножества завершённых продуктов. Для одного подмножества раннее окончание
доминирует позднее: можно дождаться любой более поздней возможности.

Расчёт времён ведётся как Fraction над предоставленными календарными float.
Сертификат ограничен следующими условиями:

- одна станция и одна антенна;
- максимум 16 готовых продуктов, горизонт максимум 3600 секунд;
- продукт передаётся целиком, без прерывания;
- статические окна видимости/доступности и постоянные скорости аппаратов;
- нет CPU-зависимостей, ограничений квоты передачи, питания, солнечной
  генерации, тепла, радиосети или DTN.

Неподдерживаемые конфигурации и исчерпание max_states отвергаются, сертификат
в этих случаях не создаётся. После выбора расписания независимая от DP
native resource-модель исполняет его. Проверяются доставленные продукты,
биты и сумма приоритетов. Геометрия/окна общие с native access, поэтому
это проверка scheduling-логики, не независимая орбитальная истина.
Сравниваемая жадная политика знает те же календари и тоже nonpreemptive.

### Полученные контрпримеры

Шесть фиксированных случаев: три шаблона × два меридианных варианта.
Это специально спроектированные regression-примеры, не шесть независимых
индустриальных миссий.

- `bulk_vs_pair`: жадный выбор получает 11, доказанный optimum — 12.
- `release_and_gap`: жадный выбор получает 17, optimum — 24.
- `infeasible`: оба получают 0; отрицательные случаи остаются в наборе.

Вторая геометрия воспроизводит те же значения. Оптимумы также проверены
в тестах отдельным полным перебором дискретных стартов на восьми небольших
задачах. Тестовый перебор не использует production `_slot` или DP-переходы.

## Воспроизводимый study

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m space_env.validation.tradeoff_study --output artifacts/my-tradeoff
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m space_env.validation.tradeoff_study --audit artifacts/my-tradeoff
python -m pytest -q tests/test_priority_calendar.py tests/test_heterogeneous_missions.py tests/test_tradeoff_study.py
```

Фиксируются исходники, manifest до измерений и вся матрица попыток. EO исполняется
в двух свежих spawn-процессах. Обычные исключения сохраняются как error-строки;
ошибки не превращаются в нулевую доказанную достижимость. Если аварийно
завершится сам процесс, study может остаться незавершённым: исходный manifest
и progress сохраняются, готовый проверенный отчёт при этом не заявляется.
Криптографические SHA удостоверяют целостность байтов, не внешнюю аттестацию.

Текущий study проверяет шесть календарей и четыре EO-попытки: два заранее
выбранных представителя (`balanced/-12`, `bulk_tradeoff/+12`) × `priority`
и `route_aware_rolling`. Все шесть объявленных EO-конфигураций проходят
конструкторные тесты, но полное исполнение всех шести не заявляется.

- Прошли 117 целевых тестов; Ruff и `git diff --check` без ошибок.
- Собран wheel, побайтно проверены 354 Python/JSON-файла. Из отдельного cwd
  через распакованный wheel решён календарный пример 12 против 11 и
  выполнены два EO-шага с cold replay. Это smoke, не полная установленная миссия.
  Использованы имеющиеся зависимости и закешированные build-пакеты,
  чистая установка всего окружения с нуля не проверялась.

они пока не являются трудным разделяющим тестом. Разрыв доказан только
в ограниченном weighted-calendar подклассе. LLM и обучение на новом наборе
не измерялись. Вывод о превосходстве симулятора над внешними системами
не делается; старые source-bound receipts остаются историческими.
