# План завершения Space Env

## Принятый порядок работы

Разрабатываем локальную библиотеку и симулятор, который пользователь может
установить, запустить и самостоятельно испытать. CI, GitHub Actions, удалённые
матрицы окружений и обязательные приёмочные кампании не нужны и не являются
условием выпуска. Для изменений достаточно локальных тестов; примеры пользователь
запускает по своему выбору. [Команды запуска](LOCAL_RUN.md).

## 1. Простой запуск

Поддерживать понятную установку, запуск Studio/пульта оператора одной командой,
готовые сценарии и объяснение настроек. Ошибки конфигурации должны показывать,
какое поле нужно исправить. Пользователь должен получить работающую миссию без
изучения внутренней архитектуры и подготовки специальных отчётов.

## 2. Основная функциональность миссий

Доводить группировки спутников, планирование на заданный горизонт, поступление
новых заявок, ограничения памяти/энергии/связи, работу наземных станций и отказы.
Сохранять совместимость API, журналов, checkpoint и продолжения миссии.
Исправления сопровождать подходящими локальными тестами.

## 3. Среды и данные для AI

Обеспечить удобные Gym/MARL interfaces и генерацию RL/SFT с понятными примерами.
Сохранять явные train/development/test splits и защиту от попадания test в train.
Статус экспертности демонстраций должен соответствовать их фактическому качеству.
Benchmark и измерения производительности остаются инструментами для желающих,
а не обязательной процедурой перед обычным запуском или выпуском.

## 4. Физика и масштабирование

Улучшать реализацию моделей и производительность по реальным задачам и найденным
дефектам. Объяснять единицы, системы координат, допущения и поддерживаемые пределы.
Покрывать численные инварианты и ограничения тестами. Различать синтетические
данные, открытые спецификации и измерения; не называть surrogate цифровым
двойником конкретного аппарата без соответствующих данных.

## 5. Документация и выпуск

Достаточны понятная инструкция установки/запуска, локальные тесты для изменений,
рабочие примеры и описание известных ограничений. Дополнительные benchmark,
audits, архивы и воспроизводимые эксперименты запускаются только по необходимости
или желанию пользователя. Создавать отдельную CI-инфраструктуру не требуется.

Коммит, push, tag и публикацию выполняет пользователь.

## Уже сделано

D2h-B2b-B добавил native incoming requests и явный rebind каталогов. B12 добавил
фиксированные benchmark-сценарии, baselines с общим forecast, measurements и
безопасный exporter явных ML splits. Их исторические результаты сохранены в
`docs/acceptance/`; упоминания прежней CI-политики в этих записях не являются
текущими требованиями разработки.
