# Задержанная телеметрия маршрутов

Маршрутная телеметрия кампании может приходить с детерминированной задержкой.
Агент получает фактически измеренный снимок прошлого состояния, его возраст
и время доставки. Политика умеет ограничивать допустимый возраст данных.
Исходные аппараты, продукты, очередь DTN, энергетика и сроки продолжают
исполняться на одном native runtime.

## Настройка

```python
from space_env.tasks.routing_campaign import routing_campaign

case = routing_campaign({
    "horizon_sec": 240,
    "release_sec": 60,
    "fault_profile": "mid_transfer",
    "route_delay_sec": 1,
    "max_route_age_sec": 2,
})
```

Для произвольной `AgentCampaignSession` настройка канала находится в
`configuration["route_telemetry"] = {"delay_sec": 1}`. Порог возраста задаётся
в публичном контракте политики: `adaptive_routing=True`, `max_route_age_sec=2`.
Задержка допускается от 0 до 3600 секунд, порог — в том же диапазоне.
Отсутствующая настройка сохраняет прежнюю мгновенную проекцию маршрутов.
Явно заданный канал с нулевой задержкой публикует текущий снимок с метаданными.

## Семантика времени

Снимки формируются при создании сессии и после каждого успешного вызова
native `step`, включая переходы с отрицательной обратной связью команд.
Чтение `observe()` ничего не измеряет и не изменяет очередь.
Это выборка на границах решений, а не независимый периодический датчик.
При длинном шаге промежуточные состояния не интерполируются и не восстанавливаются.

Для снимка с временем измерения `t_m` и задержкой `d` время доставки равно
`t_d = t_m + d`. В момент `t` публикуется последний снимок, для которого
`t_d <= t` с численным допуском 1e-9 секунды. Возраст — `max(0, t - t_m)`.
До первой доставки список `relay_routes` пуст.

У строк маршрутов сохраняются `measured_at` и `link_sample_sec`, добавляются
`age_sec` и `delivered_at`. Метаданные `route_telemetry` содержат задержку,
возраст и ближайшее время доставки уже сформированного снимка.
Это не прогноз будущего состояния сети. Поступление снимков не зависит
от исправности моделируемого радио: транспорт канала здесь идеальный,
с заданной постоянной задержкой.

Снимки формируются только для уже объявленных заявок. При публикации
дополнительно проверяется видимость идентификаторов в текущем каталоге.
Записи будущих заявок не появляются из-за чтения истории.
В очереди остаётся последний доставленный снимок и ещё не доставленные;
число измерений дополнительно ограничено контрактом сессии в 512 решений.

## Как принимает решения базовая политика

Для relay-команд требуется доступный маршрут и возраст не больше
`max_route_age_sec` с допуском 1e-9 секунды. Отсутствующие сведения
не трактуются как разрешение передачи. Порог не гарантирует корректности
маршрута: отказ мог произойти после измерения.

Если ещё есть незавершённые заявки с relay-командами, адаптивное ожидание
ограничивается ближайшей известной доставкой снимка. После выполнения
заявок канал не заставляет контроллер бесконечно опрашивать телеметрию.
При пороге меньше транспортной задержки все снимки могут быть устаревшими;
это допустимая отрицательная постановка, а не повод обходить ограничение.

## Важная граница модели

Задерживается **только `relay_routes`**. Основной граф, каталог и его маски,
заявки, результаты команд и журнал уже произошедших событий центрального
пульта остаются текущими. Через них агент может получать дополнительные
сведения об отказах и доступности. Этот режим не следует использовать как
доказательство полного отсутствия текущей информации, распределённого
бортового управления или моделирования всей линии командования.

Введённый канал позволяет отдельно измерять влияние возраста маршрутных
снимков, проверять обработку устаревших данных и генерировать tool-траектории.
Дальнейшее развитие: согласованные задержки всех каналов наблюдения,
задержки подтверждений команд, потери/переупорядочение пакетов и независимые
периоды датчиков. Физическая калибровка этим обновлением не расширяется.

## Проверки и воспроизведение

```bash
python -m pytest -q tests/test_route_telemetry.py
python -m examples.modeling.route_telemetry_study --output artifacts/my-route-telemetry
```

Проверяются причинность доставки, чистота чтения и отсутствие общих изменяемых
ссылок, очистка очереди, порог возраста и границы ожидания, восстановление
очереди через checkpoint, успешная миссия с задержкой и отказ от передачи
при заведомо устаревшей телеметрии. Нативные балансы битов проверяются отдельно.

Исследование сохраняет конфигурации оценщика, публичные эпизоды,
сетевые отчёты, RL JSONL всех профилей и SFT JSONL успешного delayed-mid.
Экспорт повторно исполняет каждый эпизод. Проверка публичной политики
восстанавливает каждое действие из полученных наблюдений.
Политика `scripted_public`; эти данные не подтверждают обучение или качество LLM.

В сравнении фиксированы время внешнего отказа и остальные параметры.
Имя `mid_transfer` описывает обрыв в базовом профиле без задержки.
Задержка изменяет моменты решений, поэтому тот же отказ может произойти
ещё до начала передачи в другом прогоне. Более ранний ground ACK при
задержке на одном сценарии не доказывает полезность задержки в общем случае.
