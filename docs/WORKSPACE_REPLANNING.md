# Перепланирование оставшейся работы

Рабочая страница, API и `MissionWorkspace.replan()` пересчитывают расписание
ещё не начатых заявок из текущего физического состояния. Операция создаёт
**отдельную ветку продолжения**. Исходная сессия, её реальные наблюдения,
команды, продукты, состояние и capabilities остаются без изменений.

Это явная команда центрального оператора. Автоматического реагирования на
отказы, новых заявок, изменения физики и прерывания текущих операций здесь нет.

## В интерфейсе

1. Создайте миссию. Выполните ручное ожидание или дойдите до завершения
   всех начатых цепочек «наведение → съёмка → обработка → передача».
2. В карточке результатов укажите причину и нажмите
   «Перепланировать оставшееся». Подсказка объясняет, допустима ли граница.
3. После проверки откроется новая ветка в том же модельном времени.
   Нажмите «Прогон планировщика», чтобы продолжить исполнение.
4. «Переключить ветку» переключает последнюю пару исходная/новая ветка.
   Истории независимы. Перед закрытием страницы сохраните отдельный файл
   доступа для каждой нужной ветки через существующую кнопку пульта.

Временное переключение хранится в памяти страницы. После перезагрузки
подключайтесь сохранённым файлом доступа. Файлы доступа содержат секреты,
их нельзя включать в обучающие корпуса. Общий лимит пульта — восемь сессий;
ненужные ветки закрываются обычным механизмом.

## SDK

```python
from space_env.workspace import MissionWorkspace

source = MissionWorkspace()
# Явное ручное ожидание: исходное расписание теперь устарело.
source.operator.step(source.connection["tokens"]["operator"], {
    "action_ids": ["wait"],
    "advance_sec": 5.0,
    "expected_revision": 0,
    "control_epoch": 0,
    "idempotency_key": "manual-wait",
})
continuation = source.replan(
    "Пересчитать после ручного ожидания",
    idempotency_key="after-wait/1",
)
state = continuation.run()
print(state["workspace"]["fulfilled"])
continuation.export("/tmp/continued-mission.zip")
# source по-прежнему находится на пятой секунде.
```

`planner={"max_search_nodes": 100000, "max_orders": 8}` позволяет явно
ограничить поиск при пересчёте. Это параметры поиска, а не обещание времени ответа.
Метод возвращает новый `MissionWorkspace`, а не меняет объект `source`.
Физические назначения остаются фиксированными, включая выбранные ранее
автоназначением. Пересчитываются порядок, времена и наведение оставшихся цепочек.

## Контракт и проверка физики

- Нужна начатая, не завершённая миссия из редактора конфигурации.
- Текущее время должно лежать на исходной сетке решений.
- Любая заявка, для которой уже отправляли команду, должна быть доставлена.
  Это консервативная граница: даже отказанная попытка начать незавершённую
  цепочку не допускает пересчёт в этом профиле. Частичные продукты не теряются:
  операция отклоняется и исходная сессия остаётся доступна для ручного завершения.
- Используется текущее состояние батарей, оставшаяся TX-квота, будущие окна
  и дедлайны. Новые ресурсы и дополнительное время не появляются.
- Прогноз строится в копии checkpoint с явно разрешённым forecast-доступом.
  Права исходного runtime и наблюдения агента не расширяются.
- Завершённые заявки исключаются из будущих команд; ранее исполненные
  шаблоны команд сохраняются. Префикс повторно исполняется с новым каталогом.
- Перед созданием ветки сравниваются результаты команд и SHA-256 полного
  native backend report. Несовпадение блокирует создание.
- Установка ветки использует стандартный restore: новые capabilities,
  provenance импортированного префикса, control epoch и durable-сохранение.

В новой ветке исторические наблюдения **реконструируются** при replay под новым
каталогом будущих команд. Побайтное совпадение этих наблюдений с оригиналом не
обещается. Фактическая исходная история сохраняется в исходной сессии; физическое
состояние и результаты исполненных команд проверяются отдельно. Это проверенный
replay-префикс, а не продолжение из сохранённой оперативной памяти.

`workspace.replan` содержит причину, ID исходной сессии, SHA-256 исходного
checkpoint/плана и физического состояния, время, revision и завершённые заявки.
Эти сведения доступны центральному оператору. Они не добавляются в наблюдения
агента. Ветка сохраняет исходную геометрическую lineage: это не новый независимый
holdout. При сборке корпуса не складывайте повторяющиеся префиксы как независимые
эпизоды и не распределяйте ветки одной миссии между train и test.

## API, повтор запроса и ошибки

`POST /api/operator/sessions/{id}/replan`, Bearer capability центрального
оператора, JSON:

```json
{
  "expected_revision": 1,
  "control_epoch": 0,
  "idempotency_key": "after-wait/1",
  "reason": "Пересчитать после ручного ожидания"
}
```

Ответ соответствует созданию обычной operator-сессии: `session_id`, `tokens`,
`state`. Старые credentials управляют только исходной сессией.

Повтор с тем же ключом и телом возвращает существующую активную ветку с её
текущим состоянием, не создавая ещё одну. Изменённое тело с тем же ключом — 409.
После рестарта plaintext capabilities не извлекаются из хранилища: повтор даёт
`replan_already_created` с ID сохранённой ветки. Используйте сохранённый файл
доступа либо существующий механизм локального восстановления владельцем ОС.
После закрытия ветки идемпотентный receipt больше не удерживается; ключ не следует
повторно использовать для новых намерений.

Права viewer, agent, admin и отдельного аппарата не дают права перепланирования.
При передаче управления агенту сначала верните его оператору. Несовпадение revision
или control epoch отклоняет устаревший запрос. Поиск делит общий локальный semaphore
с первоначальным планированием. Перепланирование не увеличивает revision исходной
сессии и не продвигает её время.

Локальные тесты:

```bash
python -m pytest tests/test_workspace_replan.py -q
```

Проверяются продолжение после ожидания с native доставкой, сохранение завершённых
цепочек, повторное ветвление, роли, stale-запросы, бюджет поиска, запись с ошибкой,
SQLite restore, HTTP-контракт и отсутствие плановых данных в канале агента.

Результат локального объединённого набора после изменения: **131 passed**,
один существующий тест реального loopback-сервера исключён из sandbox-запуска.
Новый маршрут проверен через `handle_post`; native продолжение, экспорт и replay
проверяются обычными тестами. CI и внешние сервисы для этого не требуются.

Ручная проверка веб-интерфейса: исходный план отклонён ожиданием на 5 с,
создана ветка продолжения, доставлено 2/2 заявки к 120 с. Переключение
подтвердило, что исходная ветка осталась на 5 с с 0/2 доставок; повторное
переключение вернуло завершённую ветку. Ошибок консоли не обнаружено.
