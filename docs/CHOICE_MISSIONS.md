# Миссии с выбором исполнителя и пути доставки

Этот набор расширяет прежнюю задачу исполнения заранее выбранной цепочки.
Он не содержит опорного расписания или выбранного владельца заявки.

Измеренные исходы: [CHOICE_MISSIONS_RESULTS.md](CHOICE_MISSIONS_RESULTS.md).

## Моделируемая задача

Базовая конфигурация: три аппарата со средствами съёмки и два шлюзовых
спутника, шесть заявок в двух волнах, горизонт 60 секунд, решения через
две секунды. Это компактная синтетическая близкая группировка с EO,
оценкой геометрического качества/покрытия, обработкой, памятью, энергетикой,
DTN custody и наземным подтверждением. Качество съёмки — инженерная модель,
не генерация реалистичных спутниковых изображений.

Для каждой заявки агент может:

- выбрать любой из трёх допустимых съёмочных аппаратов;
- инициировать платную переориентацию на target и съёмку;
- обработать результат на аппарате, который его получил;
- выбрать один из двух шлюзов для передачи продукта;
- инициировать наземную доставку со шлюза и дождаться подтверждения;
- отменить собственную операцию, если продолжение нецелесообразно.

Выбор реальный: native lifecycle связывает заявку с фактическим исполнителем,
память/CPU/радио оплачиваются, продукт передаётся через native custody.
Одна заявка не превращается в независимые копии для каждого аппарата.
Геометрия исходно построена по явно синтетическому правилу пересечения
начальной оси камеры с Землёй; достоверность этого профиля не равна
калибровке реальных датчиков или всей глобальной группировки.

Каталог содержит 107 действий. Он полный для разрешённого профиля:
альтернативы не отфильтрованы по заранее найденному расписанию. Профиль
разрешает маршруты camera → gateway → Ground, не произвольный граф
многошаговых путей, команды raw flight software или орбитальные манёвры.

## Четыре условия

- `open`: общие ресурсы и различные приоритеты/дедлайны, без outage.
- `memory`: память съёмочного аппарата ограничена 1.6 Мбит; конкурируют
  исходный продукт, результат и рабочее место CPU.
- `ground_window`: одна наземная антенна доступна только на интервале
  [18, 30) секунд; все заявки нельзя считать гарантированно выполнимыми.
- `link_blackout`: с восьмой секунды camera → первый шлюз недоступен;
  второй шлюз остаётся альтернативой.

Волны заявок освобождаются в native lifecycle. В этой версии события
предопределены сценарием, а будущий каталог статичен: агент может видеть
идентификаторы ещё недоступных заявок. Это **не неожиданные заявки**, не
скрытая слепая выборка отказов и не проверка генерализации.

Наблюдения — текущая идеальная локальная телеметрия. Навигационные сенсоры,
задержка этой телеметрии и оценивание относительного движения этим набором
не добавляются. Их поддержка в других профилях не означает совместимость
со всей цепочкой EO/CPU/DTN.

## Устранение подсказок

Идентификаторы заявок, продуктов, jobs, targets, областей и действий
псевдонимизированы. Они не кодируют номер фазы или исходного исполнителя.
Порядок каталога задан хешами, а не порядком «снять → обработать → передать».

Видимая семантика команд и зависимости сущностей сохраняются: агент должен
понимать, что делает команда. Маски индивидуальной допустимости также
сохраняются. Они помогают исключать явно невозможное, но не гарантируют
совместной допустимости пакета или будущей успешности операции.

Каждое условие имеет две перестановки имён (`catalogue_seed=0,19`). Это
варианты одной физики, а не независимые орбиты или seed-выборка отказов.
Они разделяют lineage и не должны попадать по разные стороны train/test.

## Исправление совместного планирования

Расширение eligible_actors выявило недостаток BaselinePolicy: действия
разных аппаратов могли не конфликтовать по ресурсам аппаратов, но
конкурировать за одну глобальную заявку. Аналогичная ситуация возможна
для одной обработки на нескольких аппаратах.

Выбор совместного пакета теперь учитывает независимые namespaces
request/job/product. Две imaging-команды на одну заявку или две transform
на один job не выбираются одновременно. Независимые заявки разных
аппаратов продолжают исполняться параллельно. Проверка native admission
остаётся окончательной; эвристика не становится oracle допустимости.

## API и запуск

```python
from space_env.tasks import TaskSession
from space_env.tasks.choice_missions import choice_mission

case = choice_mission({"family": "memory", "catalogue_seed": 0})
session = TaskSession(case["scenario"], case["task"])
observation = session.observe("camera-00")
```

Те же scenario/task можно передать MissionTaskEnv или LLMEpisode. В фиксированном
Ollama-протоколе cadence этого набора равна **2.0 секунды**, а не 5.0.
Сам факт совместимости не является результатом прогона LLM на этом наборе.

```bash
python -m space_env.validation.choice_benchmark --quick --workers 2 --output artifacts/choice-quick
python -m space_env.validation.choice_benchmark --workers 4 --output artifacts/choice-full
python -m space_env.validation.choice_benchmark --audit artifacts/choice-full
python -m pytest -q tests/test_choice_missions.py tests/test_planning.py
```

`quick`: четыре условия × четыре политики = 16 попыток.
Полный набор: восемь рецептов × четыре политики = 32 попытки.

Каждая попытка выполняется в новом процессе, максимум 180 секунд;
численные потоки ограничены единицей. Число одновременно работающих процессов
фиксируется в manifest. Тайминги при конкурентном запуске не являются
измерением изолированной скорости backend.

Политики `wait`, `priority`, `earliest_deadline`, `route_aware_rolling` используют
существующий публичный PlanningInput. Последняя выполняет ограниченный
поиск текущего пакета, а не глобальную оптимизацию всей миссии. У каждой
максимум 64 кандидата и 1024 узла поиска; сокращение списка и исчерпание
поиска сохраняются в trace.

В фиксированном V1 базовая награда TaskSpec остаётся `delivery`: число
выполненных заявок со штрафом за отклонённые команды. Бенчмарк дополнительно
измеряет доставленный приоритет; это отдельная бизнес-метрика, не доказательство
оптимальности накопленной награды. Для RL с приоритетами нужно явно выбрать
`task["objective"] = "sla"` до создания новой среды и сохранить новый рецепт.
Изменять objective у записанного эпизода или считать старый rollout результатом
такого обучения нельзя.

PlanningInput предоставляет центральному планировщику текущую объединённую
проекцию, статические resource claims и текущее состояние станции. Это не
сопоставление с акторным LLM-интерфейсом один к одному: LLM на данном наборе
ещё не измерялась. Никаких будущих forecast, native admission rollouts или
знания сценария за границей этого публичного входа политика не получает.

## Доказательства и ограничения

Сохраняются исходный manifest, исходники, compact checkpoints, ход выполнения,
все ошибки и таймауты. Trainer-only свидетельства показывают фактических
исполнителей, native fulfilled priority, затраты энергии и коды отклонений.
Они не передаются политике.

Аудит запускает холодное воспроизведение в отдельных процессах, сверяет
решения политики, native transitions, исходный рецепт и итоговые метрики.
Ошибка не исчезает из матрицы. Для неё агрегат отражает нижнюю наблюдаемую
оценку доставки, а не доказательство нулевой достижимой ценности.
`best_observed_priority` — лучший измеренный результат, **не оптимум**.
Успешный аудит целостности отчёта с ошибками не означает успешных миссий.

Наличие альтернатив и ограничений увеличивает пространство решений.
Это ещё не доказательство того, что простые эвристики систематически
проигрывают: такой вывод допустим только по опубликованным результатам,
а не по числу аппаратов, actions или шагов.

Следующие необходимые расширения: новые независимые геометрии и разделение
по происхождению; задачи с различной стоимостью/объёмом заявок и доказанным
разрывом между жадным и более сильным решением; реально неожиданная смена
заявок/отказов; EO-совместимая неполная наблюдаемость; реальные LLM-прогоны
и обучение с отдельными train/held-out семействами.

Старые source-bound acceptance receipts остаются историческими. Изменение
планировщика требует нового исполнения; их source hashes не переписываются.
