# Внешние события в непрерывной миссии

## Что добавлено

`TaskSpec.environment_events` — расписание внешних воздействий, заданное автором
сценария. Его обрабатывает сама транзакция `TaskSession`. Многоэтапный
`AgentCampaignSession` наследует эту возможность, продолжая использовать один
физический runtime для наблюдений, CPU, радиосвязи, орбит и ресурсов.

Это независимый от действий агента механизм: отказ нельзя отменить отклонённой
командой, а заявку нельзя создать через JSON-инструмент управления кампанией.
Планировщик и агент должны реагировать на изменившееся состояние; механизм
событий сам не решает задачу оптимального перепланирования.

```json
{
  "environment_events": [
    {
      "id": "cpu-loss",
      "at_sec": 4.75,
      "type": "spacecraft_fault",
      "payload": {"actor": "a", "subsystem": "cpu"}
    },
    {
      "id": "cpu-clear",
      "at_sec": 5.5,
      "type": "spacecraft_fault_cleared",
      "payload": {"actor": "a", "subsystem": "cpu"}
    }
  ]
}
```

## Поддерживаемые воздействия

- `request_added`: полноценный `CustomerRequest` и список `TransformationJob`.
  Допускается пустой список jobs для непосредственно доставляемого raw-продукта.
- `request_cancelled`, `request_priority_changed`, `request_deadline_changed`.
- `spacecraft_fault`, `spacecraft_fault_cleared`: bus, ADCS, payload, CPU, radio,
  propulsion в пределах возможностей выбранного coupled-bus профиля.
- `spacecraft_safe_mode`, `spacecraft_recover`.
- `station_outage_added`, `station_recovered`.

Все поля проверяются строгими моделями. Неизвестные подсистемы, лишние поля,
нечисловые/бесконечные времена, backdated arrival/outage и некорректные интервалы
отклоняются. События должны предшествовать горизонту runtime; outage не может
выходить за горизонт. До исполнения проверяются известные акторы, станции,
capabilities и граф будущих заявок/преобразований на отдельном временном runtime.
**В живой runtime эти будущие заявки и продукты не загружаются.**

## Время и атомарность

1. События при `t=0` применяются до первого публичного наблюдения.
2. Запрошенный интервал управления обрезается на ближайшем событии либо ранее
   достигнутой границе цели/горизонта. Следующий интервал выбирает агент.
3. Сначала native runtime исполняет команды до границы; затем применяются события
   на этой границе; затем оцениваются цели и строится следующее наблюдение.
4. Совпадающие по времени события выполняются в порядке объявления, отдельно.
   Например, второе снятие уже устранённого отказа будет отклонено, не отменяя первое.
5. State-dependent отказ применения регистрируется один раз как `native_rejected`.
   Текст исключения backend не передаётся агенту. Проверки recovery SOC, теплового
   гистерезиса, текущих faults и терминальных состояний заявок остаются native.
6. Отклонённые управляющие действия откатываются; физическое время и наступившие
   внешние события продолжаются. Ошибочный формат обращения не двигает время.

Максимум 256 внешних событий. ID уникальны, времена не убывают; различные времена
должны отличаться более чем на 1 нс. Сопоставление границ использует допуск 1 нс.
События после терминального завершения кампании не проигрываются: если нужен
продолжительный контроль, это следует явно задать последующей фазой и её целью.
Сенсорные TaskSpec пока явно отклоняют environment_events: поддержка изменения
среды в estimator-контуре требует отдельной проверки.

## Видимость и replay

`TaskSession.environment_status()` возвращает только уже попытанные события:
ID, тип, фактическое время, accepted и код. Будущих времён и payload в нём нет.
Список добавляется в публичное наблюдение `AgentCampaignSession`.

В кампании шаблоны действий с `request_ref` скрыты до появления соответствующей
заявки в текущей проекции. Попытка угадать скрытый action ID не исполняет его.
Автор должен связывать все шаблоны будущей заявки с её `request_ref`: в демонстрации
это imaging, transform и downlink. Обычный TaskSession сохраняет контракт своего
статического каталога; специальная фильтрация относится к agent-campaign мосту.

Будущую объявленную заявку можно включить в DeliveryGoal. До её поступления она
считается невыполненной. Отклонённое поступление не удаляет её из знаменателя и
не превращает невыполнимую цель в успех. Цели и полное расписание остаются
привилегированными данными checkpoint; публичную инструкцию задаёт `task_text`.

События входят в авторскую постановку задачи и воспроизводятся при replay;
переходы связывают результаты их применения с исходниками и зависимостями.
Проверены оба формата native checkpoint и восстановление agent-campaign
между поступлением заявки и следующим изменением, а также внутри CPU-прерывания.

## Демонстрации и измерения

```bash
python -m examples.modeling.dynamic_agent_campaign --profile arrival --output artifacts/my-dynamic-arrival
python -m examples.modeling.dynamic_agent_campaign --profile recovery --output artifacts/my-dynamic-recovery
python -m pytest -q tests/test_task_environment.py
```

Каталог вывода должен быть новым. Сохраняются replay-verified эпизоды, RL для
обоих вариантов и SFT успешной безошибочной сценарной последовательности.
Ожидание используется как отрицательный контроль. Происхождение политики явно
`scripted_privileged`: это проверка интеграции, не результат LLM и не обучение.

`arrival` добавляет customer-a в `t=2` и меняет приоритет в `t=2.5`.
`recovery` дополнительно прерывает CPU и станцию в `t=4.75`, снимает CPU-отказ в
`t=5.5`, восстанавливает станцию в `t=6`. Повторная CPU-команда продолжает остаток
работы. Native продукты, навигационное/физическое состояние и накопленные расходы
между событиями и фазами не пересоздаются.

У исходного EO-примера `require_healthy` запрещает любой исторический fault,
даже устранённый. Эта семантика не изменена. В recovery-fixture исторические
отказы явно разрешены (`require_healthy=false`); отдельно проверяется конечная
исправность через `metrics.current_bus_health`. Это не новый универсальный
предикат восстановления и не молчаливое ослабление старых миссий.

## Что ещё не доказано

Примеры короткие, синтетические, централизованные. Внешнее снятие отказа —
заданный экспериментатором stimulus, а не обученный FDIR и не модель ремонта.
Здесь нет измерений многосуточной точности, автоматического оптимального
перепланировщика, реального управления аппаратами, независимой калибровки или
доказательства превосходства над другими симуляторами.

Следующий физический блок: многоволновая EO→CPU→ISL→ground кампания на часы/сутки,
измерения скорости, сходимости, сохранности ресурсов и независимые эталоны.
После него — публичная политика перепланирования и LLM-бенчмарк на неизвестных
постановках, а не только авторские траектории действий.
