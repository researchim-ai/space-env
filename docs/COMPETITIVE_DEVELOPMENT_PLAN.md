а не недостаточное число env ID. Ближайший инженерный пакет уже подробно описан

## 2. С кем и по чему сравниваемся

Ниже — официально документированные возможности, а не собственные измерения
конкурентов. Отсутствие функции на просмотренной странице не доказывает её отсутствия
в продукте. Версии страниц и коммерческие комплектации могут различаться.

### Basilisk и BSK-RL: прямой ориентир для обучения агентов

[Basilisk](https://avslab.github.io/basilisk/) предоставляет модульную базу
моделирования аппаратов. [BSK-RL](https://avslab.github.io/bsk_rl/index.html)
строит поверх неё среды spacecraft tasking.
[API BSK-RL](https://avslab.github.io/bsk_rl/api_reference/index.html) документирует
Gymnasium, PettingZoo ConstellationTasking, конфигурируемые группировки, наблюдения,
действия и межспутниковый обмен. Поэтому «у нас есть Python, RL и несколько спутников»
не является уникальным преимуществом.

Наш необходимый ответ: совместимые агентные интерфейсы, общий контракт миссии,
измеренная физическая достоверность, устойчивый benchmark и проверяемые данные.
Возможное преимущество — удобство всей цепочки сценарий→агент→доказанный результат,
которое ещё предстоит измерить, а не объявить.

### STK: ориентир анализа миссий и пользовательского опыта

[Официальное описание STK](https://ansys.synopsys.com/products/missions/ansys-stk)
включает моделирование систем в контексте миссии, связь, покрытие, сенсоры,
API, отчёты и визуализацию. Это серьёзный ориентир широты и удобства инженерной работы.
Не утверждаем, что у STK нет средств интеграции с ML.

Наш ответ: единая живая миссия с timeline, ground track, 3D, заявками, ресурсами,
командами и объяснением результата. Сильный UX измеряется временем выполнения
операторской задачи и числом ошибок, не числом красивых панелей.

### GMAT и FreeFlyer: ориентиры инженерных сценариев

[NASA GMAT](https://software.nasa.gov/software/GSC-19640-1) покрывает проектирование,
оптимизацию и навигацию миссий, имеет GUI и программные интерфейсы.
[Примеры FreeFlyer](https://ai-solutions.com/_help_Files/demos_smp.htm) показывают
покрытие группировки, связь, обработку CDM и сценарии других режимов полёта.
Это не однотипные RL-библиотеки, поэтому общий рейтинг «симулятор лучше» некорректен.

Наш ответ: использовать независимые инструменты как эталоны там, где модели
сопоставимы. Строить интеграции, а не переписывать весь космический стек.
Orekit также рассматривать как reference/backend; часть его страниц при текущей
проверке была недоступна, поэтому отдельный обзор актуальных возможностей не заявлен.

## 3. Где хотим выигрывать

Продуктовая гипотеза: наиболее удобная и проверяемая среда разработки агентов,
управляющих операциями спутниковых группировок на горизонтах часов и суток.
Первый профиль — ДЗЗ и доставка данных; архитектура расширяется другими профилями.
Клиентский спрос и превосходство пока не подтверждены интервью или испытаниями.

Пять направлений преимущества:

1. **Воспроизводимое исполнение.** Любое решение объясняется командой, событием,
   ресурсным конфликтом и outcome. Ветвление и восстановление сохраняют результат.
2. **Обучение и оценка вместе.** RL, MARL, LLM tool-use/SFT и baseline planners
   действуют в одном мире и оцениваются одним независимым evaluator.
3. **Тяжёлые операционные задачи.** Сроки, ограниченные станции/память/энергия,
   задержки связи, отказы, неоднородный флот и срочное перепланирование совместно.
4. **Контролируемая достоверность.** Fast и reference профили с проверенной областью
   применимости; политика проходит проверку переноса, а не только свой simulator.
5. **Быстрый инженерный цикл.** Из YAML или SDK до первого воспроизводимого
   эксперимента и разбора ошибки в Studio без ручного склеивания скриптов.

Ни одно направление пока не называется уникальным без сравнительного эксперимента.

## 4. Последовательность реализации

### R0 — закрыть ошибки основания, обязательный блокирующий этап

Выполнить A–D предыдущего плана: полный snapshot/forecast, persistent command/resource
books, causality relay, acquisition-aware scoring, строгая схема/provenance.
Регрессионные тесты строить из текущих диагностических примеров.

Добавить проверки исключений, повторов, многократных forecast, перестановки actors,
продолжающегося радио, конфликтов внутри шага и разных dt. Провести fault injection
самого executor: частичная ошибка не оставляет половину мира в будущем.

Выход: все P0 закрыты тестами; replay совпадает по состоянию/событиям/KPI;
invalid input отклоняется до мутации. Подробный checklist — gates A–D.

### R1 — единая платформа миссии и обучения

Выполнить E/G/H: конфигурируемые флот/заявки, публичный SDK, адресные действия,
наблюдения Dict с масками, живые независимые sessions, поставка wheel со Studio.
Сначала centralized Gym; затем PettingZoo Parallel adapter к тому же executor.
Примерные новые модули, окончательное размещение выбрать после проверки кода:
`mission/executor.py`, `mission/session.py`, `envs/mission_env.py`, `envs/parallel_env.py`.

Agent policy не получает truth или ответ teacher. Для MARL определить частичную
информацию, доступность действий, обмен, задержки, появление/выбытие агентов.
Тестировать equivalence centralized/parallel на одинаковых совместных действиях.

Выход: один сценарий с 1/4/16 аппаратами проходит SDK/Gym/API; PettingZoo API tests
для распределённого режима; manual/autopilot пользуются общей книгой команд.
Новая среда получает новую версию, старые ID сохраняются через adapters.

### R2 — проверенная физика и модели аппаратов

Добавить registry моделей с units/frame, параметрами, источниками, uncertainty,
ограничениями применимости и validation fixtures. Начать с различий optical/SAR/
relay/CubeSat; дополнительные реальные названия добавлять с данными и допущениями.

Исправить stage-time RK4, независимые frames/time проверки; расширить reference pack
для орбит, access/eclipse, slew, power/thermal, линков и манёвров. Для fidelity каждого
режима заранее определить tolerances и arc length; не подгонять их после результата.
TEME не смешивать с GCRF до проверенного преобразования. Pc не квалифицировать по
самосогласованности собственной формулы.

Backend interface: propagate, frames/time, access, provenance, capability limits.
Сначала адаптировать существующие integrations, optional backend делать действительно
опциональным. Не обещать идентичность всех моделей только из-за одинакового API.

Выход: offline validation report с ошибкой/допуском/источником по каждой заявленной
возможности. Обученная на fast модель отдельно проверяется в reference profile.

### R3 — benchmark и данные, основной актив продукта

Выполнить F и добавить suite registry с версией, hashes, split policy и reference
solutions. Полный run artifact сохраняет initial config/snapshot, команды, события,
полные receipts, final state и outcome; данные включают стоимость и failures.

Первый benchmark состоит из восьми семейств:

- EO acquisition/delivery: point/strip/polygon, revisit, sensor compatibility.
- Ground scheduling: несколько станций, число антенн, outages и competing passes.
- DTN relay: очереди, store-and-forward, TTL и connectivity changes.
- Resource operations: энергия/память/тепло при полезной работе.
- FDIR: шумная телеметрия, отказ, диагностика и recovery с ценой простоя.
- Dynamic replanning: срочная заявка, изменённое окно, потеря ресурса.
- Formation/orbit maintenance: манёвры с влиянием на расписание и бюджет.
- Conjunction response: обновляемая информация и безопасность, после reference Pc.

Для каждого нужны generator, feasible/infeasible случаи, objective, safety,
baseline, holdout, tiny exact/reference и failure explanations. Реализовывать в этом
порядке; новые семейства не должны обходить общий executor.

Train/test делить по регионам, эпохам, demand process и fleet composition.
Teacher, языковая перефразировка и близкие варианты одного плана остаются в одной
группе split. Скрытый test доступен evaluator, а не алгоритму генерации/подбора.

LLM интерфейс: typed tools observe/forecast/submit/cancel/advance, ограниченный
бюджет вызовов и времени. Оценивать исполнение, а не совпадение формулировки плана.
SFT маркирует teacher/version/допущения и прошедшую replay проверку; preference
пары сравнивают исполнимые решения при одинаковом контексте.

Выход: одна команда генерирует suite→baseline report→RL/SFT shards→replay verification.
Публикуемый benchmark не содержит тестовых ответов в наблюдении.

### R4 — доказать масштаб и удобство

Лестница нагрузки: 16 аппаратов/100 заявок, затем 64/1000 и 256/10000.
Это целевые уровни, не текущие возможности. Горизонты 24/72 часа; явные типы
связности, stations, fidelity, log policy и stochastic seeds для каждого уровня.
Зафиксировать hardware и память, wall time, steps/s, requests/s, startup/reset,
snapshot/replay cost, worker scaling. Нельзя сравнивать simplified path с reference
конкурента и называть это ускорением аналогичной симуляции.

Сначала профиль, затем event queues, geometry cache с invalidation, batched states,
ограниченный журнал, независимые episode workers. Оптимизация проходит R0/R2 gates.

Studio: одна страница с timeline/Gantt, ground track/3D, footprint, запланированным
и исполненным, поиском заявки и причиной unmet, resource utilization и сравнением
двух прогонов. Добавить keyboard navigation и экспорт отчёта с provenance.
Не показывать forecast как уже исполненную траекторию.

Выход: load report, восстановление worker после сбоя, ограниченная память,
установленный wheel, проверенный браузером workflow.

### R5 — сравнительная приёмка и пилот

Выполнить протокол раздела 5. Выбрать с потенциальным пользователем одну реальную
операцию, его baseline, разрешённые данные и критерии. Нужно проверить ценность,
время интеграции и результат на новых данных, а не только выразить интерес.

Довести versioning/migrations, installation matrix, model/data licenses, telemetry,
incident recovery и support docs. Для shared deployment отдельно ownership/auth,
quotas и isolation; локальная версия не требует преждевременного Kubernetes.

Выход: воспроизводимый pilot acceptance report и решение о следующей инвестиции.

## 5. Как проверяем «лучше»

1. Выбрать overlap: EO scheduling с BSK-RL; геометрию/динамику с выбранным reference;
   операторский workflow с доступным инструментом заказчика. Не ранжировать продукты
   по задачам, которые им не ставились.
2. Зафиксировать версии, конфигурации, physics/constraints, оборудование,
   warmup/reset, budget вычислений и preprocessing. Учесть setup и compilation.
3. При несовпадении capabilities оформить ограниченный общий профиль и отдельный
   native-feature showcase. Числа этих двух режимов не смешивать.
4. Оценивать одинаковую конечную полезность/constraints, включая failed runs,
   через общий evaluator либо проверенную конверсию артефактов.
5. Использовать не менее 20 paired scenarios для первого исследования; достаточный
   размер уточнять по variance/power analysis. Указывать confidence intervals,
   seeds и все исключения. Не публиковать только лучший seed.
6. Отдельно измерять wall time, peak RSS, качество плана, violations, reproducibility,
   время настройки и время диагностики ошибки. Не объединять всё в непрозрачный score.
7. Все hardware/лицензионные ограничения и неподдержанные случаи раскрывать.
   Если коммерческий инструмент недоступен — оставить comparison unverified.

Предлагаемые целевые пороги пилота, требующие согласования с клиентом:

- Ноль нарушений инвариантов целостности/ресурсного владения в acceptance corpus;
  это не доказательство нулевого риска во всех возможных сценариях.
- Повтор run artifact даёт одинаковые discrete outcomes; численные отклонения
  укладываются в профиль tolerance на документированной платформе.
- Сократить median time-to-first-valid-experiment и median time-to-diagnosis
  минимум на 30% относительно согласованного workflow клиента.
- Показать преимущество не менее 20% в одном выбранном измерении (полезность при
  равном budget либо время при сопоставимом качестве), без ухудшения safety.
- Для основного режима fast→reference перенос имеет заранее согласованный предел
  потери полезности; публикуется вся кривая fidelity/cost, не одна удачная точка.

Числа 20%/30% — продуктовые цели, не измеренные результаты и не обещания.
Заявление «лучше» допустимо только для названной задачи, baseline и профиля.

## 6. Задание агенту и порядок завершения

Порядок: **R0 → R1 → R2 → R3 → R4 → R5**. Первое поручение агенту — целиком A–H
из DEVELOPMENT_PLAN_V093, с сохранением требований R0/R1 этого документа.
Не поручать весь roadmap как один якобы гарантированный проход: независимая
валидация, лицензии внешних инструментов и клиентский пилот требуют входных данных.
После каждого R-этапа обновлять status и evidence, затем выполнять следующий,
если зависимости доступны. Не писать «готово», пока открыт обязательный gate.

Файлы отчётности, которые должны появляться по мере реализации:

- `docs/MISSION_EXECUTION_ACCEPTANCE.md` — gates A–H и regression.
- `docs/validation/REFERENCE_REPORT.md` — версия эталонов, погрешности и limits.
- `benchmarks/suites/` — спецификации suite; `artifacts/` — генерируемые результаты.
- `docs/benchmarks/COMPARISON_PROTOCOL.md` — зафиксированный протокол до измерения.
- `docs/benchmarks/COMPARISON_REPORT.md` — полные измерения и неподтверждённые части.
- `docs/PILOT_ACCEPTANCE.md` — реальная клиентская постановка и результат.

Эти будущие пути — задания на создание, не существующие доказательства.
Актуальные внутренние подтверждения: аудит, `v093_probes.py` и verification JSON.
