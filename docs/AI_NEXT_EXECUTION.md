# Следующие крупные пакеты после AI advancement

8 ноября 2026. Выполнять последовательно, локальными тестами и измерениями.
Ни один пункт ниже не закрыт только наличием документа. CI, commit, push и
публикацию не добавлять. Исходный ограниченный пакет: [AI_ADVANCEMENT_BUNDLE](AI_ADVANCEMENT_BUNDLE.md).

## G01 — единый контракт целей для разных классов миссий

**Статус на 9 ноября: реализован opt-in физический контракт.** Delivery,
kinematic/rigid attitude, momentum unloading, body-engine impulse и timed orbital
state/waypoints работают через один evaluator; есть общий reward, terminal,
replay, actor projection, численные goal/resource features и native SFT/RL gates.
13 synthetic cases содержат matched/unmatched controller precision, chemical /
electric / rotating thrust и негативные случаи. [Контракт](PHYSICAL_MISSION_GOALS.md).
Ниже сохранены исходные критерии этого пакета, а не список отсутствующих функций.

Историческое исходное состояние до G01: LLMEpisode.finish/SFT gate проверял
доставку заявок. У прежнего operations-suite
разгрузка маховиков оценивается отдельным native evaluator: это физический
benchmark, но ещё не готовая новая цель общего SFT/RL episode. Не переносить
результат `operational_goal_met` в delivery success простым переименованием.

Реализовать версионированные встроенные goal/reward contracts над native runtime:
delivery, momentum unloading, attitude acquisition и finite-burn maneuver.
Начальные условия, единицы, frame, допуски, бюджет времени/энергии/топлива и
критерии нарушения фиксируются в task recipe. Произвольный Python callback из
недоверенного task JSON не исполняется. Goal recipe входит в checkpoint/hash,
а прогресс выводится в наблюдения только в пределах actor access policy.

Приёмка: одинаковая цель в SDK/Gym/LLM; finish только после native условия;
неуспешная или небезопасная траектория не даёт positive SFT; ошибки сохранены
для RL; cold replay подтверждает reward/discount и цель. Для каждого контракта
нужны положительная траектория, wait baseline, невозможная/недостаточная команда,
подделка evaluator metadata и source-bound повтор. Затем перевести momentum
suite на общий контракт без потери прежней независимой физической оценки.

## G02 — настоящий Qwen3.5 SFT до/после

Сначала подготовить изолированное совместимое training-окружение и настоящий
локальный HF checkpoint Qwen3.5:4b. Текущий GGUF 3.39 GB — inference weights;
импорты установленного training stack завершаются NumPy ABI error. Наличие
PyTorch/PEFT по metadata не равно рабочему training stack; CUDA сейчас недоступна.
Другую версию Qwen без явного выбора пользователя не подставлять.

На зафиксированной ревизии заново проверить corpus. Сохранить происхождение
scripted teacher, независимость geometry splits, active/wait/finish counts и
assistant-only token labels. Нельзя выдавать 72 решения двух train-миссий на
одной геометрии за 72 независимых миссии или за реальные ответы LLM.

Запустить base rollout, LoRA, сохранение/повторную загрузку адаптера и tuned
rollout на одинаковых checkpoint, protocol и бюджетах. Development использовать
для настройки; test не использовать при выборе гиперпараметров. Зафиксировать
ошибки, пропуски, токены, задержки и результат каждой миссии. Аудит artifact
consistency без resampling не является доказательством происхождения весов.

Приёмка: реальный изменённый адаптер, все объявленные evaluation cells,
provider/native binding, отсутствие evaluation в train, явное before/after без
success filtering. Улучшение не требуется для признания честного эксперимента:
нулевой или отрицательный результат публикуется как получен.

## G03 — производительность и долгие эпизоды

Новый sequence-профиль проверен до 4 actors / 16 requests / 1200 s; legacy
большие профили не расширяют этот предел автоматически. В верхней наблюдённой
нагрузке native tool execution и replay заняли примерно по 80 секунд. Это
включает Python protocol, наблюдения, журнал и сборку record, а не только ODE.

Сначала измерить стоимость native step, actor projection, checkpoint/hash,
сериализации истории и replay отдельно. Затем убрать повторную сборку истории
с квадратичным ростом: bounded spool, неизменяемые transition chunks и
проверяемая hash-chain. Не заменять native acceptance оценкой планировщика.
Проверить crash/restart, усечённый последний chunk, повтор delivery и потерю
writer lease. Старые архивы остаются читаемыми на своей ревизии.

Приёмка: замороженные нагрузки до/после, одинаковые native outcomes и фактический
внешний worker RSS. Linux VmHWM не заменять унаследованным ru_maxrss. Число
actors/horizon расширять только вместе с квалификацией; не снимать schema limit
без измерения памяти, шагов и стоимости геометрии.

## G04 — совместное перепланирование остаточных и новых работ

Текущее recovery завершает принятые residual allocations до fresh sequence
suffix. Это сохраняет данные, но не оптимизирует совместно срочную новую заявку
и остаток CPU/передачи. Поддержка nominal kinematic/omni profiles ограничена;
rigid/degraded/faulted случаи могут использовать serial fallback.

Реализовать общий residual/fresh ledger с фактической позой, оставшимся CPU,
custody, TTL, подтверждённой доставкой, memory scratch и ресурсами станций.
Перестановка работ не должна менять исторические команды или обновлять TTL
продукта при продлении заявки. Отдельно квалифицировать degraded slew и
directional-radio профили. Search budget и неполнота поиска остаются видимыми.

Приёмка: urgent fresh job во время частичного CPU и частичной доставки,
конкуренция за shared station, отказ/возврат узла, alternate custody route,
отсутствие повторной съёмки и потери продуктов. Малый ограниченный exact oracle
использовать только с доказанной областью дискретной модели; не объявлять
infeasible из-за исчерпанного поиска.

## G05 — новые benchmark-задачи и независимые сравнения

Начальные задачи ориентации, разгрузки и манёвра теперь реализованы в G01.
Следующий модельный этап — orbital maintenance по областям элементов орбиты,
relative state/formation/inspection, физические sensor/measurement models,
разнообразие аппаратных профилей и дальнейшая верификация coupled dynamics.
G02 (обучение Qwen) не является блокером развития самого моделера.

После G01 добавить полноценные задачи: управление ориентацией с wheel limits;
манёвр с конечным включением двигателя и остатком топлива; орбитальное
обслуживание; relative inspection; диагностика и восстановление подсистем;
распределённые LLM-агенты с ограниченной связью. Наличие модели двигателя или
MARL adapter не считать завершением соответствующего benchmark.

Для каждого семейства определить наблюдения, действия, partial observability,
safety/completion, отрицательные случаи и сильный baseline. Новые геометрии и
отказы фиксировать до оценки, сохранять недостижимые случаи, не фильтровать
seed по успеху. Одно центральное LLM над объединением трёх actor views не
называть тремя независимыми распределёнными агентами.

Затем реализовать воспроизводимые адаптеры независимых engines с одинаковыми
frames/time/forces/initial state. Начать с коротких orbit/attitude/burn cases,
потом согласованной mission task. Заранее объявить tolerances и различия моделей.
Не ранжировать STK/Basilisk/Orekit по описанию функций или по результатам одного
нашего внутреннего планировщика. Внешний engine должен действительно исполнить
согласованную постановку, а raw outputs и версии — сохраниться.

## Отдельная внешняя квалификация

Открытые спецификации и аналитические решения не заменяют измерения реального
аппарата. Для pilot нужна конкретная эксплуатационная задача, доступные данные,
границы ответственности и согласованный критерий качества. Flight qualification,
клиентский эффект и универсальное превосходство остаются недоказанными до своих
экспериментов. Программные тесты не закрывают эти пункты автоматически.

Реализован первый bounded блок относительных целей двух аппаратов и RTN-кинематики.
