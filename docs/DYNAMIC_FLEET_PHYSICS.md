# Динамические миссии, совместные решения и физические подтверждения

Реестр теперь включает пятый профиль — ограниченный совместный начальный
[EO/ISL-план](JOINT_NETWORK_PLANNING.md). Он поддерживает независимое продолжение
по текущему владельцу/остаткам после native-событий. При отмене незавершённой
ISL-передачи фрагменты могут быть отброшены; полное custody не подменяется
частичным прогрессом. Старые количества проверок ниже исторические.

Этот блок связывает native события и восстановление по фазам с пультом, API
и SDK. Отдельно добавлены совместные раунды, EO/CPU/ISL/Ground-ACK через тот же
SDK и аналитические проверки ядер. Область поддержки ограничена явно.

## Динамическое управление

`MissionWorkspace.evolve()` создаёт независимое продолжение. Источник, его
capabilities и реальные наблюдения не меняются. Исполненный префикс воспроизводится
и сравнивается native physical report. Активные команды прерываются штатным
`cancel_actor` за один шаг; пакет событий исполняется за следующий шаг.
Из фактических продуктов, остатков CPU и переданных битов строится план оставшихся
этапов. Новый каталог проверяется на неизменность физики префикса и событий,
затем устанавливается через стандартный operator restore.

События и поля payload:

- `request_cancelled`: `request_id`;
- `request_priority_changed`: `request_id`, `priority`;
- `request_deadline_changed`: `request_id`, `deadline_sec`;
- `station_outage_added`: `station`, `start_sec`, `end_sec`;
- `station_recovered`: `station`;
- `spacecraft_fault`, `spacecraft_fault_cleared`: `actor`, `subsystem`;
- `spacecraft_safe_mode`, `spacecraft_recover`: `actor`.

Подсистемы: bus, adcs, payload, cpu, radio, propulsion. Native модель проверяет
условия восстановления. Флаг отказа описывает доступность, а не физическую
причину поломки. В канале агента инъекция операторских событий запрещена.

Новые заявки передаются в `additions` как `MissionOrder`: явный аппарат и станция,
уже объявленные координаты, уникальный ID. Начальный граф симуляции не меняется
задним числом: заявка и job появляются через `request_added`. Планировщику отдельно
передаётся intent-граф уже применённых изменений. Новую заявку не следует менять
отдельным событием в том же пакете; изменения требуют уже объявленной и принадлежащей demand-authority заявки.
Оператор может менять и отменять её до release; невыпущенная заявка при этом
не появляется в наблюдениях агента. `request_authority` — защищённое чтение
только фактически существующего native-графа, а не будущих событий.

```python
from space_env.workspace import MissionWorkspace

source = MissionWorkspace()
source.run(decisions=20)
continuation = source.evolve(
    "Восстановить после отказа станции", idempotency_key="incident/1",
    events=[{"type": "station_outage_added", "payload": {
        "station": "West", "start_sec": 105.0, "end_sec": 140.0,
    }}],
)
result = continuation.run()
continuation.export("/tmp/dynamic-training.zip")
```

Времена выбираются по фактическому состоянию. Момент события — время источника
плюс шаг прерывания, если есть активные команды. Выпуск новых заявок и начало
отказа не могут предшествовать событию. События должны оставить будущий горизонт.

Сырой продукт требует только оставшейся обработки и передачи, финальный —
оставшихся битов передачи. Завершённые заявки не исполняются повторно. Отменённые
и невыполнимые сохраняются в знаменателе. Отказ блокирует этапы плана, но сам по
себе не выдаётся за terminal native статус заявки. После устранения отказа
можно снова вызвать `evolve`. Пустой пакет — восстановление без новых событий.

Прерванная съёмка не считается продуктом: единственная native попытка может
оказаться исчерпанной. Продолжение экспозиции с середины не обещается. CPU и TX
используют то, что native модель действительно сохранила; существующие продукты
не заменяются preload-данными и не отбрасываются планировщиком.

API: `POST /api/operator/sessions/{id}/evolve`, Bearer центрального оператора.
Обязательны `expected_revision`, `control_epoch`, `idempotency_key`, `reason`;
необязательны `additions`, `events`, `planner`. Ответ — новая operator-сессия.
Повтор того же ключа/тела возвращает ту же активную ветку; другое тело — конфликт.
После рестарта нужен сохранённый файл доступа или локальное восстановление
владельцем ОС: plaintext credentials не извлекаются из базы. `workspace.dynamic`
хранит события, состояния фаз, причину и физические SHA до/после. Эти сведения
не добавляются в наблюдения агента.

В пульте используется раздел «Динамические события и восстановление этапов»:
JSON-пакет и кнопка применения. Исходная ветка доступна через переключение;
для рестарта сохраняйте отдельные файлы доступа.

Лимиты: 4 добавления и до 8 событий вместе с добавлениями за пакет; 1–4 аппарата,
до 64 заявок, существующие точки и фиксированные владельцы. Растущие каталоги
ограничены 256 действиями пульта. Горизонт не расширяется. Энергетические оценки
консервативны, возможны false negatives. Будущие неизвестные отказы не предсказываются.

## Совместные решения аппаратов

`fleet_round()` собирает решения ролей, не двигая время. Наблюдение выдаётся
по capability участника; чужая команда и инъекция событий недоступны. Пропуск —
явный `wait`. После решений всех аппаратов оператор фиксирует один общий шаг.

```python
mission = MissionWorkspace()
round_ = mission.fleet_round()
for role in round_.roles:
    token = mission.connection["tokens"]["role:" + role]
    observation = round_.observe(token)
    round_.submit(token, ["wait"])
receipt = round_.commit(mission.connection["tokens"]["operator"], "joint/1")
```

В распределённом клиенте агент получает только свою capability, полный connection
остаётся у координатора. Общий набор проверяет native runtime: конфликты памяти,
передатчиков и терминалов не разрешаются порядком прихода голосов. Отклонённое
решение расходует время по обычному контракту шага. Изменившиеся revision/epoch
делают раунд устаревшим. Повтор commit идемпотентен; ключи раундов изолированы.

HTTP: `POST /api/operator/sessions/{id}/round`, `operation`: `create` от оператора,
`observe`/`submit` от роли, `commit` от оператора. Передаются `round_id`, для submit
— `action_ids`, для commit — `idempotency_key`. Ожидающие голоса эфемерны:
до 32 записей на процесс, TTL 15 минут. При заполнении кэша удаляется старый
исполненный раунд; активные предложения не вытесняются. Идемпотентный HTTP-ответ
доступен, пока запись сохранена. Для отсутствующей записи сначала прочитайте
текущее состояние, не повторяйте исполнение вслепую. После рестарта прочитайте durable состояние
и откройте новый раунд; предложения не были исполненными командами.

## Межспутниковый профиль

`MissionWorkspace.relay()` открывает существующий синтетический
EO → CPU → ISL → Ground ACK на том же operator runtime. Доступны `state`, `step`,
`run`, `fleet_round`, `export`; в пульте — соответствующая демонстрация. Native
DTN учитывает хранение, передачу и ACK; route-aware baseline выбирает действия.

Это не произвольный совместный оптимизатор EO/ISL/динамических назначений:
`evolve` пока требует прямой workspace EO-профиль. Runtime/API общие, но классы
планирования различаются. Свободная маршрутизация частичных продуктов между любыми
аппаратами при динамическом переназначении остаётся открытой задачей.

## Достоверность физических моделей

`GET /api/operator/workspace/physics` и карточка редактора описывают четыре
профиля, механизмы и ограничения. Это контракт, а не квалификация сценария.

```bash
python -m space_env.validation.profile_evidence --output /tmp/new-evidence.json
```

Девять аналитических случаев: круговые/эллиптические орбиты при двух максимальных
шагах, сохранение энергии; массовый расход, сухая масса и импульс постоянной тяги;
адиабатический тепловой баланс и радиационное равновесие. Орбита сравнивается
с решением уравнения Кеплера, а не вторым ODE-интегратором; массовый импульс —
с независимым рядом интеграла. Общие константы явно считаются общими входами.

Невязки и пороги относятся только к изолированным численным задачам. Они не
задают погрешность реальной орбиты, изображения, RF или ADCS. J2/drag/SRP,
coupled rigid/thermal, неопределённости и измерительная калибровка требуют своих
проверок; существующие cross-check/refinement инструменты остаются отдельными.
Собственной телеметрии нет, поэтому `hardware_calibrated=false` явно сохраняется.
Подгонка к синтетике не является аппаратной калибровкой.

## Локальные тесты

```bash
python -m pytest tests/test_workspace_dynamic.py tests/test_fleet_round.py tests/test_profile_evidence.py -q
```

Также проверяются затронутые workspace/operator, incident, demand и actor сценарии.
CI, публикация и git-операции не требуются. Ветви одного источника сохраняют общую
lineage и повторяющийся префикс: их нельзя считать независимыми train/test эпизодами.

Дополнительно выполнен существующий внешний force cross-check на этой сборке:
`force_crosscheck(long_arcs=False)` вернул `passed=true`: 9 force comparisons
и одна J2-дуга. Сравнение использует внешние формулы Boinor, но общие EOP,
константы, density и ephemeris inputs; это не независимая проверка входных
геофизических данных и не точность реальной миссии. Длинные дуги этим запуском
не подтверждаются. Отчёты временных локальных прогонов не добавляются в git.
