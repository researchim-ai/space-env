# Многоэтапные миссии для агентов

`AgentCampaignSession` подключает существующий `CampaignSession` к JSON-инструментам,
`IndustrialEpisode`, `IndustrialEnv`, проверке воспроизведения и SFT/RL-экспорту.
Все фазы используют **один** `TaskSession`: орбиты, навигационные фильтры, команды,
продукты, заряд, расход энергии и топлива продолжаются без переинициализации.

## Контракт

Конфигурация содержит `scenario`, `task`, `campaign` и необязательный `seed`.
В `task` не должно быть собственного `goal`. Цели задаются в `campaign.phases`:
уникальный ID, цель и строго возрастающий абсолютный `deadline_sec`.
Все фазовые цели проверяются существующим физическим/навигационным контрактом
до начала исполнения. Максимум 32 фазы и 512 решений. Каталог с `inject`
отклоняется: агент не может объявлять отказы, новые заявки или восстановление
аппарата собственными действиями.

```python
from space_env.industrial.campaign import AgentCampaignSession
from space_env.industrial.agent import IndustrialEpisode
from space_env.industrial.gym import IndustrialEnv

session = AgentCampaignSession(configuration)
episode = IndustrialEpisode(
    session, max_calls=128, policy_origin="external_llm",
    task_text="Публичное описание задачи с критериями и ограничениями.",
)
env = IndustrialEnv("native_campaign", configuration, max_calls=128)
```

Содержимое `action`:

```json
{"choices": {"@central": ["wait"]}, "advance_sec": 1.0}
```

Названия допустимых действий берутся из текущего `native.catalogue` наблюдения.
Продолжительность дополнительно проверяется существующим TaskSession;
ожидание ограничивается ближайшей границей активной фазовой цели.
Идемпотентный повтор возвращает прежний результат. Конфликт ключа, устаревшая
ревизия и некорректный формат не создают нового физического перехода.
Ошибочная команда модели расходует бюджет обращений IndustrialEpisode.

## Наблюдения и обучение

В публичном наблюдении находятся только существующая центральная проекция
TaskSession и ограничения длительности решения. Фазовые цели, остаточные ошибки,
список завершённых фаз и полный сценарий туда не добавляются.
Это централизованный контроллер, а не обучение независимых распределённых агентов.
Постановку задачи надо явно сообщать в `task_text`: скрытые цели не заменяют инструкцию.

Награда равна штатной награде перехода плюс единица за завершённую фазу и минус
единица при провале кампании. Завершённая фаза — историческое достижение;
если результат нужно сохранять, следующая фаза должна содержать соответствующее условие.
Ресурсные ограничения считаются от начала миссии и между фазами не обнуляются.

`metrics()` и Gym `info.trainer_only` доступны оценщику. Восстановление использует
повтор истории с проверкой исходников, зависимостей и контрольных сумм состояния.
Файлы эпизодов и checkpoint содержат привилегированную конфигурацию: их нельзя
подавать модели как наблюдение. Экспорт обучения переносит только сообщения и
скалярные награды; SFT требует успешного эпизода без ошибок и явного происхождения политики.

## Локальная демонстрация

```bash
python -m examples.modeling.agent_campaign --mission finite --output artifacts/my-agent-finite
python -m examples.modeling.agent_campaign --mission eo --output artifacts/my-agent-eo
python -m pytest -q tests/test_agent_campaign.py tests/test_composed_missions.py
```

Выходной каталог должен быть новым. Драйвер сравнивает ожидание со **сценарной
привилегированной** последовательностью, проверяет cold replay, сохраняет RL
для обоих вариантов и SFT только для успешного. Это проверка интеграции, не
результат LLM и не доказательство способности решать неизвестные миссии.

## Границы результата

Этот блок не расширяет саму физику и не подтверждает многосуточную точность.
Примеры короткие и синтетические. Внешние события поддерживаются описанным ниже расширением.
Он делает уже существующие физические фазы доступными для обучения и оценки
агентов в общем интерфейсе. До длительных операционных кампаний остаются:

1. Обобщённое перепланирование и вытеснение работ с учётом совместных ресурсов; базовая реактивная политика уже доступна.
2. Адаптивная политика ожидания и измеренная стоимость длинного исполнения (само прерывание на событиях уже поддерживается).
3. Связанный многоволновой EO→CPU→ISL→ground сценарий на часы и сутки.
4. Проверки сходимости, независимые эталоны и области применимости для каждой модели.
5. Оценка реальной модели на неизвестных задачах с провалами, стоимостью и базовыми политиками.

Старые source-bound receipts относятся к прежнему состоянию пакета; добавление
этого адаптера не превращает их в аттестацию нового состояния.

## Расширение: внешние события

Теперь TaskSpec поддерживает авторские `environment_events`: поступление и
изменение заявок, отказы аппаратов и станций, восстановление. События ограничивают
интервал решения и воспроизводятся вместе с миссией. Подробный контракт,
ограничения и запуск — [TASK_ENVIRONMENT_EVENTS.md](TASK_ENVIRONMENT_EVENTS.md).
Оптимальное перепланирование и длительная физическая квалификация остаются
отдельными задачами.

Для продолжения работ по текущим наблюдениям добавлена [публичная реактивная
политика](REACTIVE_CAMPAIGN_CONTROL.md) с явным контрактом обслуживания и локальным
сравнением при изменении времени событий. Это эвристика, а не оптимальный планировщик.
