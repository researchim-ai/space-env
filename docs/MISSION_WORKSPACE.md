# Настройка → план → выполнение → данные

Рабочая страница объединяет редактор миссии, существующий пульт оператора,
native runtime, фактические результаты и экспорт. Это новый пользовательский
путь для ограниченного профиля EO → CPU → Ground, а не замена всем моделям ядра.

## Запуск на одной странице

```bash
python -m space_env.api.server
```

Откройте <http://127.0.0.1:8766/>. Введите название, горизонт и шаг;
настройте плоскости круговых орбит, станции и заявки. Фазы в одной плоскости
задают аппараты с ID вида `a-00`, `a-01`. Координаты целей и станций заданы
в градусах, время выпуска и дедлайн — в секундах от начала миссии.

«Составить план и открыть миссию» создаёт отдельную сессию. «Шаг планировщика»
исполняет одно решение; «Прогон планировщика» последовательно исполняет план
до горизонта. Остановка прогона оставляет уже исполненные решения в журнале.
Карта и телеметрия показывают состояние симуляции; браузерные часы не двигают физику.

Карточки заявок разделяют запланированные времена и фактические этапы.
Отметки съёмки, обработки и доставки опираются на native продукты и статусы,
а не только на достижение времени в расписании. Незапланированные заявки
остаются в общем знаменателе; причина отсутствия цепочки выводится отдельно
от фактического статуса исполнения.

Изменение конфигурации не меняет активную миссию: создайте новую. Ручные команды,
отличающиеся от плана, делают его устаревшим. Автопрогон блокируется с
`plan_diverged`; можно продолжать вручную или создать новую миссию.
На допустимой границе можно явно [перепланировать оставшуюся работу](WORKSPACE_REPLANNING.md)
в отдельной ветке с проверкой физического префикса. Автоматическое реагирование
на события и прерывание активных цепочек этим интерфейсом не заявляются.

## Python SDK

```python
from space_env.workspace import MissionWorkspace, default_configuration

configuration = default_configuration()
configuration["name"] = "Две независимые съёмки"
mission = MissionWorkspace(configuration)
try:
    state = mission.run()
    result = state["workspace"]
    print(result["fulfilled"], "/", result["total"])
    mission.export("/tmp/mission-training.zip")
finally:
    mission.close()
```

`step()` выполняет следующее решение; `run(decisions=10)` ограничивает число
решений. SDK использует тот же координатор, версии состояния и механизмы
экспорта, что и веб-пульт. Пример с чтением JSON и сохранением результатов:

```bash
python -m examples.workspace.run --output /tmp/new-mission
python -m examples.workspace.run --configuration my.json --output /tmp/another-mission
```

Каталог результата должен быть новым. В нём сохраняются `configuration.json`,
`result.json` и `training.zip`. RL/SFT находятся в ролевых каталогах ZIP,
например `role-000/rl.jsonl`. Экспорт не делает эвристику экспертным учителем:
качество SFT-политики требует отдельной оценки. Файл доступа к сессии содержит
секретные capabilities; его нужно хранить отдельно от обучающих данных.

## Схема конфигурации

Публичные типы — `MissionConfiguration`, `MissionOrder`; schema ID:
`space-env.mission-configuration/1`. Полную конфигурацию можно скачать из формы,
изменить в раскрываемом JSON-редакторе и проверить перед созданием миссии.

- `epoch_utc`, `seed`, `horizon_sec`, `decision_sec`: эпоха и сетка решений.
- `planes`: ID, радиус круговой орбиты в метрах, наклонение, RAAN и фазы.
  В форме вместо радиуса показана высота над опорным радиусом Земли.
- `stations`: имя, широта, долгота, число терминалов.
- `requests`: ID, `actor_id`, станция, координаты цели,
  приоритет, выпуск и дедлайн; в JSON также длительности съёмки/обработки
  и размеры исходного/выходного продукта в битах.
- `memory_mbit`, `battery_wh`, `rate_bps`: общие для аппаратов параметры
  данного профиля. `outages` задаёт недоступность станции во временном интервале.
- `planner`: `max_search_nodes`, `max_orders`, `edge_guard_sec`.
- `max_assignment_trials`: до 32 вариантов назначения, по умолчанию 12.
  `actor_id: null` и/или `station: null` включают автоматический выбор.
  Пропущенные поля назначения также считаются автоматическими.

Ссылки, уникальность ID, границы времени и числа аппаратов проверяются до запуска.
Одинаковые координаты цели могут использоваться несколькими разными заявками;
продукты связываются с конкретной заявкой через `request_ref`.

## Что изменено в планировании

`schedule_fleet()` сначала получает полный план прежней эвристики. Затем
сравнивает детерминированные порядки: дедлайн, приоритет, короткая цепочка,
время выпуска и ограниченные перестановки. Для них пробуются раннее размещение
и компактное резервирование аппарата: позднее наведение перед доступным окном
позволяет не занимать аппарат длительным ожиданием передачи.

Выбор лексикографический: сумма приоритетов запланированных заявок,
затем число заявок, затем меньшая сумма времён завершения. Приоритеты неотрицательны.
Исходный полный план сохраняется, если не найден лучший. Поиск всех вариантов
делит общий бюджет узлов; если бюджета не хватает даже для исходного полного
плана, создание миссии завершается понятной ошибкой. Варианты не оцениваются
скрытыми native прогонами: прогноз одинаков для всех кандидатов.

Учитываются длительности наведения/съёмки/CPU/TX, окна и дедлайны,
блокировки аппарата и терминала станции, консервативный запас энергии и TX-квота.
Это ограниченный эвристический поиск, без гарантии глобального оптимума.
Регрессионный пример с поздним окном связи даёт 2 запланированные заявки
вместо 1 у исходного размещения; этот пример не является общей оценкой качества.
Реальную доставку по-прежнему подтверждает только исполнение симулятора.

## Область поддержки

- 1–4 аппарата, 1–16 станций, 1–64 заявки и до 16 разных точек съёмки.
- Горизонт 60–3600 с, шаг 1–30 с; горизонт кратен шагу, до 240 решений.
- Аппарат и станция назначаются вручную или ограниченным поиском.
  ISL-маршрутизация и автоматическое перепланирование здесь пока отсутствуют.
- Кинематическое наведение и условные бортовые продукты; геометрические окна,
  идеализированная передача. Не моделируются изображения реального сенсора,
  метео-зависимый радиоканал или откалиброванный конкретный аппарат.
- Ограничения этой формы не являются пределами всех профилей библиотеки.
  Более крупные workloads запускаются отдельными инструментами.
- Локальный режим оператора; существующая SQLite-сессия сохраняет конфигурацию
  и план при восстановлении в совместимой сборке. Не является multi-tenant сервисом.

Дополнительная информация о плане доступна только центральному оператору;
она не добавляется в наблюдения агента и роли аппарата.

## HTTP API и локальные тесты

- `GET /api/operator/workspace/presets`: стартовая конфигурация и лимиты.
- `POST /api/operator/workspace/configuration`: проверка и нормализация JSON.
- `POST /api/operator/workspace`: построение плана и создание сессии.

Дальнейшие шаги, роли, checkpoint, replay и экспорт используют существующий
operator API и его capabilities/revision/control epoch. Создание плана ограничено
одним одновременным вычислением в процессе; занятый планировщик отвечает 429.

```bash
python -m pytest tests/test_workspace.py tests/test_operator.py tests/test_operator_durable.py tests/test_chain_planning.py tests/test_release_benchmark.py -q
```

Этот набор локально завершился: **128 passed**. Он проверяет реальное выполнение
и экспорт, восстановление, ручное отклонение, невыполнимые окна, ролевую изоляцию,
валидацию конфигурации и соблюдение бюджета планирования. Стартовый сценарий
отдельно выполнен через веб-интерфейс: обе заявки доставлены. CI не требуется.


## Автоматический выбор аппарата и станции

В форме выберите «Автоматически» в одном или обоих полях заявки. Кнопка
«Автоназначение» загружает пример с двумя свободными заявками. Явное назначение
фиксировано: поиск не меняет выбранный пользователем аппарат или станцию.

Поиск начинает с детерминированного распределения по доступным ресурсам,
затем сравнивает альтернативные пары аппарат/станция для отдельных заявок.
Для каждого варианта компилируются native заявки и команды, собирается
разрешённый прогноз и строится полное расписание. Выбирается лучший найденный
вариант по сумме приоритетов, числу запланированных доставок и времени.
Улучшения продолжаются в пределах `max_assignment_trials`; число узлов
всех запусков планировщика вместе ограничено `planner.max_search_nodes`.
Ошибочные варианты отражаются в отчёте и консервативно расходуют выделенный бюджет.
Также ограничено число хранимых предложений. Это локальный эвристический поиск,
а не полный перебор всех назначений. При большом числе ресурсов малый бюджет
может не позволить рассмотреть подходящий вариант. Бюджет узлов не ограничивает
время вычисления; число сборок прогноза ограничено числом вариантов.

`workspace.configuration` сохраняет исходные намерения, включая `null`;
`workspace.resolved_configuration` — выбранные назначения. `workspace.assignment`
содержит варианты, прогнозные оценки, ошибки и расход общего бюджета. Эти поля
доступны центральному оператору и в его результате, а не в наблюдениях агента.
Невыполнимая заявка остаётся в общем числе заявок даже при автоназначении.

```python
configuration = default_configuration()
for request in configuration["requests"]:
    request["actor_id"] = None
    request["station"] = None
mission = MissionWorkspace(configuration)
```

Низкоуровневый `compile_configuration` требует уже назначенные заявки;
для автоматического выбора используйте `MissionWorkspace` или HTTP API создания.
Проверки нового блока: `python -m pytest tests/test_workspace_assignment.py -q`.

`test_workspace_assignment`, `test_workspace`, `test_operator`,
