# Mission Families v1 — разнообразные задачи исполнения для LLM-агентов

8 ноября 2026. `space_env.llm.mission_suite` расширяет постановки над общим
MissionRuntime и форматом LLMEpisode. Никакая модель не вызывается автоматически.

## Фиксированный набор

36 физических конфигураций: шесть семейств на шести геометрических группах,
по две геометрии в train/development/test. Геометрии взяты из ранее опубликованного
network regression suite, а не объявлены новыми закрытыми holdout. Между splits
пересечение geometry fingerprints запрещено. Разные workload variants на одной
геометрии не считаются независимыми геометрическими примерами.

Семейства меняют конкретные входы, а не только название задачи:

- **relay-chain**: два направленных ISL-звена, до двух переходов, без прямой
  перемычки fleet-00 → fleet-02.
- **cpu-backlog**: 35/20/45 секунд CPU-работы у трёх продуктов.
- **memory-pressure**: ёмкость памяти 1,2 Мбит, в том числе запросы с объёмом
  исходного продукта больше доступной памяти.
- **station-blackout**: наземная станция недоступна на [0,120] с.
- **link-blackout**: первое направленное ISL-звено недоступно на [0,90] с,
  прямая перемычка удалена.
- **deadline-pressure**: три заявки с дедлайнами 30/45/60 с.

Компиляция не исполняет миссии, не читает оценки агентов и не отбирает только
достижимые варианты. Некоторые заявки и даже целые сценарии могут оказаться
недостижимыми. Это часть проверяемой задачи, а не повод исключить их из отчёта.

Это исполнение операторского каталога команд, не свободный синтез плана. Отказы
заданы конфигурацией до запуска. Внезапные новые события во время диалога и
политика восстановления после них требуют отдельного интерактивного контракта;
данный пакет не называет заранее объявленный outage динамическим открытием.

## Baseline и причинность

Для каждого выбранного case исполняются три политики с одинаковым исходным
native checkpoint и бюджетом 64 вызова:

1. `wait` — отрицательный baseline.
2. `public_memory` — доступные текущие наблюдения и память использованных команд.
3. `reference_schedule` — privileged scripted демонстрация по рассчитанному плану.

Третья политика явно отделена в отчёте; её нельзя ранжировать как честного
actor-only агента. Никакой scripted baseline не называется Qwen или результатом
обучения. Успех, полнота доставки и приоритет берутся из фактического native
lifecycle, а не из планового списка команд. Возврат из runtime без исключения
(`status=completed`) не означает, что все заявки выполнены (`metrics.success`).

Ошибки native setup/политики сохраняются как error cells. В агрегатах они остаются
в знаменателе: value_lower=0, value_upper=1 для неизвестного результата такой
ячейки. Измеренная неудачная миссия с нулевой доставкой имеет известный ноль,
а не неизвестную верхнюю границу. Матричный контракт запрещает пропущенные,
дублированные и неверно подписанные case/policy ячейки.

## Исполнение и аудит

```bash
# Только заморозить конфигурации — без запуска физики:
python -m space_env.llm.mission_suite --compile /tmp/families-v1.json

# Все 36 случаев × 3 scripted baseline:
python -m space_env.llm.mission_suite --output /tmp/new-family-benchmark

# Небольшая явно выбранная подматрица:
python -m space_env.llm.mission_suite --output /tmp/new-family-smoke \
  --case equatorial-relay-chain --case equatorial-memory-pressure

python -m space_env.llm.mission_suite --audit /tmp/new-family-smoke
```

Output должен быть новым. `progress.json` сохраняет промежуточные ячейки;
только `report.json` вместе с успешным аудитом является завершённым результатом.
При остановке процесса частичная output-директория остаётся для диагностики,
не получает статус принятого корпуса. Автоматического resume здесь нет.

Аудит не вызывает провайдера. Он проверяет source binding, frozen suite,
выбранную матрицу и агрегаты, повторяет native-эпизоды и связывает их с исходной
конфигурацией, task text, бюджетами, split, policy origin и итоговыми метриками.
Подмена метрик или принадлежности split с пересчитанным JSON checksum не проходит.
Historical source-bound результаты надо воспроизводить на их ревизии.

## Связь с корпусом SFT/RL

Каждый успешный native запуск сохраняет LLMEpisode (`case--policy.json`). Его
можно передать `space_env.llm.corpus build`. Только train попадает в data/;
неуспешные миссии сохраняются для RL, positive SFT требует error-free native goal.
Для общей защиты между наборами зарегистрируйте корпус в том же factory registry.
Privileged provenance сохраняется, не превращается в actor-only teacher.

Нативных episode JSON недостаточно для wire-SFT: реальный provider request/response
нужно получить через локальный LLM-runner и проверить как local-provider bundle.
Для Qwen конфигурация case извлекается из frozen suite и передаётся в существующий
`examples/llm/run_local_qwen.py --configuration ... --split test
--case-group ... --protocol-profile json_fixed_v1 --max-calls 64`. Это отдельный
inference-эксперимент с записью модели и расходов, не часть scripted benchmark.

Результаты данного пакета не доказывают улучшение от SFT, OOD-обобщение,
аппаратную точность или превосходство над внешним симулятором.

Представительный пример для проверки всей цепочки и трёх splits:

```bash
python -m examples.llm.family_demo --output /tmp/new-family-demo
```

Он выбирает все шесть семейств на первой train-геометрии и relay-chain на одной
development и одной test-геометрии: восемь cases × три политики = 24 исполнения.
Это явная подматрица, не приёмка всех 108 исполнений полного набора. `--full`
запускает всю матрицу. В отчёте всегда сохранён точный `selected` список.

## Измеренный представительный прогон

На финальных исходниках 24/24 baseline-исполнения прошли native replay без runtime
ошибок: восемь случаев на трёх геометриях, все ML splits. Это не полный прогон
36 × 3. **Полное выполнение всех трёх заявок не достигнуто ни одной политикой**
в этой подматрице. Reference schedule доставлял одну заявку в семи выбранных
случаях и ни одной в deadline-pressure; public_memory/wait не закрыли всю миссию.
Сводка не превращает частичную доставку или `status=completed` в успех цели.

Это выявленная граница нынешнего планировщика/каталога и политик на данных
нагрузках, а не положительный SFT-корпус или превосходство агента. Следующий
этап — диагностировать полноту доступных цепочек и качество политики на
многозаявочных миссиях. Без этого масштабирование положительного SFT преждевременно.

27 новых tests плюс предыдущие LLM/corpus/wire/episode/benchmark/Ollama tests:
**103 passed / 104.01 s**. Полная регрессия всей физической библиотеки этим
прогоном не заявляется. [Машинный протокол](acceptance/LLM_MISSION_FAMILIES_V1.json).

Дополнительно восемь reference-эпизодов из smoke собраны в общий корпус и
зарегистрированы, с независимой проверкой: 6 train + 2 evaluation, три
независимые геометрии. Получено 6 RL-строк и **0 positive SFT**; evaluation
в training JSONL не попал. Это проверка интеграции с corpus/registry, а не
подмена частично успешных примеров экспертными демонстрациями.
