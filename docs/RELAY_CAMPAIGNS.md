# Длительная миссия с ISL и общим наземным ресурсом

`space_env.tasks.relay_campaign.relay_campaign` объединяет существующие native
EO, CPU, RF и DTN-компоненты в одной непрерывной кампании. Два аппарата a/b
снимают и обрабатывают данные; два аппарата r/s принимают custody и доставляют
результаты на общую станцию. Управление централизованное, по текущей идеальной
телеметрии; это не распределённое обучение четырёх независимых агентов.

## Что исполняется

Начальные три заявки аппарат a доставляет напрямую на S-band станцию Ground.
Две поздние заявки появляются внешними событиями. Каждая проходит собственную
цепочку imaging → transform → relay → ground ACK. После выполнения заявок
кампания продолжается до заданного горизонта без сброса орбит, памяти и энергии.

Для камер отдельно сконструированы окна наблюдения: WGS84-пересечение
фиксированной начальной оптической оси в номинальную середину acquisition.
Геометрия не подбирается политикой во время исполнения. Порог ориентации и
исходный footprint не ослаблены для достижения успеха. Это конструктивный
синтетический workload, не произвольные customer targets и не blind holdout.

Поздние продукты направляются по объявленным маршрутам a→r и b→s.
Камеры передают на 2.2 GHz, ретрансляторы — на 8.2 GHz. Late-Ground принимает
8.1–8.3 GHz: прямой наземный путь камер не обеспечивает совместимость диапазонов.
В публичном каталоге нет обходного downlink позднего продукта с камеры.
Native RF-budget дополнительно подтверждает нулевую скорость такого пути.

Передача между аппаратами использует native whole-product custody,
stop-and-wait фрагменты, собственную память приёмника, сохранение исходной копии
до подтверждения, таймауты и повторы. Подтверждение custody перемещает владельца
native продукта; наземный ACK завершает клиентскую заявку. Дополнительного
прикладного счётчика доставленных битов нет.

## Конкуренция за станцию

После подготовки обоих продуктов общая станция восстанавливается внешним
событием. При одном терминале и агрегированном лимите 250 kbit/s запросы r/s
конкурируют за один ресурс. У ретрансляторов фиксированная объявленная мода
250 kbit/s; native receiver имеет отдельные ограничения терминалов, скорости
и полосы. Выделение детерминированное, не оптимальное и не гарантированно справедливое.

Для диагностики resource-lanes журнал теперь сохраняет `radio_offers` до
распределения общего ресурса. Прежние фактические выдачи сохраняются отдельно.
Новый readonly-режим native selector используется только для регистрации спроса;
обычное распределение по умолчанию не изменено.

Trainer-only `metrics.network_accounting` выводит из этих журналов:

- Историю смены custody, число завершённых/истёкших передач и повторов ACK.
- Дублирующиеся принятые биты и ошибки inventory/receiver/serialization-баланса.
- Число одновременных выдач, максимум выделенной скорости и превышения лимитов.
- Длительность интервалов, когда pre-resource-lane спрос превышал число терминалов.

Последняя величина — интервал избыточного спроса, не сумма задержек всех аппаратов
и не общий детектор любых resource bottlenecks. Например, два терминала при
лимите 250 kbit/s всё ещё ограничены скоростью. Диагностика не добавляется в
наблюдение агента; actor-local resource-lane проекция не получает чужие заявки.

## Ориентация по текущему запросу

`CampaignPolicySpec.request_pointing=true` включает ограниченную реактивную
поддержку slew к текущему target_id запроса. Она работает только для объявленных
request_ref-шаблонов с публичным текущим pointing error выше payload tolerance.
Если imaging уже доступен, он имеет приоритет. К произвольному quaternion,
станции или скрытой будущей цели такая логика не применяется.

При текущем `current_settling`/`current_body_rate` политика сохраняет короткий
опрос, чтобы не перескочить период готовности. Native rate-limited slew,
settling и весь интервал съёмки продолжают проверяться исполнителем.
По умолчанию request_pointing выключен; прежние политики сохраняют поведение.

## Запуск и данные

```bash
python -m examples.modeling.relay_campaign_study --output artifacts/my-relay-study
python -m examples.modeling.relay_campaign_audit artifacts/my-relay-study
python -m pytest -q tests/test_relay_campaign.py
```

В библиотеке:

```python
from space_env.tasks.relay_campaign import relay_campaign

case = relay_campaign()  # двухчасовой профиль
configuration = case["configuration"]
public_contract = case["public_contract"]
public_brief = case["public_brief"]
```

`public_brief` явно сообщает SLA, ресурсные ограничения, необходимость дежурить
до конца горизонта и ёмкость общего наземного ресурса. Времена новых заявок и
восстановления станции остаются в привилегированной конфигурации.

Генератор сохраняет RL для всех вариантов и SFT основного двухчасового успешного
варианта. Каждый экспорт повторно проверяет native эпизод. Отдельно пересчитывается
каждое действие по публичному наблюдению. Сохранённый native-network журнал
аудируется по терминалам, скорости, bits-per-interval, receipts и DTN serialization.
Аудит архива не заменяет replay и не является независимой физической моделью.

## Физические и протокольные границы

Используются J2-орбиты, пакетные EOP, кинематическая ориентация, RC-тепло и
battery-only coupled bus. В отличие от базового long_campaign, здесь включены
sampled RF-бюджеты и packet/custody-модель. Параметры синтетические, адаптированы
из пакетного operator_relay fixture, без аппаратной калибровки.

Антенны заданы без узкого body-pattern, погода ясная. Модем — пороговая модель
Eb/N0 и объявленных кодовых режимов; waveform, интерференция, ITU rain и реальный
tracking loop не моделируются этим профилем. ACK — идеальный out-of-band канал
с объявленной вероятностью потери, не физическая обратная RF-линия.
Это не BPv7/BIBE/LTP или CCSDS wire-interoperability.

Сетевой grid по умолчанию 5 s; временные границы acquisition, фрагментов, ACK,
таймаутов и событий дополнительно дробят исполнение. Отдельный короткий вариант
с grid=1 s проверяет устойчивость результата, без универсальной оценки точности.

Выбор и переключение маршрутов добавлены отдельной постановкой: [ROUTING_CAMPAIGNS.md](ROUTING_CAMPAIGNS.md).
Следующие расширения: реальные антенны/наведение,
разделённые частичные наблюдения, более крупные группировки и независимые эталоны.

## Измеренный результат — 16 ноября 2026

Пройдены 159 локальных тестов. В семи эпизодах проверены public-policy trace,
export-time native replay и согласованность сохранённых сетевых журналов.
Двухчасовой сценарий четырёх аппаратов завершился за 59 решений с пятью
подтверждёнными заявками. Получены семь RL-строк и одна SFT-строка алгоритмической
публичной политики, без inference или тренировки модели.

В коротком одноканальном варианте зарегистрировано 2.5 секунды интервалов
избыточного спроса на терминал; одновременно выделялся только один grant,
суммарная скорость не превышала 250 kbit/s. Поздние 1000000 бит доставлены через
два подтверждённых custody-перехода. В варианте потери ACK выполнено шесть
повторов и принято 1500000 дублирующих битов, без дополнительных доставок клиенту.

Последний наземный ACK поздней волны пришёл через 17.926412 s после release
при одном терминале/250 kbit/s. Добавление только второго терминала сохранило
эту задержку. При двух терминалах и лимите 500 kbit/s одновременно работали
оба передатчика, ACK пришёл через 15.104169 s: примерно на 2.82 s раньше.
Это время доставки, а не конец кампании: endurance-горизонт оставался тем же.
В данной модели ground energy составила соответственно 382.23, 432.23 и 350 J;
Это native-счётчики инженерной модели, не измеренное потребление настоящей станции.

При TTL=0.001 s обе ISL-передачи истекли, наземная доставка поздней волны
составила ноль, а цель осталась проваленной. Native inventory/receiver/wire
балансы не нарушились. При переходе с сетевого grid=5 s к 1 s результат
сохранился; разница позднего ACK составила около 2.5 μs на этом коротком случае,
что не является общей оценкой точности сетевой модели.

Артефакты: `artifacts/relay-agent-campaign-20261116`. Сравнения аппаратных пулов
сохраняют ту же native-постановку кроме объявленных числа терминалов и aggregate
rate; аудит проверяет это отдельно.

Генератор, двухэтапный custody-путь и 240-секундная кампания также выполнены
из установленного wheel вне checkout. Совпали 383 Python/JSON-файла.
[Source-bound свидетельство](acceptance/RELAY_CAMPAIGNS_V1.json) связывает
исходники, окружение, тесты, записи, сетевые журналы и артефакты; прежние
свидетельства не перепривязывались к новым исходникам.
