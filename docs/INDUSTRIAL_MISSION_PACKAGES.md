# Три пакета операционных задач для AI

Состояние реализации: 11 ноября 2026 года. Новый модуль `space_env.industrial`
объединяет **контракт решений и данных**, но не объявляет три разных исполнителя
одной совместно квалифицированной физической системой. Пакеты имеют разные
области применимости. Все исходные native API и старые форматы данных сохранены.

## Пакет 1 — операционная автономность

`OperationsSession` исполняет EO → CPU → ISL → Ground через существующий
`TaskSession`, с настоящими native продуктами, ресурсами, custody и ACK.
Исходный профиль: два съёмочных аппарата, два шлюза, четыре неоднородные заявки,
горизонт 60 секунд. Не реализован новый дублирующий ledger продуктов.

Добавлены:

- Привилегированный драйвер причинных событий. Будущие отказы, отмены,
  изменения заявок и outages не передаются агенту вместе с конфигурацией.
- Настоящее добавление отложенной заявки через `request_added`: заявка и job
  отсутствуют в исходном native lifecycle. Геометрия цели и ограниченные
  шаблоны команд заранее подготовлены; это не генератор произвольных новых
  целей/команд в процессе полёта.
- Каталог агента содержит только собственные actor-команды и заявки,
  присутствующие в объединении текущих акторных наблюдений. Внутренние
  `@driver`-действия запрещены политике. Это один центральный агент с обменом
  текущими наблюдениями; стоимость распределённого обмена здесь не моделируется.
- Диагностика с затратой времени; отчёт ideal synthetic built-in test
  раскрывает текущие флаги неисправности только после выполнения проверки.
- Ограниченный reset радио/CPU и выход из safe mode. Reset выдерживает
  заданную задержку, затем выполняет native событие очистки; постоянный
  отказ сбросом не устраняется. Выход из safe mode проверяет native условия.
- Время диагностики, сброса и commit проходит через native исполнение:
  продукты, текущая обработка, орбиты, питание и тепло продолжают изменяться.
- Неуспешная команда агента не отменяет поступление внешнего события.

### Семантика времени и ограничений

Сетка — две секунды. Событие применяется отдельной native транзакцией и
занимает две секунды исполнения. При совпадающих временах события выполняются
последовательно в детерминированном порядке. Поэтому это **явная задержка
диспетчеризации**, а не модель мгновенных аппаратных interrupts. Фактические
времена и отклонения событий остаются в trainer-журнале. Начальное событие
может сдвинуть время первого наблюдения с 0 на 2 секунды.

`reset_sec=6` означает шесть секунд ожидания плюс две секунды commit;
внешние события могут дополнительно задержать управление. Отдельная аппаратная
энергия перезагрузки, реальные BIT, схемы резервирования и механизмы ремонта
не моделируются. Reset — объявленный идеальный наземный maintenance-сервис,
а не новая команда FSW и не промышленно откалиброванный FDIR.

Операционные счётчики и орбиты этого профиля остаются ideal-local.
Флаги причины скрыты от обычного наблюдения, но симптомы admission-mask могут
помогать диагностике. Это не доказательство реалистичности диагностики.

## Пакет 2 — относительная навигация и безопасность

`ProximitySession` — отдельный ограниченный профиль относительного движения
в вращающейся RTN-системе кругового chief. Использует существующую CW STM:

```text
x'' = 3 n² x + 2 n y'
y'' = -2 n x'
z'' = -n² z
state(t+h) = Phi(n,h) state(t)
```

Есть задачи удержания, позиционной инспекции и объявленного безопасного
отхода; импульсы ограничены разовым и общим delta-v. Abort фиксируется,
запрещает дальнейшую инспекцию и может включать немедленный импульс.
Успешный аварийный отход в задаче инспекции не превращается в успешную инспекцию.
Для отдельной задачи `mode="retreat"` отход является объявленной целью.

### Наблюдаемость

Агент получает оценку относительного шестимерного состояния и covariance,
а не истинную траекторию. Линейный фильтр использует зашумлённые синтетические
измерения положения, dropout и задержки. Пакет фиксируется на эпохе приобретения;
при позднем поступлении переигрывается фильтр от нужной эпохи с сохранёнными
управлениями. Точное относительное положение не подставляется вместо пропущенного
измерения. Process PSD — модель неопределённости фильтра; отдельные случайные
возмущения истинной динамики этим параметром не добавляются.

Это идеализированный relative-position sensor, не камера с pose estimation,
не лидарный point cloud и не clock/range-only навигация. Нет контактной
динамики, тормозной системы захвата или модели изображения поверхности.
Область начальных конфигураций и исполнения ограничена 1% радиуса chief;
малость расстояния не доказывает заданную точность CW на произвольной дуге.
Частота `n` задаётся явно; `n=0` разрешён как прямолинейный проверочный предел,
а не физическая земная круговая орбита.

### Проверка интервалов

`interval_separation` проверяет весь интервал, используя предоставленную
верхнюю границу скорости относительного движения `V`:

```text
min_distance_on_interval >= min(distance_left, distance_right) - V*h/2 - epsilon
```

Это следует из Lipschitz-свойства расстояния. Неопределённый интервал
делится пополам. Возвращаются три различных результата:

- `safe`: нижняя граница всех подынтервалов не меньше keepout;
- `unsafe`: найдена точка внутри keepout с учётом численного allowance;
- `indeterminate`: бюджета/разрешения недостаточно, безопасность не заявляется.

Для CW реализована аналитическая верхняя граница скорости из абсолютных
членов STM. Native-truth witness не передаётся политике. Любой unsafe или
indeterminate прекращает эпизод без присвоения статуса безопасного успеха.
Проверка условна относительно корректности модели, speed bound и численного
allowance. Это float-расчёт, не доказательство через интервальную арифметику
и не сертификация нелинейной GCRS-динамики. Keepout проверяется между отсчётами;
допуск инспекции/удержания оценивается на границах решений.

Публичная политика использует только estimate/covariance и краткий прогноз.
Запас в три sigma — эвристика, не доказанная вероятность безопасности в 3D.

## Пакет 3 — сервис группировки

`ServiceSession` моделирует целочисленные потоки данных через slotted
store-and-forward сеть:

- новые потоки появляются на объявленной границе; будущие flows/events скрыты;
- приоритеты, дедлайны, частичная доставка и отмены;
- custody и очереди на спутниках, ограничения памяти;
- общий лимит терминалов спутников и наземных станций;
- ёмкость направленного канала за слот, текущая доступность контакта;
- handover с явным выбором нового peer и задержкой;
- энергетический бюджет узлов и потребление активных терминалов;
- отказ/восстановление узла без исчезновения хранящихся на нём данных;
- активация резервного узла с задержкой commissioning;
- отдельные наземные receipts и точный баланс целочисленных битов.

Полученное в конце слота нельзя передать дальше в том же слоте. Один
transfer занимает по терминалу на обоих концах на весь слот; модель намеренно
не подразумевает незаявленное внутрислотовое мультиплексирование. Несколько
transfer используют дополнительные терминалы. Передача запрещена во время
handover. Даже нулевой handover budget требует отдельного решения без передачи
этим узлом в том же слоте. Слоты half-open; доставка точно на deadline засчитывается.
При отмене/истечении срока уже доставленные биты сохраняются, остатки списываются.
Отказ хранения не моделируется: fault блокирует сервис узла, сохраняя его очередь.

```text
released_bits = queued_bits + delivered_bits + discarded_bits
slot_energy = (idle_power + terminal_count * terminal_power) * slot_duration
```

Capacities и контакты задаются входными данными. Это не новый RF/waveform solver:
нет beam hopping, спектральных помех, BER/PER, TCP, вычисления орбитальной
видимости или обратной связи с native ADCS. Смена peer моделирует ресурсный
handover, не весь протокол пользовательского мобильного handover.
Commissioning здесь — доступность сервисного узла после задержки, **не физическое
развёртывание группировки по орбитальным позициям**. Такое развёртывание требует
дальнейшей связи с native манёврами. Поддержанные пределы 64 узла/256 links/512 flows
являются ограничениями входа, а не измеренной масштабируемостью всей физики.

## Единый агентный контракт

```python
from space_env.industrial import OperationsSession, ProximitySession, ServiceSession

session = ProximitySession({"measurement_latency_steps": 2})
transition = session.step(
    {"kind": "inspect"},
    expected_revision=0,
    idempotency_key="decision-0",
)
restored = ProximitySession.from_checkpoint(session.checkpoint())
```

Все три класса имеют `observe`, `step`, `metrics`, `checkpoint` и `from_checkpoint`.
Revision/idempotency защищают от повторного исполнения. Checkpoint содержит
привилегированную конфигурацию, source hashes, версии Python/зависимостей,
историю решений и hash конечного состояния. Восстановление заново исполняет
историю, а не доверяет флагам успеха. Не передавайте checkpoint агенту.

Для текстовых агентов:

```python
import json
from space_env.industrial.agent import IndustrialEpisode, verify_episode, export_training

session = ProximitySession()
episode = IndustrialEpisode(session, split="train", policy_origin="scripted_public")
for index in range(3):
    episode.call(str(index), json.dumps({
        "expected_revision": episode.observe()["revision"],
        "idempotency_key": str(index),
        "action": {"kind": "inspect"},
    }))
record = episode.record()
verify_episode(record)
export_training(record, "artifacts/new-inspection-sft.jsonl", format="sft")
```

Новый tool называется `space_env_industrial_step`. JSON Schema переносит
`$defs` на правильный корневой уровень. Неверные JSON/решения расходуют бюджет
вызовов; скрытые backend-сообщения об ошибках не возвращаются модели. Модель
не может повторно получить награду, переиспользуя idempotency key.

Экспорт — **одна episodic строка**, не PPO token advantages. SFT принимает
успешные train-эпизоды без ошибочных/отклонённых решений и с явным происхождением
политики. RL сохраняет также неуспехи. Test/development не экспортируются как
training. В training-строке только причинный диалог, награды и outcome labels;
исходная truth-конфигурация и checkpoints не включаются. Само объявление
`policy_origin="external_llm"` не доказывает реальный inference. Обучение и
улучшение модели этой реализацией не заявляются.

Gym bridge:

```python
from space_env.industrial.gym import IndustrialEnv

env = IndustrialEnv("proximity", {}, max_calls=64)
observation_json, info = env.reset(seed=7)
```

Action/observation — JSON text spaces. Это интерфейс для языковых агентов,
а не новый фиксированный числовой observation tensor. `step` принимает весь
JSON tool payload с revision/key/action. Произвольная строка из `action_space.sample`
обычно является невалидным решением и расходует call budget. В `info["trainer_only"]`
есть оценочные исходы: их нельзя включать в наблюдения политики. Seed меняет
случайность относительных измерений; у детерминированных операций/сети он
не создаёт новую физическую геометрию. Gym registry автоматически не расширяется.

## Локальная матрица и воспроизведение

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m space_env.industrial.study --output artifacts/new-industrial-study
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m space_env.industrial.study --audit artifacts/new-industrial-study
python -m pytest -q tests/test_industrial_*.py
```

Матрица фиксируется до исполнения: 5 operations, 6 proximity, 6 service
конфигураций × две публичные политики (`wait`, `public`) = 34 попытки.
Public — простые опубликованные эвристики, не доказанные оптимумы. Ошибки
инфраструктуры и отрицательные сценарии сохраняются в denominator. Audit
проверяет всю матрицу, исходники, конфигурации, replay действий и повторное
вычисление решений самой политики. `valid=true` означает целостность,
а не успешность всех миссий или отсутствие error-строк.

Конфигурации близки и публичны: это регрессионный набор. Alias, measurement seeds
и разные условия одной формации не дают независимый holdout. Результаты нельзя
объединять в соревнование с Basilisk/BSK-RL/Orekit без одинаковых задач и входов.

## Что остаётся до полной версии трёх направлений

1. Аппаратные модели FDIR: реальные telemetry channels, неоднозначные симптомы,
   резервные компоненты, собственная стоимость/надёжность recovery и calibration.
2. Нелинейная native относительная навигация с измерениями, covariance и
   непрерывными safety events; независимая проверка на внешнем движке.
3. Подключение service capacities к native RF/access, влиянию ориентации,
   энергетики и погоды; QoS-потоки, пользовательский handover и помехи.
4. Полное физическое развёртывание/пополнение группировки, длительные манёвры,
   проверка ошибки CW и переход между уровнями детализации.
5. Действительно разные геометрические семейства, открытые внешний datasets,
   измеренная масштабируемость и обучение SFT/RL с оценкой на независимом holdout.

Ни один из этих пунктов не закрывается одним общим JSON-интерфейсом.

## Проверка фильтра на статистическом ансамбле

Отдельный воспроизводимый пример:

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python examples/modeling/relative_filter_study.py --seeds 64 --output artifacts/new-relative-consistency.json
```

Начальное истинное состояние выбирается из объявленного Gaussian prior;
seed измерений отделён от seed начального состояния. Истинная модель —
детерминированная CW, process PSD фильтра для этой проверки равен нулю.
Проверяется конечный NEES по шестимерному состоянию и последний NIS по
трёхмерному измерению; сохраняются все попытки, в том числе ошибки.
Одинаковые truth seeds между профилями образуют парные случаи.

В прогоне 11 ноября 2026: по 64 полных попытки в каждом из трёх профилей.
Средние NEES: nominal 6.2214, latency 6.6773, dropout+latency 6.1603.
Заданный 95%-интервал среднего: [5.1813, 6.8779].
Средние NIS: 3.1822, 3.1755 и 3.0343 при интервале [2.4300, 3.6291].
Все шесть проверок попали в интервалы; 95% тесты по природе могут отвергаться
случайно. Это matched-model statistical consistency, не flight calibration,
не доказательство Gaussian ошибок реального датчика и не OOD-проверка.

Дополнительно проверены slotted service сети с 16/32/64 узлами и
60/124/252 потоками, по 32 решения в каждой. Это прямые объявленные каналы,
одна наземная станция с восемью терминалами, один повтор; не performance claim
для native орбит, RF или EO-группировки. Сохранение битов и replay проверяются.

Демонстрационный экспорт содержит по одному успешному train-эпизоду каждого
пакета и по одной строке SFT/RL для него. Эти примеры происходят от тех же
публичных регрессионных семейств, что study: **это проверка формата, а не
независимое разделение train/test**, не обучающий эксперимент и не измерение
улучшения LLM. Скриптовые политики явно помечены как `scripted_public`.

## Итоги локальной проверки окончательных исходников

Артефакты: `artifacts/industrial-packages-20261111/`.

- 250 целевых/регрессионных тестов прошли: 69 новых и 181 существующий тест
  динамических workspace/network операций, relative goals, навигации и planning.
  Это не полный прогон всего репозитория.
- Матрица: 34/34 попытки завершились без ошибок инфраструктуры и без невалидных
  tool-вызовов. Неуспех миссии учитывается отдельно от ошибки инфраструктуры.
- Operations: публичная эвристика выполнила все 4 заявки в 4/5 конфигурациях;
  wait — в 0/5. Добавление заявки, reset радио, CPU+новая заявка и outage
  проверены сквозным native исполнением. Постоянный отказ — 0 доставок:
  эвристика делает 14 maintenance-попыток и не умеет прекратить бесполезный
  recovery. Это сохранённый недостаток baseline, не доказанная невозможность
  миссии и не искусственное исключение трудного случая.
- Proximity: public завершила объявленную задачу в 5/6 случаях, wait — в 2/6.
  В оставшемся crossing-case public выполнила безопасный abort, но инспекция
  не засчитана; wait пересекла keepout. Простая задача с dropout=1 также
  решена из хорошего prior: она не доказывает необходимость измерений или
  сложность задачи для обученного агента.
- Service: public полностью выполнила исходные потоки в 2/6 случаях, wait —
  в 0/6. При постоянном отказе промежуточного узла резерв доставил срочный
  поток, а данные на отказавшем custodian остались заблокированы. При его
  восстановлении выполнены оба потока. Перегрузка, отмена и отказ при приёме
  сохранены. Строгий all-flows success включает исходный denominator;
  cancelled/expired/rejected и частичные доставленные биты даны отдельно.
- Эти бинарные критерии разных исполнителей нельзя суммировать в универсальный
  рейтинг качества симулятора. Оптимальность публичных политик не доказана.
- По одному успешному train-эпизоду каждого пакета экспортировано в SFT и RL:
  шесть episodic строк. Экспорт проверяет replay, но не выполняет обучение.
- Wheel 0.134.0: побайтно сопоставлены 363 Python/JSON файла, включая девять
  новых модулей. Из отдельного cwd через распакованный wheel выполнены по
  два шага каждого пакета и cold replay. Использованы имеющиеся зависимости;
  это smoke, не чистая установка и не полный installed-study.

Исходное установленное distribution metadata в рабочем окружении сообщает
0.24.0, тогда как `pyproject.toml` и собранный wheel — 0.134.0. Новые checkpoints
фиксируют фактические версии в своём окружении. Старые identities не мигрируются

## Native пример физического фазирования

```bash
python examples/modeling/deployment.py --actors 2 --output artifacts/new-phasing-2.json
python examples/modeling/deployment.py --actors 4 --output artifacts/new-phasing-4.json
python -m pytest -q tests/test_industrial_deployment.py
```

Пример строит от 2 до 8 аппаратов в разных начальных фазах одной плоскости.
Каждый выполняет конечное включение 2 Н на 20 секунд; направления чередуются
вдоль/против начальной скорости. На эпохе 60 секунд проверяются отдельные
GCRS position/velocity goals всех аппаратов и резерв топлива 9.98 кг.
Целевые состояния рассчитываются отдельной реализацией RK4 с шагом 0.005 с,
центральной гравитацией и аналитическим расходом массы. Native executor
использует свой solver. Допуски: 1 см по положению и 1e-5 м/с по скорости.
Это численное сравнение идеализированной модели с общими константами,
не точность знания реальной орбиты и не аппаратная калибровка.

Проверены полные варианты на 2 и 4 аппарата: reference завершает все цели,
wait их не выполняет. Четыре agent-эпизода прошли native replay.
Топливо каждого аппарата после включения составляет примерно 9.9864 кг.
Отдельный отрицательный тест меняет знак тяги одного аппарата: общий goal
не выполняется, хотя второй аппарат достигает своей цели.

Reference — привилегированный заранее составленный план, не результат
обученного агента. Орбиты наблюдаются идеально. Здесь explicit-resource
surrogate, без ADCS/энергетики реального двигателя, полного commissioning,
контроля непрерывного столкновения и многосуточного развёртывания группировки.
Физический phasing и slotted service остаются разными исполнителями;
перенос их состояния/ресурсов и синхронизация часов не фабрикуются.

### Установка и версии наблюдений

Для этих примеров нужны используемые native reference/coverage зависимости:

```bash
pip install -e '.[reference,coverage,dev]'
```

В industrial tool payload используется **верхнеуровневый** `revision` из
`episode.observe()`. Вложенные native actor views в OperationsSession содержат
собственный native revision; он не является номером решения внешнего драйвера.

Дополнительно прошли 5 тестов native phasing-примера: суммарно **255 различных
целевых тестов** в двух запусках. Текущая матрица и аудит находятся в
`qualified/` и `qualified-audit.json`; demonstration exports — в
`qualified-export-demo/`, статистика фильтра — в `qualified-filter-consistency.json`.
Предварительные development-прогоны не перепривязаны к новым source identities.
