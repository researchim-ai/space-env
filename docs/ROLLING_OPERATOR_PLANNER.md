# Сохраняемый rolling-планировщик оператора

Пульт и `MissionWorkspace.relay()` используют один causal route-aware baseline.
До этого подсказка создавала новую политику на каждом шаге: терялись сведения
о застрявших передачах и временно нежелательных направлениях. Теперь состояние
сохраняется на протяжении миссии, при архивировании и в SQLite.

## Что учитывается

- Текущие публичные наблюдения, видимые продукты, их остатки, ресурсы и контакты.
- Состояния видимых DTN-передач и направление source → destination.
- Временная задержка повторных попыток после неудачной передачи.
- Наблюдаемые ground ACK; освобождение подходящих завершивших доставку команд,
  только если соответствующая команда отмены объявлена в каталоге.
- Фактически исполненные команды и feedback, включая ручное управление.

Будущие окна, scenario truth, известный симулятору граф будущих отказов и пробные
native прогоны вариантов не передаются политике. Восстановление воспроизводит
только уже исполненный префикс, а не оценивает альтернативные будущие траектории.

У короткой relay-команды может не накопиться достаточно наблюдений для обычного
счётчика застоя. Поэтому новый наблюдаемый переход передачи в failed/cancelled/
expired с ненулевым остатком тоже временно откладывает направление. Один старый
отказ не продлевает задержку при каждом чтении. Успешный transfer/custody сам по
себе не объявляется наземной доставкой: требуется native ground ACK.

Это консервативная эвристика: неудачный исход может быть вызван длительностью
команды или ресурсами, а не неисправностью линии. Задержка может отложить полезный
маршрут. Политика не диагностирует физическую причину отказа и не гарантирует
оптимальность маршрута или выполнение всех дедлайнов.

## Общий цикл SDK и пульта

```python
from space_env.workspace import MissionWorkspace

mission = MissionWorkspace.relay()
mission.run(decisions=3)
state = mission.state()
print(state["rolling_planner"])
mission.run()
```

В пульте выберите «EO → CPU → ISL → Ground ACK», нажмите «Новая миссия», затем
«Прогон планировщика». Под командами показывается статус памяти политики.

Сервисная конфигурация: до 64 кандидатов и 256 узлов поиска за решение;
задержка повторной попытки — 4 decision epochs, не 4 секунды. Общий baseline
сохраняет свои публичные настройки отдельно; параметры сервиса фиксируются
в checkpoint и проверяются при восстановлении.

Рабочий EO-профиль с заранее составленным прогнозным расписанием продолжает
исполнять свой план. Rolling-политика активируется для общего causal fallback;
её состояние не подменяет расписание workspace и не расширяет область поддержки
динамического EO/ISL-планирования.

## Воспроизводимость и сохранение

`planner_state` — дополнительное поле operator snapshot/archive. Внутри находятся
checksum политики, параметры, счётчики, cooldown, revision и hash task-каталога.
Native task checkpoint, модельное время и revision от запроса подсказки не меняются.

Первая новая подсказка может сохранять служебную запись и увеличивать generation
SQLite-хранилища. Повтор того же запроса на том же входе не создаёт новую запись.
Generation хранилища не является revision симуляции. Межпроцессный CAS/fencing
сохраняется: устаревший writer должен заново получить handle.

Если после подсказки оператор выбрал другую команду, память политики записывает
реальный выбор. Отказ ручной команды не штрафует неисполненную подсказку. Если
подсказки пропускались, состояние всё равно обновляется при последующих шагах.
Повтор native idempotent step не учитывается как ещё один шаг политики.

При первой активации после ручного префикса выполняется bounded replay истории.
При восстановлении из SQLite/архива состояние сравнивается с детерминированным
пересчётом по native-префиксу. Простого перевычисления внешнего checksum после
подмены cooldown недостаточно: семантическая подмена отвергается.

Архив без `planner_state` структурно поддерживается: политика активируется
лениво. Это не автоматическая миграция физических checkpoint между разными
сборками: прежние ограничения source/build fingerprint остаются. Новые архивы
не обещают совместимость со старыми читателями.

Проверка подсказки не превращает baseline в квалифицированного SFT-учителя.
Native provenance остаётся `external`; восстановление памяти не меняет авторство
реально исполненных действий.

## Права агента

`GET /api/operator/sessions/{id}/suggest` требует capability центрального
оператора с правом записи. Agent, viewer, admin и роль аппарата получают 403.
Это закрывает доступ канала агента к прогнозному операторскому расписанию.

Агент по-прежнему получает свои наблюдения и исполняет собственные решения через
step или совместный раунд. При необходимости он может использовать чистый
`BaselinePolicy` на разрешённом `PlanningInput`; HTTP-подсказки оператора для
этого не нужны. Состояние политики не добавляется в наблюдения агента.

## Проверки

Новые тесты покрывают воспроизводимость после рестарта, реальный ручной feedback,
пропущенные подсказки, bootstrap, rollback при ошибке диска, старый архив,
семантическую подмену памяти, idempotency и ограничения каналов доступа.

В сценарии с недоступной линией a → b политика сначала выполняет попытку,
наблюдает её неуспех и выбирает hop-second-c. Она не получает таблицу outages
как planning input. В этом ограниченном сценарии одна из двух заявок остаётся
невыполненной: поздняя попытка передачи не подменяет отсутствующий ACK.
В штатном relay-сценарии native результат — 2/2 доставок.

Остаётся отдельной задачей общий оптимизатор назначения EO, многошаговых ISL
маршрутов и динамических событий. Этот блок укрепляет существующий общий цикл
исполнения и адаптации, не заявляя такой оптимизатор завершённым.

Объединённый локальный набор planning/rolling/operator/durable/workspace/fleet:
**189 passed**, один существующий loopback HTTP-тест исключён из sandbox-запуска.
В браузере штатная relay-миссия выполнена до 20 с: обе заявки имеют native
completed, память политики сохранена на revision 9. Ошибок консоли не было.
CI и удалённые кампании не добавлялись.
