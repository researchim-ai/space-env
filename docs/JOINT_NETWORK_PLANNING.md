# Совместный выбор исполнителя EO, ISL-пути и времени доставки

Новый ограниченный профиль объединяет выбор аппарата для съёмки, обработку на
нём, 0–3 направленных custody-перехода и наземный ACK. Все этапы исполняет
существующий native runtime; отдельной демонстрационной физики нет.

## Быстрый запуск

```python
from space_env.workspace import MissionWorkspace

mission = MissionWorkspace.network()
initial = mission.state()["network"]
print(initial["requests"][0]["plan"]["path"])
result = mission.run()["network"]
print(result["fulfilled"], "/", result["total"])
mission.export("/tmp/network-training.zip")
```

```bash
python -m examples.network.run
python -m examples.network.run --configuration mission.json --output /tmp/new-network-mission
python -m examples.network.recovery
```

Пример создаёт три аппарата и одну заявку. Только первый видит точку съёмки;
наземная станция доступна третьему. Выбирается
`fleet-00 → fleet-01 → fleet-02 → Ground` — два реальных DTN-перехода, а не
декоративная линия. Начальные бортовые продукты отсутствуют. Raw 1 Мбит и final
0,5 Мбит получаются съёмкой и обработкой. Доставка подтверждается ground ACK.

В пульте нажмите «EO / ISL / Ground», проверьте отдельный JSON-редактор и
«Построить совместный EO/ISL-план». Затем запустите план на той же странице.
Обычная форма EO и сетевой JSON создают самостоятельные профили; изменение
одной формы не меняет уже исполняемую миссию.

## Конфигурация и API

`NetworkConfiguration` содержит:

- `mission`: существующая `MissionConfiguration` с орбитами, станциями и заявками;
- `links`: направленные source/destination, max_range_m и известные outages;
- `max_hops`: 0–3 ISL-перехода; 0 разрешает только прямую доставку;
- `max_search_nodes`: 1–500000, по умолчанию 50000;
- `radio_rate_bps`: 10000–1000000 бит/с, по умолчанию 250000.

`actor_id: null` разрешает выбор исполнителя; явный actor фиксирует его.
`station: null` разрешает выбор станции; явная station остаётся назначенной.
Окончательные actor/station вносятся в native request до начала исполнения.
Промежуточный владелец продукта меняется только через native custody ACK.

Лимиты профиля: 1–4 аппарата, до 16 заявок и 4 станций, до 12 направленных
ISL-связей, горизонт 60–1200 с, до 240 решений. Шаг 1–30 с должен делиться
на 0,5 с и укладываться в ограничения обычной MissionConfiguration.
Акторы и станции имеют разные ID; дубликаты и неизвестные endpoints запрещены.

HTTP:

- `GET /api/operator/network/preset` — стартовая конфигурация;
- `POST /api/operator/network` — построение плана и создание operator-сессии;
- стандартные step/suggest/checkpoint/archive/export — дальнейшее исполнение.

`state.network` доступен центральному оператору и его наблюдателю. В нём
разделены planned и fulfilled, показаны выбранные пути, стадии, причины отказа
планирования и исчерпание бюджета. Роли аппаратов и канал агента не получают
forecast/расписание; операторская подсказка требует отдельной capability.

## Что делает поиск

1. Геометрический scaffold с минимальными размерами продуктов создаётся только
   для расчёта известных траекторий/окон. Он никогда не исполняется как миссия.
2. Для каждого возможного owner собираются окна съёмки. Для ISL и Ground
   вычисляются sampled RF-условия на сетке 0,5 с; будущие native исходы не проигрываются.
3. Для каждой заявки рассматриваются owner, station, простые пути без циклов и
   размещение стадий по времени. Заявки пакуются по убыванию приоритета, затем
   дедлайну/ID. Среди найденных вариантов выбирается раннее завершение, затем
   меньшее число переходов и детерминированный порядок узлов.
4. Общий бюджет учитывает поиск путей, стартов и слотов. Сохраняются только
   полностью найденные цепочки. Исчерпание бюджета не считается успехом:
   незапланированные заявки остаются в полном знаменателе.
5. Выбранная конфигурация компилируется с настоящими размерами raw/final и
   направленными DTN-связями. Для наведения материализуется выбранная поза.
   Native выполнение, а не план, определяет фактический результат.

Это bounded serial joint owner/path/time packing, не глобальный оптимум всех
порядков и маршрутов. При маленьком бюджете допустимый вариант может не попасть
в поиск; прогноз 0/1 не доказывает математическую невыполнимость миссии.

## Ресурсы и временные бюджеты

Одновременная занятость запрещается для аппарата; ISL занимает и передатчик,
и приёмный аппарат на весь консервативный интервал. Наземные терминалы учитываются
общим календарём станции. Память резервируется консервативной суммой продуктов
по всей миссии, включая промежуточных владельцев; это может отсеять допустимый
временной packing, но не предполагает исчезновение хранимых данных.

Энергия учитывает базовое потребление на весь горизонт, стадии slew/EO/CPU,
передачу и работу приёмника с discharge efficiency. Сохраняется 20% батареи;
будущая солнечная генерация не зачисляется как гарантированный ресурс.

Стадии округляются вверх к шагу q. CPU-бюджет включает работу, обмен raw/final
через память 100 Мбит/с и запас lifecycle-обработки. Для F фрагментов применяется
консервативный бюджет ISL:

`ceil_q(bits/R + F × (2×10⁷/c + 0.06 + 4×0.5))`.

Здесь 10⁷ м — верхняя граница разрешённой дальности, 0,06 с — acquisition и
ACK processing, 0,5 с — RF/DTN-сэмплирование. Для ground добавляются ACK processing
0,05 с, propagation bound и два sample-интервала. TTL каждого hop привязан к
дедлайну; первый custody TTL не обновляется в бесконечность на следующем hop.
Выход продукта из передатчика не подменяет custody или наземный ACK.

RF-ячейка разрешается только при достаточной скорости во всех её sample-точках.
Ячейка Ground должна целиком лежать в одном геометрическом/доступном окне.
Любое пересечение ISL-ячейки с объявленным outage запрещает её, даже если outage
короче sample-интервала. Предположения остаются условными на физический профиль.

## Область физических предположений

- J2/gravity-only орбиты и существующие EOP/frames, без манёвров во время плана.
- Кинематическое наведение; metadata acquisition и metadata CPU-продукты.
- Синтетический S-band: 2,2 GHz, 1 W RF, номинальные 6 dBi и G/T=0 dB/K,
  один modem mode; идеальное согласованное наведение без BODY-диаграммы.
- Нет случайного fading, packet/ACK loss и неизвестных будущих отказов.
  Дальность, Earth occultation, Doppler, RF margin и объявленные outages учитываются.
- Native stop-and-wait fragments, задержки, RX-питание, memory/custody и ground ACK
  сохраняются. Это инженерный DTN-моделер, не wire-совместимая реализация BPv7/LTP.

Прогноз использует те же известные физические формулы и входы, что runtime.
Он не является независимым подтверждением физической точности. Ни аппаратная
калибровка, ни научное качество изображения, ни robust-выполнимость при случайных
потерях этим профилем не заявляются.

## Восстановление, данные и следующие границы

План и конфигурация связаны checksum с native definition и каталогом команд.
Они сохраняются в checkpoint/SQLite/архиве. Неисполненные вручную изменения
не теряются: реальное отклонение от action/dt префикса блокирует старую подсказку.
Можно продолжить вручную или создать новую миссию; незаметного сброса состояния нет.

Профиль поддерживает начальный план и `MissionWorkspace.evolve()` — независимое
продолжение из фактического состояния. POST `/api/operator/sessions/{id}/evolve`
использует тот же контракт, что обычный workspace. В сетевом блоке пульта есть
редактор событий и кнопка продолжения.

```python
mission.run(decisions=22)  # в примере продукт уже принадлежит fleet-01
branch = mission.evolve("Продолжить доставку", idempotency_key="custody-recovery")
print(branch.state()["network"]["dynamic"]["states"])
result = branch.run()
```

`examples.network.recovery` воспроизводит отдельный синтетический случай:
продукт у fleet-01, отказ радио fleet-02, новый путь через fleet-03, native ACK
и неизменность checkpoint источника. Это проверка механизма на одном сценарии,
не сравнительный benchmark и не доказательство преимущества над другими системами.

Продолжение воспроизводит только исполненный префикс, проверяет полный physical
report, прерывает активные команды штатным cancel_actor и применяет native-события.
Для прерывания нужен один шаг q, для пакета событий ещё один q. События не могут
задним числом начинать outage: start_sec задаётся не раньше момента события.
Новая ветка получает собственные capabilities; источник не меняется. Повтор
одного idempotency_key возвращает ту же активную ветку, другое тело с тем же ключом
отклоняется. Контроль revision/epoch и права центрального оператора обязательны.

Поддержаны отмены, приоритеты, дедлайны, отказы/восстановление станций,
подсистем и safe mode. До четырёх новых заявок за изменение, до восьми событий
включая additions; суммарно сохраняются лимиты 16 заявок/240 решений. Новые заявки
требуют уже объявленной точки, явного аппарата и станции, release не раньше
применения события. Геометрия, аппаратура и набор ISL-связей не меняются.

Восстановление различает fresh/raw/final/completed/terminal/blocked. Готовый final
ищется у реального владельца после custody ACK. Raw продолжает оставшуюся работу
того же CPU job; завершённые съёмки не повторяются. Память уже находящихся на
борту продуктов входит в резервирование, энергия берётся из текущей батареи.
Остаток наземной передачи сохраняется native-моделью; частично переданный на
Землю продукт нельзя отправить по ISL, который требует целого продукта.

**Отмена ISL не является сохранением прогресса фрагмента.** Native-модель может
отбросить полученные незавершённые фрагменты; их затраты и discard-счётчики
остаются в истории. Целый продукт остаётся у подтверждённого владельца, если
custody ещё не завершилась. Незавершённый/pinned переход не выдаётся за доступную
копию на приёмнике: заявка блокируется, если после шага отмены остаётся unsettled
custody. TTL bundle не продлевается повторным планированием или увеличением дедлайна
заявки: residual forecast ограничивается уже существующим временем expiry.

Поиск остаётся bounded serial packing: fresh-заявки в продолжении используют
уже закреплённого native исполнителя и destination. Миграция вычислений,
переназначение получателя, изменение ISL-топологии, сохранение частичных ISL
фрагментов между отменёнными командами и масштаб большой группировки не заявлены.

Экспорт использует существующий VerifiedEpisode/роль-aware RL/SFT. В строках
наблюдений нет network_workspace/forecast. Выбор планировщиком не делает эпизод
экспертным учителем; в корпусе сохраняются реальные отказы и общий знаменатель.
Варианты одной геометрии следует держать в одной lineage-группе.

```bash
python -m pytest tests/test_joint_network.py tests/test_network_dynamic.py -q
```

Локальная проверка этого пакета: 102 passed в общем наборе; после финальных
уточнений TTL и нормализации — 35 passed в пересекающемся целевом наборе.
Один loopback HTTP-тест исключён из sandbox-набора; фактический браузерный
запуск отдельно подтвердил применение отказа, новый маршрут и native ACK 1/1.
Количество тестов не является оценкой физической точности.

## Численные проверки и измерение масштаба

Требуется установка с reference-зависимостями: `pip install -e '.[reference]'`.
Пакет выполняется локально по явному запуску, без CI и сетевых сервисов:

```bash
python -m space_env.validation.network_evidence --output /tmp/new-network-evidence --repeats 2 --external-forces
python -m space_env.validation.network_evidence --audit /tmp/new-network-evidence
python -m pytest tests/test_network_evidence.py tests/test_profile_evidence.py tests/test_joint_network.py -q
```

Каталог output должен быть новым. `repeats` — 1–3; timeout каждого отдельного
процесса — 1–600 с, по умолчанию 120 с. Каждая строка результата сохраняется
сразу после завершения процесса. Таймаут, ошибка запуска или некорректный ответ
остаются отдельной строкой с полным числом заявок и неизвестным, а не нулевым,
фактическим результатом. Частичный каталог после прерывания не выдаётся за
законченный пакет: итоговый report появляется только в конце.

### Независимость RF-проверки

`rf_evidence()` отдельно рассчитывает линейную мощность и спектральную плотность:

`L = (λ / (4πd))²`, `C/N₀ = EIRP × L × (G/T) / k`,
`margin = 10 log₁₀((C/N₀) / R / 10^((Eb/N₀_req + loss)/10))`.

Этот расчёт не вызывает production helpers для ожидаемых значений. Входы,
SI-константы и физические уравнения общие: это независимая реализация вычисления,
а не независимая измерительная истина. Сравниваются FSPL, C/N₀, margins,
eligibility и выбранный modem mode. 16 случаев включают S/X/Ka частоты,
500–10000 км, порог ±0,01 dB, полосу, спектральные границы, доплер, rate cap и
потери. Допуск точного линейного сравнения — 1e-10 dB. Дополнительное сравнение
с округлённой GHz/km формой ITU использует 0,02 dB именно из-за округления.
Это не точность реального RF-канала.

Источники уравнения свободного пространства:
[ITU-R P.525](https://www.itu.int/rec/R-REC-P.525-5-202411-I/en),
[ITU-R RA.2510, формула GHz/km](https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-RA.2510-2022-PDF-E.pdf).
Диаграмма антенны, атмосфера, waveform, сопровождение и временная дискретизация
контактов этой проверкой не подтверждаются. Тест с намеренно искажённым C/N₀
должен проваливать проверку — совпадение не подставляется из production output.

### Аналитика и внешний расчёт сил

Существующие девять аналитических случаев сохраняются отдельным файлом:
Kepler-решения, постоянная тяга/расход массы и изолированный тепловой баланс.
Флаг `--external-forces` добавляет отдельные формулы Boinor для J2/drag/third-body
и 600-секундную J2-дугу с LSODA против production DOP853. Frame/EOP, плотность,
эфемериды и константы здесь общие и перечислены в отчёте. Это сравнение формул
и интегрирования при заданных входах, не погрешность эксплуатационной орбиты.
Ошибка/отсутствие optional comparison сохраняются как неуспешный результат.

### Что измеряется в сетевом профиле

Фиксированы четыре workload: 1 аппарат/1 заявка, 2/4, 4/16 и четыре аппарата
с отказом приёмника после первого custody-перехода. Первые три — плотная группа
на одной орбите, одна точка наблюдения, общий терминал, разные приоритеты.
Это синтетическая ресурсная нагрузка, не выборка разных промышленных миссий.
Повторы одного входа не становятся независимыми геометриями или ML holdout.

Восемь свежих процессов в сохранённом запуске дали соответственно 1/1, 2/4,
4/16 и 1/1 — по два повтора. Невыполненные заявки не отброшены. Исчерпания
бюджета поиска не было. Пределы профиля не расширены за 4 аппарата/16 заявок.
Успех пакета означает завершение проверок/измерений, а не 100% обслуживания.

Сохраняются время построения и восстановления плана, p50/p95/max SDK-шагов,
RSS, размер/время checkpoint, native fulfilment, прогноз и узлы поиска.
SDK-шаг включает операторскую проекцию и обработку состояния, это не скорость
голого интегратора. `elapsed_sec` начинается после импорта модуля/SDK; старт и
завершение интерпретатора не включены. Измерения зависят от host и его нагрузки,
не задают SLA; малое число повторов не даёт устойчивой оценки хвостов.

На Linux RSS берётся из `/proc/self/status:VmHWM`, то есть пика address space
текущего executable после exec. `ru_maxrss` способен наследовать пик родителя:
его использование давало одинаковые завышенные значения во всех строках.
На других POSIX-платформах fallback getrusage явно маркирован как потенциально
включающий pre-exec peak. Ограничение памяти ОС не устанавливается.
Число BLAS/OpenMP threads фиксировано в каждом worker и записано в environment.

### Связность доказательств и открытые границы

Inputs, RF, аналитика, внешний расчёт и все строки связаны checksum. Parent
проверяет входной и source SHA worker, численные измерения и полный знаменатель.
`--audit` проверяет сохранённые файлы, отсутствие пропущенных/дублирующихся строк,
итоговые флаги и совпадение текущих исходников. Он не исполняет native replay
и не доказывает физическую истинность данных. Checksum не является подписью
независимого эксперта. После изменения кода старый receipt остаётся историческим.

Маленький [receipt конкретного запуска](acceptance/NETWORK_PROFILE_EVIDENCE_V1.json)
содержит полные входы, исходные hashes и измерения. Большие временные каталоги
не добавляются в репозиторий. Для воспроизведения запускайте команду выше:
времена и итоговые hashes нового отчёта закономерно будут другими.

Локальный целевой набор: **41 passed**. Остаются независимые mission-level
геометрии/наблюдения, аппаратная калибровка, большие группировки, сопоставление
с конкурентами и проверка обучения/переноса политики. Маленькая численная
ошибка общего уравнения не закрывает эти задачи.


## Обучаемый диспетчер и разделённые геометрические группы

Следующий локальный пакет сравнивает **начальное планирование** при одинаковом
прогнозе. Он использует существующий native runtime и новый необязательный
`MissionWorkspace.network(configuration, request_order=[...])`. Порядок обязан
содержать все заявки ровно один раз; исключение трудной заявки из знаменателя
запрещено. Лимиты поиска и остальные правила упаковки стадий одинаковы.
По умолчанию порядок остаётся приоритетным; HTTP-контракт конфигурации не меняется.

```bash

python -m space_env.planning.network_benchmark --audit /tmp/new-network-learning
python -m pytest tests/test_network_benchmark.py tests/test_joint_network.py tests/test_network_evidence.py -q
```

### Входы и ML-разделение

В коде зафиксированы шесть геометрий: экваториальная и наклонения 20°, 35°,
75°, 55°, 98°, разные радиусы, RAAN, фазы, WGS84-цели и станции. Координаты
заданы литералами; builder не вызывает прогноз или native-исполнение, не ищет
удачную точку под спутником и не отбирает сценарии по полученному результату.
Это авторские синтетические входы, а не независимая промышленная выборка.
Состав бизнес-заявок одинаков между геометриями: этот набор проверяет перенос
между орбитами/контактами, но не перенос на новое распределение приоритетов,
размеров продуктов или типов услуг. Для этого нужен отдельный frozen-набор.

Train: экваториальная и 20°; development: 35° и 75°; test: 55° и 98°.
Каждая группа содержит обычный сценарий и известный заранее outage станции
100–140 с. Итого 12 случаев, по три заявки с разными приоритетами, дедлайнами,
объёмами raw/final и CPU-стоимостью. Все вариации одной геометрии остаются в одном
разделе. Геометрический hash не зависит от названия, seed и ID станций/плоскостей;
изменение имени не создаёт новый holdout. Группы нельзя переносить через split.
Также нормализуются перестановки аппаратов/плоскостей, полный оборот RAAN,
избыточные RAAN/фазы круговых экваториальных орбит, эквивалентная запись epoch
и долготы ±180°. Это защита от известных алиасов, а не доказательство
статистической независимости близких геометрий.
Похожие/коррелированные реальные миссии требуют ещё более консервативной lineage.

### Что именно обучается

Три правила задают порядок заявок: priority, earliest_deadline, value_per_bit.
Для каждого train-случая выполняются все три native-прогона. Reward равен сумме
приоритетов фактически completed заявок, делённой на сумму приоритетов всех
заявок. Отсутствие Ground ACK не считается доставкой. Неуспешный worker оставляет
неизвестный исход; он не превращается в искусственную нулевую метку обучения.
При неполной train-матрице модель не обучается, а её строки оценки остаются
ошибками с полным знаменателем.

Из train-таблицы обучается линейный softmax-диспетчер: контекст из шести признаков
выбирает одно из трёх правил. Признаки — bias, разброс приоритетов, средний slack,
средний output, доли доступных контактов и съёмок. Оптимизируется ожидаемый reward
по полной train-таблице: 600 gradient steps с фиксированным learning rate 0,2.
Нормализации или подбора параметров по test-исходам нет. Модель сохраняет веса,
seed, список train-случаев и hashes точных входов/строк обучения.

**Это full-information contextual bandit, а не command-level RL.** Он не управляет
непосредственно приводами, не учится online-реакции на неизвестный отказ и не
доказывает качество PPO/MARL/LLM. Native-прогоны train служат payoff-таблицей,
а не экспертными SFT-демонстрациями. Expert teacher qualification остаётся false.
Три seed означают три инициализации оптимизатора на одной train-таблице, а не
три независимо собранных корпуса.

### Равная информация, исполнение и отчёт

Все методы получают один и тот же sealed forecast конкретного случая. Один
scheduler использует одинаковые max_search_nodes/max_hops; методы отличаются
порядком заявок. Прогноз содержит известные будущие окна и объявленные outages,
поэтому сравнение относится к привилегированному forecast-planning, а не к
частично наблюдаемому агенту без будущего. Native future не исполняется внутри
оптимизатора. После обучения веса заморожены; только затем исполняются
результаты development/test. Выбор лучшего seed по test не производится.

Каждая оценка выполняется в отдельном процессе. 12 случаев × (3 правила +
3 learned seed) дают 72 строки, но только шесть геометрических групп и две
test-группы. Полные знаменатели, таймауты и ошибки сохраняются. Для неизвестных
исходов агрегат показывает нижнюю/верхнюю границы reward, а не среднее по одним
удачным запускам. Отдельно показывается парная разница по test-группам; bootstrap
при двух группах только описательный, он не устанавливает статистическое
превосходство. Флаг superiority_established остаётся false.

Число узлов, время SDK/scheduler и RSS относятся к worker-процессу. Время
внешнего выбора правила и старта интерпретатора в эти метрики не включено.
Для оценки стоимости обучения необходимо учитывать исходные 12 train-rollout,
а не только дешёвую оптимизацию softmax-весов.

`--audit` проверяет файлы, полную матрицу case/policy, общий forecast, исходники,
native-счётчики и воспроизводит обучение из **только train** строк. Для каждого
learned результата проверяется выбранное моделью правило. Это проверка связности
и воспроизводимости оптимизатора без нового native replay; checksum не является
подписью внешнего эксперта. Аудит требует совпадающих исходников этого пакета.

Не закрыты: случайные/неизвестные online-отказы, большие и внешние holdout-наборы,
сильные оптимизационные baseline с сертификатами, command-level RL/MARL,
оценка sim-to-real и аппаратная калибровка. Наличие обученной модели само по себе
не означает улучшение над лучшим правилом: это должен показать сохранённый отчёт.

### Дискретная оптимизационная модель

`MissionWorkspace.network(config, planning_method="exact_small")` использует
глобальный выбор цепочек. Пределы: свежая начальная миссия, до 6 заявок/48 ячеек,
до 4 аппаратов, простые ISL-пути до заданного max_hops. Для остаточных состояний
используется `evolve()` с явно отмеченным serial_recovery, а не заявление об
оптимальном динамическом продолжении. request_order нельзя смешивать с exact_small.

Для заявки r перечисляются допустимые кандидаты k: владелец, время непрерывного
slew→imaging→CPU-префикса, путь и времена передач. Между транспортными стадиями
разрешено ожидание. Продолжительность Ground зависит от его start cell и
консервативного бюджета повторного захвата антенной. В кандидате проверяются
release/deadline, capture, целые контактные интервалы, память и энергия.

Бинарные x[r,k] выбираются при ограничениях:

- Σ[k] x[r,k] ≤ 1 для каждой заявки;
- Σ[r,k: uses(a,t)] x[r,k] ≤ 1 для каждого аппарата/ячейки, включая ISL RX;
- Σ[r,k: ground(s,t)] x[r,k] ≤ terminals[s];
- Σ[r,k] memory[r,k,a] × x[r,k] ≤ memory[a];
- Σ[r,k] energy[r,k,a] × x[r,k] ≤ usable_energy[a].

Память резервируется консервативной суммой на весь горизонт, без зачёта её
будущего освобождения. Энергия не получает гарантированного кредита от Солнца.
Цель — максимальная сумма приоритетов, затем число доставок. Кодирует её
целое `score = priority_sum × (N+1) + fulfilled_count`.

Solver — детерминированные перечисление кандидатов и branch-and-bound с
допустимым incumbent. Общий max_nodes 1–500000 (в наборе 50000), до 8192
кандидатов по умолчанию; половина node-бюджета (минимум один work unit) выделяется перечислению.
Счётчики измеряют алгоритмические work units, а не одинаковое число FLOPs или
равное CPU-время у разных методов. Все worker имеют timeout 120 с; время и RSS
сохраняются отдельно. При исчерпании бюджета сохраняется достижимый план,
полный знаменатель и верхняя граница; незавершённый поиск не выдаётся за оптимум.

`optimal=true` означает закрытую границу этой модели: завершены перечисление и
поиск либо feasible incumbent достиг суммы приоритетов/числа всех заявок.
Иначе верхняя граница может оставаться грубой суммой всех весов. Она **не является
верхней границей произвольной непрерывной native-миссии**: ранняя подготовка
ориентации, переиспользование памяти, параллельные подсистемы и более точное
управление наземными терминалами могут выходить за ограничения этой модели.
`verify_exact_schedule()` проверяет binding и ресурсы плана; сам по себе этот
admission не подтверждает глобальную границу. Audit повторяет forecast-поиск,
а отдельный unit-case сверяется с независимым полным перебором 196 комбинаций.
Ни один из этих механизмов не исполняет native future внутри поиска.

### Исправление бюджета захвата наземной антенной

Новая нагрузка выявила пропуск в старом прогнозе: RF backend сохраняет направление
антенны и тратит время на повторный захват, а план выделял только передачу/ACK.
В конкретном trace разворот занял 2,70015658 с; из 600000 бит осталось около
25039 бит. Команда завершилась, но заявка истекла без полной доставки.
Критерий результата не менялся: завершённая команда не подменяет Ground ACK.

Исправлена длительность в forecast, **аппаратура и native-механика не менялись**.
Для start cell берётся максимум углового перемещения от возможных ранее
использованных направлений на этой станции, включая фактически сохранённые
pointing при восстановлении. Направления выражены в одной ENU-системе. Для
межсэмплового зазора 0,5 с добавляется `Δθ = v_bound / range_floor × 0.5`:
12 км/с и 300 км дают примерно 1,15°. Sample-guard проверяет range с запасом
6000 м и скорость с acceleration guard 12 м/с²; вне области метод отклоняет
прогноз вместо экстраполяции. Это условный gravity-only LEO envelope, не
измеренная неопределённость реальной антенны.

Бюджет Ground — округлённые вверх к q передача, ACK/propagation/sample-запас,
acquisition и Δθ/slew_rate. На весь интервал резервируются аппарат и терминал;
энергия учитывается консервативно. В самый ранний допустимый момент первой передачи, когда прошлого направления
нет и предыдущая передача ещё невозможна, учитывается только acquisition. Для
более позднего первого использования конкретного терминала envelope может
закладывать повторный захват даже при отсутствии предшественника в выбранном
плане. Envelope допускает
невозможные на практике предшествующие последовательности ради консервативности:
это может отсеять хороший план. Sequence-aware antenna scheduling остаётся
отдельным улучшением. RF sampling, отсутствие случайных потерь, metadata payload
и отсутствие аппаратной калибровки сохраняют прежние ограничения профиля.

## Ограниченный поиск и селектор второго поколения

Новый `optimize_network(..., pruning=True)` сохраняет прежние ограничения и
лимит 50000 work units. Безопасные отсечения используют остаточную ёмкость,
обязательные пересечения actor/station cells всех ещё допустимых кандидатов,
доминирование одинаковых ресурсных состояний и симметрию аппаратов. Симметрия
разрешена только после полного перечисления прямых цепочек с одинаковыми
ресурсными параметрами и множествами возможностей; для ISL и неполного
перечисления классы одноэлементные. Ключ энергии точный (`float.hex`), после
возврата из ветки восстанавливается исходное значение без накопления ошибок
вычитания. Кэши ограничены 16384/4096 состояниями и node budget. Переключатель
`pruning=False` предназначен для сопоставления алгоритмов на одном forecast.
`verify_exact_schedule` по-прежнему проверяет допустимость, а не независимо
доказывает верхнюю границу.

`network_selector.fit_regret_selector()` — отдельная версия модели `/2`.
Нормализация оценивается только на train; bias сохраняется, постоянные признаки
имеют scale=1, значения ограничиваются ±8. Цели — равномерное распределение
между стратегиями с максимальной train native reward. Это классификация лучшего
правила, не оптимизация непрерывных команд и не обучение RL. Для неодинаковых
размеров проигрыша классификационная ошибка и ценностный regret различаются.
Используются фиксированные full-batch softmax cross-entropy, L2=0,01,
learning rate=0,2, максимум 2000 итераций. Критерий остановки — норма градиента
≤1e-6; факт сходимости, loss и train regret записываются отдельно. Даже
сходимость этой функции не доказывает обобщение или оптимальность миссии.

## Последовательности наземных сеансов: безопасное сокращение резервов

```python
from space_env.workspace import MissionWorkspace

mission = MissionWorkspace.network(configuration, planning_method="sequence_compact")
print(mission.state()["network"]["terminal_sequence"])
result = mission.run()
mission.close()
```

Это отдельный opt-in проход над `exact_small`: сначала выбираются допустимые
цепочки в прежней консервативной модели. Затем сохраняются заявки, маршруты,
все времена старта и EO/CPU/ISL-стадии; сокращаются только длительности Ground
и соответствующий консервативный расход энергии. Высвобожденные интервалы не
заполняются дополнительными заявками. `serial` и `exact_small` не заменены.
Область остаётся fresh initial mission, ≤6 заявок, ≤48 ячеек, ≤4 аппаратов.

Для станции с одним терминалом предшественник однозначен. Реальное освобождение
может произойти раньше конца резерва, поэтому берётся **весь** интервал
предыдущего сеанса `[start, reserved_end]`, а не направление на его конце.
Из известных эфемерид собираются единичные направления `u(t)` через 0,5 с.
Верхняя оценка поворота к следующему сеансу:

`theta = min(180°, max acos(u_previous · u_next) + 2 * degrees(12000/300000 * 0.5))`.

Новое направление также охватывает начало и следующий RF sample. Двойной
угловой guard покрывает два межсэмпловых зазора при прежних range/speed guards
(≥300 км, ≤12 км/с, gravity-only LEO); collection сначала повторно проверяет
совпадение исходного forecast и применимость envelope. Время setup — acquisition
плюс theta/slew_rate. Для первого использования чистого терминала разворота нет.
Используется минимум старой и новой допустимых верхних оценок; pass никогда не
расширяет резерв. Длительность — округление вверх `(ground_seconds + setup)/q`
с сохранением минимального `ground_cells` и прежнего ACK/sample запаса.

Это расчёт номинальной последовательности с успешным завершением предыдущих
сеансов. Неожиданный отказ, пропуск сеанса или изменение команд требуют
перепланирования из фактического состояния; initial certificate не является
гарантией исполнения после таких изменений. `evolve()` сохраняет существующий
`serial_recovery`, а не объявляет динамическое восстановление точным поиском.

Для станции с несколькими терминалами native-контроллер сам выбирает свободный
физический терминал. Пока его нельзя гарантированно закрепить за планом,
сохраняется старый envelope: `terminal=None`, `mode=conservative_unpinned`.
Назначение виртуальных terminal IDs не выдаётся за аппаратное управление.

Сохраняются исходный план и sealed terminal geometry; новый план содержит
resource witness на отдельном effective forecast, hashes происхождения,
предшественников, before/after cells и сумму освобождённого резерва.
`verify_terminal_schedule()` воспроизводит весь проход и отдельно допускает
resource witness. Старый bound узкой модели не переносится в более широкую:
остаётся только тривиальная сумма весов всех заявок. Поле
`global_sequence_optimality_established=false`; SDK `optimization=None` для
этого режима. Это не глобальный sequence-aware optimizer и не доказательство
прироста числа доставок.

Явное локальное парное сравнение:

```bash
python examples/network/compare_terminal_sequence.py --output /tmp/new-terminal-comparison
```

Два режима используют одинаковые mission inputs и sealed forecast; каждый
исполняется в свежем процессе. Сохраняются также ошибки, таймауты, native reward
и все знаменатели. Сокращение **резерва** не подменяет сокращение измеренного
setup time, wall time или рост пропускной способности миссии.

## LLM-агенты: диалоги, SFT, RL и benchmark

Основной продукт — воспроизводимые взаимодействия LLM-агента с космической
миссией и проверяемые данные для его обучения. Числовой Gymnasium/RL API остаётся
одним из интерфейсов. Новый слой `space_env.llm` использует существующий
`TaskSession` и его native executor; отдельная упрощённая физика для LLM не вводится.

### Инструменты и граница наблюдений

`LLMEpisode(session, task_text=..., group=..., split="train", max_calls=256)`
владеет cold-replayed копией сессии. Агент получает разговор `messages` и
JSON schemas `tool_schemas()`, вызывает `space_env_actor_observe` либо
`space_env_actor_joint_step`. Совместное действие — роли, action IDs, revision,
idempotency key и физическая длительность. Поддерживаются команды из нативного
TaskSpec, в том числе EO/CPU/relay/downlink. Python runtime или checkpoint в
инструментах не передаётся.

Наблюдение — набор существующих actor-only projections. У каждого аппарата
свои текущие entities, relations, catalogue и conservative mask; операторские
инъекции и чужая роль запрещены при исполнении. Это **один централизованный
LLM-контроллер команды**, видящий разрешённые локальные наблюдения её ролей,
а не уже реализованный протокол независимых распределённых LLM-переговоров.
Текст задачи задаёт вызывающая сторона: автоматически проверить отсутствие
секретов в произвольном пользовательском тексте невозможно.

Каталог содержит подготовленные оператором шаблоны команд. В network benchmark
он происходит из выбранных планировщиком цепочек; это подсказка о пространстве
действий. Benchmark оценивает исполнение такого каталога, **не** независимый
синтез полного плана, выбор всех возможных исполнителей или новую оптимальность.
Наблюдения наследуют ideal-current-local профиль и известные параметры команд;
они не выдаются за шумную реальную телеметрию или экспертные рассуждения.

Каждая попытка, включая невалидный JSON, тратит tool-call budget. JSON с NaN,
повторяющимися ключами, неизвестными аргументами или запрещённой ролью становится
ошибкой инструмента с неизменным физическим временем. Неожиданные программные
ошибки не превращаются в положительные обучающие метки. Успешный native retry
возвращает поля исходной квитанции вместе с текущим actor observation; для RL
повторный reward равен нулю и
`transition_applied=false`. Уникальные call IDs обязательны.

`max_dialogue_bytes` (по умолчанию 16 MB) останавливает продолжение после ответа,
пересёкшего бюджет: последний реальный ответ сохраняется для replay. Это бюджет
UTF-8, не число токенов; один завершающий ответ может его превысить. Отмена уже
выполненного физического шага из-за длины текста не производится. Для модели
адаптер должен отдельно ограничивать context window, tokens, timeout и стоимость.
Политика происхождения (`scripted_public`, `scripted_privileged`, `external_llm`,
`human`, `unspecified`) сохраняется как декларация источника, не аттестация модели.

### Генерация SFT/RL

Готовый воспроизводимый пример без внешнего API:

```bash
python examples/llm/generate.py --output /tmp/new-llm-data
python examples/llm/generate.py --audit /tmp/new-llm-data
```

Он генерирует `episode.json` (trainer-side audit), `sft.jsonl`, `rl.jsonl` и
`manifest.json`. Демонстратор знает расписание и явно помечен
`scripted_privileged`; данные не выдаются за ответы обученной LLM.

`verify_record()` восстанавливает начальную native-сессию, заново выполняет все
вызовы и сравнивает ответы, сообщения, метрики и финальный checkpoint. Требуются
зафиксированные исходники и совместимое native окружение. Перезапечатывание
изменённого ответа не заменяет replay. Полные сценарии, truth accounting и
checkpoints остаются audit-данными и не попадают в `messages`.

Один SFT sample — полный causal разговор с tools. `message_loss_mask` отмечает
только assistant; user/system/tool — контекст. Это **маска сообщений**: trainer
сам переводит её в token labels по chat template конкретной модели. SFT требует
всех положительно объявленных целей и либо завершения физического горизонта,
либо принятого `space_env_actor_finish`, а также отсутствия
ошибочных/rejected calls; rollout с частично доставленной миссией не становится
автоматически хорошим SFT. Replay и успех не означают экспертную оптимальность.

RL sample сохраняет разговор, per-call native rewards, physical-time discounts,
`transition_applied`, позиции assistant сообщений и `rl_group_id` для повторных
rollouts одной начальной задачи. Невалидные и неуспешные rollout сохраняются;
повторные idempotent calls не увеличивают return. Reward наследуется от
`TaskSpec.objective`, а не угадывается по тексту задания. В данном network-suite
native delivery reward и дополнительная benchmark-метрика weighted priority —
разные величины. Для обучения по SLA следует задавать нативную цель `sla` при
создании TaskSession. Trainer обязан согласовать выбранный reward, полные budgets
и grouping; logprobs, value estimates, PPO/GRPO/SFT optimizer этим экспортом не
вычисляются. Это готовый источник rollout, а не уже обученная модель.

Training export допускает только `split="train"`; development/test отклоняются
до публикации файла. Связанные случаи должны иметь корректную группу: ручной SDK
не способен распознать произвольно переименованные чужие данные. Frozen benchmark
использует существующий geometry-group split guard и связывает episode со своей
исходной конфигурацией. Для фабричных публикаций сохраняется существующий registry.

### Подключение модели

```python
from space_env.llm import LLMEpisode
from space_env.llm.benchmark import run_agent

episode = LLMEpisode(native_session, task_text=task, group=geometry_group,
                     split="test", max_calls=64, policy_origin="external_llm")

# Адаптер вашего inference server: callable получает ТОЛЬКО копии messages/tools.
# Возвращает {"name": tool_name, "arguments": json_string} либо None для остановки.

```

Адаптер провайдера самостоятельно обрабатывает generation/usage/timeouts и
выбирает один вызов инструмента за раз. Внешний model endpoint, ключи и платный
inference не включаются автоматически. Не передавайте модели audit record или
privileged schedule. Статус `external_llm` без реального запуска не создаёт
LLM baseline или доказательство learning improvement.

### Фиксированный benchmark

```bash
python -m space_env.llm.benchmark --output /tmp/new-llm-benchmark
python -m space_env.llm.benchmark --audit /tmp/new-llm-benchmark
```

12 frozen demand-cases / 6 geometry groups / train-development-test. На каждом
одна и та же начальная native-сессия, один task catalogue, 64 tool calls максимум.

Все строки, включая errors, остаются в знаменателе. Для неизвестных результатов

### Сравнение с другими проектами и критерий превосходства

Проверены первичные публичные источники, дата просмотра 2026-11-06:

- [Basilisk](https://avslab.github.io/basilisk/) документирует модульную
  астро/ориентационную динамику, Monte Carlo и real-time/HIL. Это важный ориентир
  по физике и проверке моделей; наличие у нас JSONL не доказывает превосходства
  над его динамикой или скоростью.
- [BSK-RL](https://avslab.github.io/bsk_rl/api_reference/index.html) уже имеет
  single-agent Gymnasium, tuple multi-agent и PettingZoo constellation tasking,
  конфигурируемые спутники, цели и intersatellite communication. Само наличие
  группировки или RL API не является нашим уникальным преимуществом.
- [Space Robotics Bench, статья авторов](https://arxiv.org/abs/2509.23328)
  описывает процедурную генерацию и массово параллельные робототехнические среды.
  Это ориентир по разнообразию и масштабу данных; его робототехнические task scores
  нельзя непосредственно сравнить с EO/CPU/ISL/Ground ACK.

Отсутствие отдельной возможности в краткой документации не доказывает её
отсутствия в проекте. Численный внешний head-to-head пока **не выполнен**;
Basilisk/BSK-RL в текущем окружении не установлены, согласованный adapter и
контракт общих задач ещё не реализованы. В отчёте это `not_run`, не score=0.
`competitor_superiority_established=false` и `llm_training_gain_established=false`.

Для доказательства преимущества нужны три отдельных эксперимента:

1. Общая физическая постановка: одинаковые эпоха/система координат, initial states,
   forces, integrator/tolerance, subsystem assumptions. Публиковать ошибки и
   ресурсы при заданной точности; не сравнивать surrogate с high-fidelity как равные.
2. Общие mission tasks и бюджеты: совпадающие deadlines, targets, capacities,
   observation privileges, action expressivity, Ground ACK semantics и stopping.
   Unsupported задача получает N/A с причиной, а не проигрыш конкурента.
3. Одни LLM/backbone/inference settings: zero-shot → train-only SFT → RL,
   одинаковые tool/token/cost budgets, новые заранее закрытые test/OOD groups.
   Измерять gain по native reward/constraints и перенос на внешний backend;
   отдельно стоимость получения пригодного train sample и replay/invalid rate.

Только после таких измерений можно заявлять превосходство по конкретной метрике
и области. Универсальное «лучше всех симуляторов» из этого пакета не следует.

### Первый локальный результат LLM data pipeline

Сквозной default-network demonstrator: native goal 1/1, 30 tool calls, без
failed/rejected calls; сгенерированы один полный SFT conversation и один RL
rollout, оба сверены аудитом. Это один scripted privileged пример, не результат
генерации или обучения внешней LLM.

Frozen catalogue benchmark: 36/36 scripted rollouts, 1728 tool calls, 12 train RL
файлов. На четырёх test-случаях weighted value: wait 0; public-memory и privileged
reference — 0,6175088132. Улучшения обученной модели здесь нет: модель не вызывалась.
Две test-геометрические группы дают только описательный результат.

Ни один из 36 demand rollouts не удовлетворил строгой full-mission SFT gate:
во всех остались невыполненные заявки. Поэтому benchmark экспортировал **0 SFT**,
а не переименовал partial delivery в успешную полную миссию. Следующий блок
фабрики должен задавать заранее достижимые положительные цели и явно объявленные
подзадачи длинных миссий; нельзя выбирать «цель» задним числом по успешному outcome.
Legacy term-coverage rubric не используется как оценка качества нового tool-agent
или как допуск к native SFT.

Локально: 89 тестов протокола/runtime/export/selector и 7 отдельных тестов
benchmark accounting прошли. Включены malformed/duplicate/nonfinite JSON,
role/operator guard, idempotency reward, source/native replay, semantic tamper,
train-only export, assistant masks и byte-budget stop. Это проверки реализации,
а не доказательство learning gain или аппаратной достоверности.

## Надёжный LLM-протокол: fixed cadence и реальные train-данные

### Что исправлено

Предыдущие неудачи сохранены: [prompt study](acceptance/QWEN35_PROTOCOL_STUDY_V1.json),
[brief/native-tool parser study](acceptance/QWEN35_BRIEF_STUDY_V1.json),
[JSON preflight](acceptance/QWEN35_JSON_PREFLIGHT_V1.json). Более длинная инструкция
не решила задачу: модель повторяла relay без локального продукта, ошибалась
ревизией, а Ollama иногда возвращала HTTP 500 при разборе повреждённого XML
вложенных tool arguments. Неуспехи не удалены и не считаются независимыми задачами.

`brief_v1` детерминированно представляет только **последнее публичное наблюдение**:
текущую ревизию, actor entities и relations с сохранёнными индексами, строковые
статусы вместо одних числовых кодов, available actions и причины blocked actions.
Старый initial snapshot не дублируется как якобы текущее состояние. Значения
получаются из actor projection; backend truth/расписание не читаются. В схемах
действий остаются только IDs из текущей публичной single-action mask, а native
joint admission по-прежнему может отвергнуть конфликтующую комбинацию.

`json_action_v1` использует JSON schema вместо native XML tool parser. Каждая
роль получает скалярное поле `action_i`, а не вложенный словарь `choices`.
Это объявленное ограничение до одного действия на роль за решение, не свободная
генерация произвольных команд. Корректный JSON с недопустимым физическим шагом
передаётся нативному инструменту и получает публичную ошибку с пределом времени;
SDK не обрезает длительность и не заменяет выбранные действия. Для данной
network-миссии `max_decision_sec=5`, не общий TaskSpec default 30.

Рабочий профиль — **`json_fixed_v1`**. Модель выбирает инструмент joint-step/finish
и каждое role action. SDK обслуживает служебные поля: expected_revision из
текущего публичного наблюдения, уникальный idempotency key и объявленный фиксированный
такт. В измерениях такт 5 с совпадает с cadence scripted baseline. Команда slew
может длиться много тактов: её длительность и физика не сокращаются. После каждого
шага приходит свежее наблюдение; отдельный observe не предлагается в этом профиле.
Ни wait, ни relay, ни downlink за модель не выбираются. Неверный JSON или ошибка
провайдера не превращаются в scripted fallback.

JSON grammar ограничивает синтаксис и предлагаемые action IDs. Поэтому выигрыш
относится к **интерфейсу, представлению наблюдений и ограниченному action space**,
а не только к тексту prompt и не к изменению весов Qwen. Это по-прежнему исполнение
операторского command catalogue, не независимый синтез миссии.

### Проверяемое завершение

`space_env_actor_finish` проверяет, завершены ли lifecycle requests фактическим
native delivery/ACK. Неполная цель получает `mission_incomplete` без движения
времени и без выдачи скрытых журналов. Принятый finish закрывает LLM-эпизод с
`verified_goal`; native reward за предыдущую доставку повторно не начисляется.
Последний RL discount равен 0 при успешном finish, даже без physical transition.
Завершение физического горизонта остаётся вторым корректным окончанием.

Проверена закрытая delivery-миссия с заранее заданными заявками. Для open-ended
миссий с будущими новыми обязательствами или отдельных safety/robustness целей
нужен явно заданный task-specific completion contract; predicate всех текущих
заявок не является универсальным сертификатом такой миссии. В измеренных LLM
прогонах здесь конец наступил по горизонту; ранний finish отдельно проверен тестом.

### Измеренный результат

[Итоговый receipt](acceptance/QWEN35_FIXED_WORKFLOW_V1.json):
старый control 0/1, fixed-profile development 1/1, две дополнительные геометрии
по 1/1, без failed calls во всех трёх успешных evaluation-прогонах. На каждом —
30 решений модели; исходный public-memory baseline также решает эти задачи.
Это **не превосходство над эвристикой или конкурентами**. Две дополнительные
геометрии ранее участвовали в проверке транспорта и являются regression cases,
не pristine blind holdout. Все случаи — близкие варианты одной delivery-семьи.
Fine-tuning не проводился; веса Qwen3.5:4b Q4_K_M не менялись.

```bash
python examples/llm/run_local_qwen.py --protocol-profile json_fixed_v1 --output /tmp/new-qwen-fixed
python examples/llm/run_local_qwen.py --audit /tmp/new-qwen-fixed
```

Аудит воспроизводит native episodes, восстанавливает каждое фактическое causal
окно, JSON schema, SDK metadata и преобразование model JSON в native tool arguments.
Сохраняются decoded и реально выданные calls: при multi-call ответе допускается
только исполненный prefix, а не выдуманное применение остатка после окончания.
HTTP errors сохраняют bounded response body/status; отсутствующий usage помечается
`usage_incomplete`, не считается точным нулём. LLM не пересэмплируется аудитом.

### Данные из реальной локальной модели

Отдельная **train-геометрия** зафиксирована до генерации, отличается от трёх
проверочных геометрий; reserved-split manifest проверяется до запуска. Модель
решила её 1/1 без ошибок. Получено:

- `rl.jsonl`: один нативно проверенный episodic rollout;
- `sft.jsonl`: один полный native-tool conversation;
- `wire-sft.jsonl`: **30 решений одной миссии** в том JSON-формате, который
  действительно генерировала Qwen, с её фактическими входами и ответами.

Wire SFT обучает semantic JSON; служебных SDK revision/nonces в target нет.
Маска сообщений — `[false,false,true]`; trainer сам переводит её в token labels
по chat template. Подтверждаются соответствие context/target/native event,
целый успешный goal, отсутствие ошибок и split=train. Test/development episode
не публикуется как train. Это execution-verified data, не expert qualification.

В этой миссии лишь 6 решений содержат non-wait actions, 24 — только ожидание;
30 строк не означают 30 независимых миссий. Балансировка ожиданий и расширение
семейств остаются задачами фабрики данных. Нет заявления, что обучение на этих
30 строках уже улучшило модель: обучения пока не было.

```bash
python -m examples.llm.generate_local --configuration train.json --reserved-splits reserved.json --output /tmp/new-local-train
python -m examples.llm.generate_local --audit /tmp/new-local-train
```

Неуспешные train rollouts сохраняются для RL; положительный SFT создаётся только
после quality gate. Имена файлов/групп не заменяют semantic registry: для большой
публикации нужно подключить существующий factory registry ко всем corpus bundles.

Локально **90 integration/agent tests + 5 wire-data tests passed**. Дополнительно
native/data audit выполнен из восстановленного source snapshot с совпадающими
зависимостями: путь и checksum локального архива сохранены в receipt. Веса в архив
не включены. Сами generated datasets и полные traces лежат в указанных `/tmp`
каталогах; воспроизводимые команды и компактные receipts сохранены в проекте.

## Корпус нескольких LLM-миссий — 8 ноября 2026

Следующий слой над отдельными эпизодами: `space_env.llm.corpus`. Он собирает native
эпизоды и provider-bound local bundles, повторно проверяет replay и wire context,
выводит только train-строки в `data/`, оставляя evaluation в privileged `audit/`.
Geometry identity берётся из общего `factory.semantic.split_group`, поэтому
factory и LLM-регистрация используют один и тот же локальный SQLite registry.
Дубли LLM-траекторий не становятся новыми примерами при смене prose/group.

Регистрация явная и отдельная от публикации файлов, с атомарным rollback всех
claims при конфликте. Успех сборки ещё не означает регистрацию. Одинаковая база
registry нужна всем производителям; независимого cross-format trajectory identity
с прежним factory форматом пока нет. Старый paragraph о необходимости подключения
registry выше описывает состояние на момент Qwen receipt; новый контракт закрывает
это для зарегистрированных native LLM corpora, не для произвольных внешних JSONL.

В отчёте отдельно считаются эпизоды, геометрии, splits, formats, policy origins и
ожидающие решения. Неуспешные вызовы остаются RL-данными, не становятся positive SFT.
