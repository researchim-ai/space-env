# Следующие этапы моделирования после 0.98.0

> **Текущая очередь после 0.134.0:** [INDUSTRIAL_ROADMAP_V0134.md](INDUSTRIAL_ROADMAP_V0134.md).
> Проверка: [V0134_STATE.md](audits/V0134_STATE.md). Ниже исторический план0.98;
> многие его части уже реализованы и требуют интеграционной приёмки.

Дата: 27 октября 2026. База — незакоммиченное рабочее дерево поверх `9a95032`.
Это актуальная очередь моделирования. Планы 0.93 и прежний конкурентный roadmap
сохраняются как история требований; выполненные части не реализовывать повторно.
Текущее состояние и проверки: [V098_STATE.md](audits/V098_STATE.md).

## 1. Целевой результат

Настраиваемая среда **исполнения целой миссии группировки**: орбита и бортовые
подсистемы, наземный сегмент, полезная нагрузка, задания, связи, задержки и отказы
образуют один причинно согласованный мир. Оператор, planner, RL/MARL и LLM работают
через один контракт команд. Данные обучения являются проверяемым следствием исполнения.

Первый проверяемый профиль — неоднородная LEO-группировка ДЗЗ с доставкой данных.
Не ограничивать архитектуру ДЗЗ, но новые режимы вводить только с отдельной
спецификацией, эталоном и критериями. Библиотека ещё не квалифицирована для полётов.

## 2. Что уже есть и не требует повторного создания

- MissionWorld с общими часами, постоянной книгой команд, резервами relay,
  проверкой горизонта и откатом при ошибке engine.step.
- Расширенный snapshot health/restores/attitude/RNG и исправление старого forecast.
- Арбитраж armed radio, дополнительные проверки YAML и semantic hash.
- Request scoring с разделением product_id, сравнение unmet при replay.
- MissionSession с revision, API создания/advance, FleetWatch на 1–4 аппарата.
- Smoke suite nominal/outage/infeasible/curriculum и включение Studio в wheel config.

Это полезная база, но отдельные реализации частичны. «Есть класс» не равнозначно
закрытому промышленному контракту. Новые конкретные дефекты перечислены в аудите.

## 3. Конкурентная цель

[BSK-RL](https://avslab.github.io/bsk_rl/api_reference/index.html) уже документирует
Gymnasium/PettingZoo, неоднородные группировки и обмен данными.
[Basilisk](https://avslab.github.io/basilisk/) документирует моделирование орбиты и
ориентации, Monte Carlo, HIL и Vizard. Наличие этих возможностей само по себе
не является нашим отличием. Не приписывать другим продуктам отсутствие функций
по одной странице документации и не обещать универсальную победу.

Наши проверяемые направления преимущества:

1. Сквозная проверяемость задания: команда → ресурс → продукт → квитанция → KPI.
2. Один benchmark для планировщиков, RL/MARL и LLM с одинаковой информацией и budget.
3. Связанные операционные ограничения и устойчивое перепланирование целой миссии.
4. Воспроизводимые данные, перенос политики между fidelity profiles и объяснение сбоев.
5. Меньше времени от нового сценария до воспроизводимого эксперимента и диагностики.

Превосходство подтверждается только по названному workflow/метрике и общему профилю.
Ускорение упрощённой модели против полной модели конкурента не считается победой.

## 4. Пакеты реализации

### M0. Закрыть семантику исполнения и восстановления — первый обязательный этап

Файлы: `simulation/world.py`, `commands.py`, `snapshot.py`, `mission/session.py`,
`tasking.py`, `api/server.py`, соответствующие contract/roundtrip tests.

1. Сделать accept/advance транзакцией: проверить дубли ID внутри batch, body conflicts,
   повтор одного actor, параметры и dt до записи. Snapshot брать **до** арбитража,
   снятия armed radio, изменения книги команд и передачи данных.
2. Адресация должна исполняться: request_id выбирает проверенную заявку/геометрию,
   destination_id — допустимую цель связи, cancel — существующую операцию.
   Неизвестная заявка не может получить completed. Ввести running/failed и
   завершать операцию по фактическому результату, а не отсутствию station conflict.
3. Обеспечить блокировку на сессию, атомарный revision check, idempotency request
   и ограниченные ресурсы API. Устранить скрытое изменение world.accept при плохом dt.
4. Самодостаточный JSON snapshot содержит конфигурацию, станции, цели, динамические
   события, состояние command batch и lineage. Восстановление не зависит от старого
   пути YAML; проверять version/hash до мутации. Согласовать KPI и журнал после resume.
5. Исправить outcome: проверять **каждую** acquisition и выбирать самое раннее
   допустимое полное выполнение. Более объёмный поздний продукт не отменяет ранний.
   Ввести строгие допустимые ranges, quality и повтор custody без удвоения.
6. Relay и downlink проводить внутри общего executor, с интервалами владения
   терминалом и моментом доступности данных. Не завершать будущую передачу заранее.
7. Проверять конфликты не только в начале шага, но и при входе в контакт внутри него.

Приёмка: новые случаи `v098_probes.py` превращены в regression tests; конфликтный batch
не меняет книгу; неизвестная заявка rejected; поздняя acquisition не стирает успех;
snapshot с Кирунoй восстанавливает Кируну; две конкурентные advance не исполняются
на одной revision. Проверки dt 1/5/10/60 с и восстановления внутри операции.

### M1. Контракт достоверности и reference pack

Файлы: `validation/`, `core/propagate.py`, `frames.py`, `time.py`, `integrations/`.
Зависимость: M0 для сквозного outcome; независимые physics fixtures можно готовить раньше.

1. Специфицировать training/reference profiles: силы, кадры, шкалы времени,
   интегратор, шаг/допуски, event tolerance и допустимая длительность дуги.
2. RK4 вычисляет время и зависимые координаты на каждой стадии. Ввести convergence
   и error budget отдельно для position/velocity, contact boundaries и outcomes.
3. Создать независимые fixtures: two-body/J2, drag, SRP/тень, третьи тела,
   EOP/время/frames, AOS/LOS, манёвр. Фиксировать источник и версию внешних данных.
4. Адаптировать имеющиеся backend integrations; TEME→GCRF вводить только после
   эталонной проверки. Optional backend не должен менять семантику mission commands.
5. Численные допуски выбираются из требований профиля **до** прогона, а не из
   получившейся ошибки. Для каждого fixture указать аналитический/внешний эталон.

Приёмка: offline report measured error/tolerance/source/applicability; одинаковый
тест различает намеренно испорченную модель и корректную. Внешний backend не заменяет
сам по себе validation. Не требовать bitwise parity между разными интеграторами.

### M2. Связанные модели борта и операций

Файлы: `core/spacecraft.py`, `attitude.py`, `power.py`, `thermal.py`, `simulation/engine.py`.
Зависимость: M0–M1.

1. Capability-based модель борта: режимы, ресурсы, разрешённые переходы, длительность
   подготовки/завершения, несовместимость imaging/slew/downlink/relay по конфигурации.
2. Attitude: quaternion, ограничения скорости/ускорения и settling; влияние pointing
   на съёмку и заряд. Мгновенная смена надписи режима не считается физическим slew.
3. Power: доступная генерация от ориентации/затенения, батарея и режимные нагрузки,
   гистерезис safe mode/recovery. Thermal: калибруемый упрощённый узел/сеть с limits.
4. Memory: throughput, processing, compression, продуктовые очереди, eviction/loss;
   пропускная способность и энергия обработки входят в расписание.
5. Propulsion: impulsive профиль отдельно от finite-burn; последний требует mass
   depletion, thrust bounds и event integration. Не выдавать прежний Δv budget за эту модель.
6. Паспорта аппаратов содержат значения, единицы, источник, uncertainty и assumptions.
   Сначала проверить существующие optical/SAR/CubeSat/relay модели; затем добавлять новые.

Приёмка: сохранение энергии/данных в выбранной модели; работа останавливается при
нехватке ресурсов; последствия slew и отказа воспроизводимы. Численные параметры
не выводятся из названия реального спутника без подтверждающих данных.

### M3. Реалистичная полезная нагрузка и спрос ДЗЗ

Файлы: `mission/factory.py`, scenario schema, sensor/access и outcome modules.
Зависимость: M2.

1. Заявки point/strip/polygon, revisit, stereo/multi-angle и зависимые операции.
2. Optical: off-nadir, illumination, cloud uncertainty, smear/settling и модель
   допустимого качества. Развести успешную экспозицию, обработку и доставку продукта.
3. SAR: incidence/swath/mode, duty cycle, energy/thermal constraints на уровне
   операций. Генерация физически достоверного raw SAR — отдельный проект.
4. Спрос задаётся независимо от удобных станционных проходов: AOI, urgency,
   сроки, конкуренция, приоритеты и доля недостижимых задач. Старые удобные точки
   остаются curriculum, а не доказательством реализма промышленного спроса.
5. Определить fairness/service-level и бизнес-полезность; нельзя просто максимизировать
   число снимков, игнорируя сроки, качество и доставку.

Приёмка: geometry/quality fixtures, выполнимые и невозможные заявки, проверенный
спрос вне текущей трассы. Включить 24/72-часовую миссию со связанными ограничениями.

### M4. Наземный сегмент и DTN-сеть

Зависимость: интервальный executor M0 и ресурсы M2.

1. Несколько антенн/терминалов, acquisition/setup times, выбранная станция,
   station outages, частотная/терминальная совместимость и конфликты расписания.
2. Планируемая скорость по geometry/link budget, явные допущения weather/error model;
   не считать видимость равной гарантированной передаче всех битов.
3. DTN: store-and-forward, queue priority, TTL, custody ACK/retry, processing latency,
   routing при смене topology, bandwidth sharing и half/full-duplex capabilities.
4. Добавить независимые задачи ground scheduling, routing и joint EO+delivery,
   использующие тот же physical state и command executor.

Приёмка: задержки и обрывы меняют фактическое время сдачи, нет сверхсветовой/ранней
доставки, дубликаты не создают продукт, невозможно занять один terminal дважды.

### M5. Неопределённость, отказы и безопасность миссии

Зависимость: M1–M4.

1. Разделить truth, измерения, state estimate и forecast; модель sensor noise,
   bias, sampling rate, missing data и задержки явно конфигурируется.
2. FDIR: скрытые причины и симптомы, деградация, ложные тревоги, safe mode и
   восстановление с затратами. Event injection и recovery не применяются задним числом.
3. Orbit knowledge: ограниченные измерительные профили с наблюдаемостью и covariance;
   не заявлять operational OD из короткой синтетической дуги одной станции.
4. Conjunction updates и avoidance с влиянием на полезную миссию. Pc и covariance
   transport проверяются независимыми примерами до заявлений о пригодности.
5. План обслуживания орбиты: phasing, station keeping, drag compensation, disposal
   с расписанием полезной работы. Выделить пределы моделей относительного движения.

Приёмка: агент не видит скрытую причину, знает только доступную информацию; одинаковые
noise streams воспроизводимы; безопасность оценивается отдельно от mission utility.

### M6. Общие интерфейсы агентов и проверяемый benchmark

Зависимость: M0; семейства задач добавлять после соответствующих M2–M5 gates.

1. Новая версионированная Gym-среда: конфигурируемые лимиты флота/заявок,
   Dict entities/masks, валидные адресные действия и доступный backlog/operations.
   FleetWatch сохранить: его лимит 4/16 и flat observation — текущая граница.
2. PettingZoo Parallel adapter поверх того же executor; задать коммуникации,
   CTDE/частичную наблюдаемость и правила наград. Тестировать эквивалентность joint action.
3. Typed tools для LLM: observe/forecast/submit/cancel/advance с ограниченным budget.
   Языковое описание плана оценивается исполнением, не сходством с teacher response.
4. Scenario registry, hidden holdout по epoch/region/demand/fleet, baselines
   random/FIFO/EDF/priority/rolling-horizon и tiny exact solutions с объявленной задачей.
5. Run artifact: конфигурации/модели, seeds/RNG, commands/events, полные product
   receipts, final state и KPI. Dataset RL/SFT/preferences строится из replay-verified
   записей; teacher и близкие варианты одного задания остаются в одном split.
6. Smoke suite оставить regression. Добавить learning experiment и статистический
   benchmark: failures входят в результат, все семена и compute budget сохраняются.

Приёмка: checker/API tests; реальный env.step parity с SDK/CLI, включая imaging request;
воспроизводимый train→holdout→reference evaluation; нет скрытых teacher/truth inputs.

### M7. Масштаб, Studio и промышленная поставка

Зависимость: M0–M6; profiling начинать раньше, не оптимизируя неправильную семантику.

1. Лестница испытаний: 16 аппаратов/100 заявок → 64/1000 → 256/10000, 24/72 часа.
   Это целевые нагрузки. Для каждой фиксировать CPU/RAM, connectivity, fidelity,
   logging, setup/reset, wall time и outcome equivalence.
2. Event queues, кэш geometry с invalidation, batching и episode workers по профилю.
   Bounded event storage и restart/resume не должны менять KPI.
3. Studio подключить к живым MissionSession: 2D/3D, ground track, footprint,
   timeline/Gantt, операции, resource utilization, причины отказа и сравнение run.
   Manual/autopilot используют один мир. API наличие не означает готовую UI интеграцию.
4. Wheel установить вне checkout в новое окружение, проверить assets/configs,
   CLI/API/dataset/replay. Сборка wheel в рабочем дереве недостаточна.
5. CI fast contract/reference/full profiles, compatibility/migrations, data/model
   licenses, limits, observability и support docs. Shared hosting — отдельный
   ownership/auth/quotas/isolation gate, не обязательная ранняя Kubernetes-поставка.

Приёмка: опубликованные локальные load/validation/install reports, проверенный
браузером workflow и клиентский пилот на разрешённых новых данных.

## 5. Как доказать преимущество

До измерения зафиксировать сопоставимый профиль с BSK-RL и reference tool:
версии, physics, данные, действия, objective, safety, hardware и compute budget.
Если функции не совпадают — сузить overlap и отдельно показать native возможности.

Оси сравнения: качество/выполнимость плана, violations, fidelity error, runtime/RSS,
dataset throughput, воспроизводимость и время настройки/диагностики.
Первые исследования — минимум 20 paired scenarios, затем объём уточнить по variance;
публиковать confidence intervals, failures и все исключения. Недоступный инструмент
остаётся unverified, а не проигрывает автоматически.

Предлагаемые продуктовые цели, **не текущие результаты**:

- Не менее 20% улучшения выбранной полезности при равном budget либо runtime при
  сопоставимом качестве и safety; критерий фиксируется до эксперимента.
- Не менее 30% сокращения времени до первого valid experiment/диагностики в пилоте.
- Никаких нарушений целостности и ресурсного владения в acceptance corpus;
  это не математическая гарантия для всех возможных миссий.
- Fast→reference degradation и все numerical tolerances укладываются в заранее
  согласованные пределы; плохие сценарии не исключаются после измерения.

Коммерческое преимущество подтверждается клиентом; технический benchmark его
не заменяет. Нельзя говорить «лучше всех симуляторов» по одному общему score.

## 6. Поручение следующему агенту

Первый проход: **M0 целиком + спецификация и небольшой reference pack M1**.
Не начинать с новых ID или очередного интерфейса. Превратить новые observations
в failing tests, исправить причины и проверить совместимость существующих миссий.
После этого выполнять M2 → M3/M4 → M5 → M6 → M7 с gates каждого профиля.

Для каждого этапа сохранять код, команды проверки, результаты, limits и artifact
hashes в `docs/IMPLEMENTATION_STATUS.md` и отдельном acceptance report.
Не объявлять внешний эталон, browser workflow или клиентский пилот выполненным,
если нет данных/доступа. Не коммитить, не пушить и не создавать PR самостоятельно.
